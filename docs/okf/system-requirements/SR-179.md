# SR-179 — The acceptance record can only be written by copying live text

**Requirement.** The kit shall refuse a recorded copy that is not byte-identical, in the commit
that writes it, to the live text it claims to record - so the only path into the
record runs through the live registry first.

**Acceptance criteria.** A commit that writes a recorded copy differing from its live counterpart is refused, which is the one comparison that catches a hand edit, a partial copy and a copy-then-amend-live alike; a faithful copy passes; a copy removed while the rest of the record stands is refused, while a wholesale replacement of the record is not; the first record refuses to create itself without an explicit seed, so no automated step can bless a tree; and prose that is not a recorded registry is exempt.

**Rationale.** MINTED 2026-08-18 by the SR-140 split (one-decision doctrine R1). This is the ANTI-LAUNDERING half, and it fails independently of both siblings: a comparison that reports drift faithfully against a record a hand edit wrote is a comparison against a forgery, so SR-178 can pass in full while this row is violated. It is what makes "the record holds what was actually blessed" a DECIDABLE property rather than a convention.
IN THE COMMIT THAT WRITES IT is the whole strength of the rule and the reason it is stated as a refusal rather than a report. One comparison, made at the moment of the act, catches a hand edit, a partial copy and a copy-then-amend-live alike - three attacks that need three different detectors if the check is made after the fact. It is the replacement for the co-mutation guard the abandoned on-row anchor design would have needed: a stronger rule for less machinery.
NOTE THE REVERSED SIGN, recorded so it is never read as a softening: under the anchor design a stamp written beside its own amendment HID the amendment, so same-commit was an error; under copies the copy MUST ride the approval commit, because riding it is the only thing that makes "this copy is what was blessed" decidable. Its companion rule, the SEED, is deliberately NOT here: refusing to create the first record without an explicit seed is a statement about how a record comes into being and rides its approval commit, which is SR-140's subject, so it sits there. This row governs every write AFTER that, which is where laundering actually lives.
DELETION IS AN ATTACK ON THIS ROW, not on SR-140's: the cheapest laundering is never to forge the record but to remove the page, since the unanchored rule reports a row whose copy reads below it and deleting the copy deletes exactly that evidence. So a registry removed WHILE THE REST OF THE RECORD STANDS is refused, and a wholesale replacement of the record is not - retirement is legitimate, and a rule that fired on it would make its own design undeployable.
