# SR-175 — Declared inclusion rule for content dispatched to a model provider

**Requirement.** The delivered loop content shall compose what it dispatches to an external model runner under a DECLARED inclusion rule rather than an implicit one — the content eligible for each dispatched brief, and what is excluded, readable as a declared set — with the basis on which repository content crosses to a declared provider stated as the scope of the consent the enabling surface grants, never presented as a technical bound on what an invoked runner reads.

**Acceptance criteria.** The inclusion rule for each brief class the loop dispatches is readable as a declared set naming what is eligible and what is excluded, so a composer can be checked against it rather than against convention; a planted credential inside brief-eligible content blocks dispatch (C-SEC-5's fit criterion, on the same scanner the transcript path already runs); the basis and exclusion for repository content crossing to a declared provider are stated where the provider is declared, and the consent surface's documentation names them as the scope of what enabling consents to; the pull channel is presented as consent-scoped, never as filtered. The conventions this row makes declared are, today, the planning surface's allowlist-only registry read and the composers' by-name exclusions and clipped log reads; the declared-set surface itself is the row's stated build gap.

**Rationale.** Hat-derived (hat.DATA-PROTECTION, with hat.SECURITY C-SEC-5 and hat.LEGAL C-LEG-3 converging on the same boundary control — three charters, three reasons, one crossing; clause texts in docs/plans/2026-08-16-blind-derivation-c-hats.md): repository content is briefed to external model providers, and for an adopter that content's history carries every contributor's name, email and timestamp — personal data crossing with no declared basis or exclusion in any need. SN-026's own text governs WHICH model runs, never WHAT IT IS SHOWN, so this obligation is content beyond the parent's demand — the derived-requirement class, labelled so the deriving lens is reviewable and the need owner sees it fed back (ruled at sitting-3 §0.4 item 8, 2026-08-17, adopting the intake proposal, docs/plans/2026-08-17-wi468-obligation-intake-options.md §1 option (b); the SN-026 amendment was the alternative, deliberately not taken alongside — one rule, one home). WHAT EXISTS TODAY IS A DISCIPLINE, NOT A DECLARATION: the push channel is measurably narrow — an allowlist-only planning surface, the project log excluded BY NAME in three composers, zero authorship fields formatted into any prompt — but the rule lives as a convention inside the composing functions, unfalsifiable because no requirement stated it; this row converts it into a stated one and the chain below pins the conventions as they exist. NOT YET MECHANIZED, stated rather than implied: the declared-set surface itself (a per-row inclusion/exclusion field on the provider registry, or a policy dial) and the planted-credential dispatch block in the acceptance are not built.
