# SR-042 — OKF knowledge-bundle export

**Requirement.** gen_okf.py shall export the spine registries AND the key process docs as a
generated Open Knowledge Format bundle under docs/okf:
one typed markdown concept per real row (graph as resolvable markdown links,
per-tier indexes);
plus a Process Guide concept per present process doc (a summary derived from
that doc and a resource pointer to the unmodified source).
The bundle shall be deterministic (no clocks), with --check failing on any
stale, missing or extra bundle file; docs/process.toml [checks] okf_export =
false silences (the legacy docs/okf-export is still read through the migration
window) and placeholder-only registries are vacuous.

**Acceptance criteria.** One frontmatter-typed file per real SN/SR/LLR/TC row whose graph links resolve; a Process Guide concept for each present process doc carrying a summary derived from the doc (not hand-authored) with the source left unmodified; regeneration is byte-identical; --check trips on a registry OR doc edit, a missing bundle and a hand-added file; the write mode prunes extras; off and placeholder-only registries pass silently, and process guides emit only alongside a real spine.

**Rationale.** Realizes SN-010 and SN-012 — traceability and process knowledge held only in this repo's own formats cannot be read by anything else, so the knowledge is trapped in the tool that produced it. The export is emit-only and stdlib-only, adding no runtime dependency and no parser: introducing a parser was rejected because reading the format back would make the bundle a second source of truth that can drift from the registries, whereas a derived bundle can only be STALE, which --check detects. Leaving the source docs untouched keeps the export non-intrusive, and the dashboard's Knowledge tab (SR-038) is its first consumer, so the bundle has a reader rather than being written for nobody.
