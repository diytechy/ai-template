# SR-140 — The attestation anchor lives on the artifact's own row

**Requirement.** The kit shall record each acceptance on the accepted artifact's own row - the
commit whose tree carries the text that was accepted, a digest of that row's
NORMATIVE cells, the transition accepted, and the acting reviewer that accepted
it, so an approval delegated to automation on a tier the declared ratification
level released is distinguishable BY QUERY from a human one - never in a second
registry keyed on the same artifact.
It shall report text that has moved away from its recorded anchor regardless of
any Status movement.
It shall treat an anchor written in the same commit as the text it anchors as an
error.

**Acceptance criteria.** An artifact whose normative text has moved since its recorded anchor is reported whether or not its Status moved; an anchor that cannot be recomputed, or that names an artifact which is not a current row, is a finding rather than silence; an acceptance recorded with no acting reviewer, or one whose acting reviewer cannot be told apart from a human's by query, is a finding — releasing a tier delegates the review, it does not skip it; a commit that writes an anchor cell while also changing that row's normative cells is refused, because a re-stamp in the same breath as an amendment hides the amendment; and the same rules hold for a stakeholder need, which has no Status cell for the amendment machinery to watch.

**Rationale.** Attestation STATE is already the row's own Status - derive_gate computes the gate from those cells and reads no other source - so a separate ledger was a second home for a fact the row already carried, and three of its seven columns duplicated cells outright (Decision=ratified|meaning IS Status; superseded IS SupersededBy). What the ledger got right is the ANCHOR ITSELF: 'has this been ratified' was answered by walking git for the newest commit where a row read Verified, which is sound only while every amendment flips its row in the same commit - precisely the sanctioned path the staged-amendment guard deliberately ignores. Two cells are kept rather than one because they fail in DIFFERENT directions: the commit is what a human can review and what the before/after brief diffs against, while the digest is what survives a squash-merge, a rebase or a shallow clone, any of which makes a recorded sha unresolvable and would otherwise silence drift detection repo-wide at once. Owner ruling 2026-08-09, docs/repo-lock.md D-1. One-shall waiver (13v): record / report-drift / refuse-same-commit-stamp are one anti-tamper contract whose clauses deliberately fail in different directions; splitting would mint three rows for one (SN-029, B-02) pair against the 13p invariant, and a participle re-word would bury two refusal contracts a TC must target by name. Extended 2026-08-15, WITHOUT adding a fourth shall: SN-029's DELEGATED-APPROVAL RECORD — "each automated approval on a released tier appends a durable record (row, transition, acting reviewer, commit) distinguishable from a human approval by query — releasing a tier means the review is delegated, never skipped" — had ZERO textual occurrence in the SR layer while `orphans=0` held (neither `delegated` nor `acting reviewer` appeared in any of the 64 rows). Two of its four fields, the row and the commit, were already this row's; the transition and the acting reviewer were the missing half, and they belong HERE rather than on SR-139 because this row is the one that says what an acceptance record contains and where it lives, while SR-139 says which tiers are held. The query-distinguishability is the load-bearing part: a record that cannot separate a machine approval from a human one turns a released tier into an unauditable one, which is the failure the need exists to prevent.
