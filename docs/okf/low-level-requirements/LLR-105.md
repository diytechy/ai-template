# LLR-105 — Interactive-control contrast in both themes (T5 core)

**Detail.** The mechanized core of usability anchor T5 (docs/rubrics/dashboard-usability.md): EVERY control painted over a node's own fill clears the WCAG 3:1 UI-boundary floor against EVERY node fill declared in STATUS_FILL/TIER_FILL/OKF_TYPE_FILL/SW_NODE_FILL/PHASE_ACCENTS, in BOTH themes — computed per fill (white or near-black, whichever contrasts more), never a single fixed hue. Covers the descend/hover/focus ring AND the containment/descend arrow (.cedge shaft plus its marker head), which derives from the same per-fill --ring token; its marker head takes a per-ink marker because marker content is rendered from the defs tree and cannot see the referencing node's custom properties (a constraint recorded in _arrow_markers), and RING_INKS is the closed ink set that makes that emission total. SCOPE: a control's contrast against its host fill, arithmetic like the sibling A4 tests. Whether the affordance otherwise reads as inviting stays perceptual under LLR-055/TC-055.

**Rationale.** A fixed hue vanishes on whichever fill happens to match it, and the failure is total where it lands: the measured collision put a control at 1.00:1 against its host, i.e. invisible. Fixing only the ring was rejected once the same fixed token was found on the descend ARROW — the very control a reader must find to descend a tier — measuring 1.06:1 light and 1.99:1 dark on a shipped phase fill. One control's fix does not generalise; deriving every such control from the host fill does.
