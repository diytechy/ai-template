# LLR-174 — Rate-limit recognition + bounded, surfaced wait

**Detail.** A rate limit is recognized only on an error signal (the JSON result's is_error, or a nonzero exit for a plain-text template) whose message carries a reset wording - a healthy transcript merely mentioning limits never reads as a throttle - and it wins the outcome ladder as WAITING, bypassing the stall guard. With --wait-on-limit set, a parsed reset within that ceiling is slept and the session retried, the sleep printed with its reset time; an unparseable wording sleeps min(--limit-retry-fallback, ceiling), printed, and retries. Past the ceiling, or without the flag, the run stops at EXIT_WAITING (5) with a banner naming the resume time. Both dials are declared flags with declared defaults (0 / 3600), never in-line literals. The outcome ladder itself (WAITING ahead of every other code) is LLR-028's home; this row owns the recognition gate, the two clocks and the wait/stop fork.

**Rationale.** The wait/stop fork keys on the one ceiling the human consented to, so an unbounded silent sleep is unrepresentable - the fallback nap is capped at the same ceiling for the same reason, and every arm prints what it is waiting for so a throttled run is tellable from a wedged one at the console.
