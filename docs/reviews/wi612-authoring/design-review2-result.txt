**Blocking**

1. **The read path writes into the primary repo.** Every uncached `carrier_candidate` runs `derive_tree`, whose scratch replay ends with `commit-tree` plus `git fetch` into the primary object store and FETCH_HEAD. That import is only needed by `publish`, which must `read-tree` the objects. On the identity path the tree sha comparison alone suffices and the objects already exist. Concurrent scheduler queries contend on FETCH_HEAD and each leaves a dangling carrier commit with a fresh timestamp. Parameterize `derive_tree` (for example `import_objects=False`) and pass False from `_verified_candidate`. This also makes IF-180's "may import Git objects" clause narrower and truer.

2. **Undeclared IF-175 requestors.** `primary_approval.py` and `primary_turn.py` import `kitlib.verdict` directly, and primary_approval reading round evidence unbound is now an explicit design decision of this WI. IF-175's own notes say an import no requestors entry carries is an undeclared seam. Add both, and state in the notes that primary_approval reads unbound by design at the pre-publication candidate.

3. **Probable ruff I001 in two files.** `primary_publication.py` has `from pathlib import Path` before `from functools import partial`, and `from kitlib import verdict` isolated between stdlib and local blocks. `tests/test_primary_session.py` has `import sys` inside the third-party block after `import pytest`. The bar runs ruff; verify before claiming green.

**Should fix**

4. **One predicate, two shapes.** `carrier_candidate` requires exactly one `Primary-Publication-Turn` trailer; `publication_commit` and `_verified_candidate` use a substring test that accepts two. A forged commit with a duplicated trailer is "completed" but not a carrier. Move the exactly-one check into `_verified_candidate` so completion and identity are literally the same proof, as LLR-207 now claims.
