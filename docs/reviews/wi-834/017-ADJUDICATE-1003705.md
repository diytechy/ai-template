## R16F1: a PowerShell assignment hides its command from the blackout hook

**What I observed.** I called `coordinator_guard.launch_reason`, the function
the PreToolUse hook denies from, on this repository's own `docs/agents.toml`
(model CLIs `claude`, `codex`) at HEAD 1003705d.

| PowerShell command | Decision | Segments |
|---|---|---|
| `claude -p x` | deny | |
| `$response = claude -p x` | allow | `[['$response', '=', 'claude', '-p', 'x']]` |
| `[string]$r = claude -p x` | allow | |
| `$a, $b = claude -p x` | allow | |
| `$r += claude -p x` | allow | |
| `$env:X = claude -p x` | allow | |
| `$r = (claude -p x)` | deny | |
| `$r = & claude -p x` | deny | |
| `$r = $(claude -p x)` | deny | |
| `$r = ... \| claude -p x` | deny | |
| `$r = 'claude -p x'` | allow (correctly) | |
| `$r = "claude -p x"` | allow (correctly) | |

Bash `r=$(claude -p x)` is denied. The cause is `_segment_command`, which
skips only POSIX `NAME=value` words, so the PowerShell assignment target
`$response` is taken as the command.

In a real PowerShell session, `$r = cmd /c echo LAUNCHED-RHS`, `[string]$s =
...` and `$a, $b = ...` each ran the right-hand command and captured its
output. A single-quoted right-hand side stayed literal. The builder's account
of the code holds.

**Scope.** Unlike R4F1 (sitting 005), the reproduction needs no contrived
input:
- `$x = some-command args` is PowerShell's ordinary way to capture a command's
  output, the direct counterpart of Bash `r=$(...)`, which the hook already
  denies.
- An agent capturing a model's answer would write exactly this.

So it is content agents write in a normal environment, and in scope.

It also breaks the declared coverage. The Part B Done-when and LLR-300 promise
denial of "a `Bash` or `PowerShell` call naming a model CLI as any command
word, including after ... `VAR=value` prefixes". In
`$response = claude -p x`, `claude` is the command word PowerShell runs. The
hook is supervision rather than enforcement (ruling (f)), but a supervision
rule that misses the ordinary capture form fails open on normal use, which §6
counts as a bug.

**Cost.** The fix stays at the one shell-reading boundary, where the earlier
rounds placed this class:
- the PowerShell dialect skips a leading assignment target and operator, and
  reads the next unquoted, non-variable word as the command;
- a quoted right-hand side stays data (`$r = 'claude'` must not become a false
  denial, so quotedness must survive the reading);
- regression cases are added to TC-339's evidence.

The builder estimates about 30 to 45 lines plus tests. That is small next to a
blackout fail-open on a common form. The row texts (LLR-300's "command word",
TC-339) already describe the intended behaviour, so this should need no
re-attestation unless their wording changes.

RULING: R16F1 FIX the PowerShell reading takes an assignment target as the command word, so `$response = claude -p x` (and `[type]$r =`, `$a, $b =`, `+=`, `$env:X =`) launches a model through the armed blackout hook, while plain `claude -p x` and `r=$(claude -p x)` are denied; this is ordinary output capture inside the declared "any command word" coverage, not evasion, and the fix belongs in the one shell-reading boundary with quoted right-hand values kept as data
