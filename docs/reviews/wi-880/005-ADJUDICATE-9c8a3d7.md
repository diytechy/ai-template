# WI-880 dispute adjudication: 005 at 9c8a3d7

Scope bound: `project-trajectory/PROCESS.md` §6, "Review threat model". A review hunts defects in the content agents write into the repository, in supported configurations, and in regressions of supported behaviour. A finding is out of scope when reproducing it needs a compromised or contrived host: a fake or hostile binary, a working-directory-dependent shim, PATH changed mid-call, or a tampered tool.

## G1: a `[run]` line's bare `python` on Windows resolves from the working directory first

**What I observed at the range.** `run_menu.py` is unchanged between `fd55051a` and HEAD. I ran it on python.org 3.11 against a scratch `docs/stack.ini`. My session's environment carries `NODEFAULTCURRENTDIRECTORYINEXEPATH=1`, which the agent harness sets. With that variable present, the reviewer's line `cd /d C:\Python38 && python -c ...` printed `3.11.9 ...\Python311\python.exe`, so the finding looks refuted. With the variable unset, which is a stock Windows console, the same line printed `3.8.10 C:\Python38\python.exe`. A second route needs no `cd` at all. With a `python.exe` copied into the working directory the menu starts from, a plain `python -c ...` line printed `3.8.10 ...\g1\python.exe`; with it removed, it printed 3.11.9. In both routes cmd's current-directory lookup runs before the PATH that `_interpreter_dir` prepends.

**Scope.** In scope. The reproduction needs no compromised host. Both inputs are repository content: a declared `[run]` line, or a file at the root the launchers `cd` into. The configuration is the default Windows command processor. The §6 exclusion for "a shim whose output depends on the working directory" does not cover this case, because the interpreter at work is a real, unmodified install.

**Is it a defect?** Yes, but in the approved TEXT, not in the code.
- **What the spine promises.** SR-046, blessed in sitting 003, promises that a line using bare `python` "resolves to the floor-resolved interpreter on every supported platform". LLR-047 promises a directory "whose bare python runs the menu interpreter exactly on every platform". Both statements are false on Windows for a line whose working directory holds a `python.exe`.
- **Why that matters.** A blessed claim that a constructible repository input falsifies is exactly what the approval record must not carry. My own sitting-003 blessing missed it.
- **The coordinator's two arguments.** The first holds only for the `cd` route: a line that changes into an interpreter's directory has chosen that interpreter. It does not hold for the repository-root route, where the line chose nothing. The second argument is decisive against the reviewer's remedy, though: `NoDefaultCurrentDirectoryInExePath` in the child environment changes how every bare command of every adopter's Windows line resolves. A `cd tools && mytool` line would stop working. That is a shipped migration far larger than the defect, which needs an interpreter binary sitting in a line's working directory. CLAUDE.md's "edit conservatively" points the same way.

**The fix, so the argument ends here.** Make the spine true by narrowing it. Do not change the child environment.
- **Amend SR-046 and LLR-047** to state the Windows exception plainly. On Windows, the command processor resolves a bare name from the line's working directory before PATH. A `python.exe` in that directory, whether the repository root the launchers start from or a directory the line changes into, therefore runs instead of the menu interpreter. The guarantee covers lines whose working directory holds no interpreter. The reasoning in D-003 does not need repeating; record the choice as a lane decision beside it.
- **Extend the RESYNC sentence and the docstring of `run_menu._interpreter_dir`.** Each needs one clause on this route.
- **Extend TC-047** with the boundary, if the lane keeps it mechanized. Such a test must unset `NoDefaultCurrentDirectoryInExePath` explicitly, because this harness sets it and would otherwise hide the route.
- **Route the amended rows** to a fresh amendment sitting.

RULING: G1 FIX SR-046 and LLR-047 claim bare python is exact "on every supported platform", but on Windows cmd resolves a python.exe in the line's working directory (a cd'd interpreter dir, or the repository root) before the prepended PATH; reproduced with the stock lookup (3.8.10 ran). Fix by narrowing the two rows (plus the RESYNC sentence, docstring and TC-047 boundary) to state that exception, NOT by setting NoDefaultCurrentDirectoryInExePath, which would change every bare command in every adopter's Windows lines.
