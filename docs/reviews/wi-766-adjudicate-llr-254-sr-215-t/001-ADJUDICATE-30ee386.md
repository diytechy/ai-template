## Re-attestation

I would bless TC-036, TC-055, TC-209, TC-210, TC-211 and TC-247 as written. They carry out the owner's signed direction in WI-747 ("a declared trigger with a floor"; "first judgement as today"; "max_age stays as the backstop"), and the five rubrics they cite exist under `docs/rubrics/`.

I would NOT bless SR-215, LLR-254 or TC-248:

1. SR-215 AcceptanceCriteria and LLR-254 Detail: the first decision rule reads "No result is due immediately" / "No record is due immediately". Read literally, that says nothing is due immediately, which inverts the rule. PROCESS.md "Observation judgement" says it unambiguously: "A case with no result is due immediately". A requirement's first rule must not parse two ways.
2. SR-215 AcceptanceCriteria: "Every observation case references a numbered rubric written before its first judgement" is an authoring obligation that the Requirement cell never states. "Written before its first judgement" and "numbered" are also observed by no check (LLR-294 tests only that the Rubric cell is non-empty). trace.py flags the same thing mechanically: "SR SR-215 Rationale/AcceptanceCriteria names a CRITIQUE instrument (... a rubric) while Verification is 'Test'". The authoring rule's one home is PROCESS.md, which already states it. The SR's acceptance should carry only the mechanized half: an omission warns.
3. SR-215 Coincident and Title were not amended and are now false. The Coincident cell still says the need "asks for an observation's result re-judged when what it judged changes; one re-judge item filed per stale case is that outcome", but the floor now deliberately withholds a re-judge after a change. That limit derives from the owner's cost and determinism direction; it is not coincident with the need. The Title, "a changed or expired observation test is queued once", no longer describes the decision.
4. LLR-254: CodeSymbol names `checkpoint_for` (the coordinator tagged it at landing), but the Detail states no obligation for it. A builder cannot tell from the row what it must return: the case's explicit release or stage-gate checkpoint, else merge.
5. TC-248 Method: LLR-255 (Approved, unchanged) requires the release checklist to carry "a required item ... naming that command and the count". TC-248 is LLR-255's only verifier, and its amended Method no longer says it checks the item is required or names the command. A test following the new text could pass a checklist that LLR-255 forbids. The current test still asserts both (`test_the_release_checklist_carries_the_required_rejudge_item`), so this is a text regression, not a code one.

Gap noted for the successor, not a reason on its own to withhold the text: SR-215 says the harness files "when ... a stage gate is checked". Nothing that checks a stage gate files or prompts anything. The only path is a person running `intake.py rejudge --checkpoint stage-gate`, and unlike release (whose checklist carries a required item, LLR-255), no gate surface names that command.

Because TC-248 is not blessed, the test-case registry cannot be copied this sitting. A copy is refused while any drifted approved row in it is left out of `--reattests`. So the six TC rows I would bless stay drifted, and they are re-judged with the corrective amendment. SR-215 and LLR-254 are not re-anchored. The follow-up is drafted in `## Dispositions` of `docs/work/queued/WI-766-adjudicate-llr-254-sr-215-t.md`.
