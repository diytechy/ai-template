- [MEANING] SN-003 need -> before: a team in **any language** can use the process. The promise covers every language, and adoption means re-pointing the harness at that stack's tools -> after: a team can use it **on a stack whose tools it declares in a stack profile** -> the universal over languages is now conditional on the team's declaration and on what a stack profile can express. If a language's tools cannot be stated in the profile's schema, the new text is met for it (the condition never fires) while the old one is broken. The kit owns that schema, so the reach of the promise now follows a kit artifact. The old acceptance already required a declared toolchain, so in practice the gap is small. It is still a narrowing of who is promised, not a rewording.
- [MEANING] SN-008 need -> before: a pass verdict never hides a skipped check, a stub, or **an unmet criterion** (any criterion) -> after: never hides **an unmet declared criterion** -> the honesty promise used to cover any unmet criterion. Now it covers only the criteria that are declared. A gate whose declared set leaves out a criterion can pass with that criterion unmet and satisfy the new text, while a reader of the old text would call that a hidden unmet criterion. The acceptance cell is unchanged, and it only ever tested declared items, so the narrowing is small. The need's promise to the reader moved all the same: how complete the declared set is no longer falls under this need.
- [CLARITY] SN-009 need -> before: a secret or private identity is caught before it publishes, **in every repo**, without extra setup (always on, no opt-in) -> after: caught before it publishes **in a repository that adopts this process**, without extra setup -> same promise. The kit acts only in a repo it is dropped into (README vision; in MULTI_REPO each member repo runs its own `check.py`). So "every repo" could only ever mean every repo carrying the kit, and the generic "a repository that adopts" still means any of them. "Without extra setup" is kept, so it is still always on, and the acceptance (an always-on floor on every commit's staged diff, message and outgoing range, with privacy behind its dial) is unchanged. A system delivering one delivers the other.
- [MEANING] SN-025 acceptance -> before: next work is derived from the WI DAG plus Git, **never from prose or a hand-maintained pointer, and never from predefined tracks**; the human-read status surface is **generated, never hand-copied** -> after: derived from the WI DAG plus Git **alone**; the status surface is **generated from that tracked state** -> two acceptance conditions moved. (1) The explicit exclusions are gone. Prose and a hand-maintained pointer are themselves files tracked in Git, and a "track" can be encoded in tracked state, so "Git alone" no longer rules them out the way the old cell did by name. A launch reading a committed next-step pointer could plausibly pass the new text and fail the old. SR-148 still carries "no prose surface and no predefined track", but the need-level acceptance no longer requires it. (2) The status surface gains a source condition: it must be generated *from the tracked state*. A surface generated from anything else (for example untracked runtime state) passed the old text and fails the new. The need cell is unchanged.
- [MEANING] SN-043 need + acceptance -> before (need): a reviewer sees whether each premise **has itself been checked**; (acceptance): each premise shows **whether a current result evidences it**, a premise **relied on without evidence is visible as such**, and a premise shown false is reported with every requirement relying on it -> after (need): whether any premise **has been shown false**; (acceptance): each premise shows **its approval status and whether it has been shown false**, and a premise shown false is reported with its relying requirements -> both cells moved. The evidence axis is removed: an unchecked premise is no longer flagged and no longer separated from one that was checked and survived. A new approval-status display is required. Falsification is now the only truth signal. A system delivering the old text (evidence status shown, no approval status) fails the new text, and the reverse also holds.

## For the owner

- **SN-003:** The promise went from "any language" to "any stack whose tools the team declares in a stack profile". In effect that is what the old acceptance already demanded, so the change is small. Signing as written is reasonable. If you want to keep the universal intent, "a stack whose tools can be declared in a stack profile" would read as a capability of the kit, not a duty on the team.
- **SN-008:** "Unmet criterion" became "unmet declared criterion". This is the satisfiable form of the promise and I would sign it. Note that it moves completeness of the declared criteria out of this need, so check that another need (for example SN-004's coverage) still carries it.
- **SN-025:** The acceptance lost its explicit "never from prose, a hand-maintained pointer or predefined tracks" exclusions. "Git alone" does not clearly rule out a pointer file committed to Git. The status surface also gained a "generated from that tracked state" condition. I would not sign as written unless the exclusions are restored or "alone" is pinned to exclude committed prose and pointers. SR-148 still states them, so restoring them at the need level costs nothing.
- **SN-043:** This realizes your signed 2026-10-02 assumption ruling: status and standing only, falsification as the one signal, no evidence ladder. The checked/evidenced axis is gone from both cells, and approval status is shown in its place. The text matches the ruling, and I would recommend signing it as written.
