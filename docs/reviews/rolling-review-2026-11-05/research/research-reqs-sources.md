| INCOSE's solution-free rule is conditional on rationale, not absolute. | INCOSE Guide to Writing Requirements v4 summary sheet (INCOSE RWG, 2023), rule R31 Solution Free, https://www.incose.org/docs/default-source/working-groups/requirements-wg/guidetowritingrequirements/incose_rwg_gtwr_v4_summary_sheet.pdf (snippet fetched 2026-11-05; PDF not reached — incose.org ENOTFOUND) | Avoid stating implementation in a need statement or requirement statement unless there is rationale for constraining the design. | The kit already models 'unless rationale' at SR (waiver token in Rationale); extend the same recorded-waiver route to the LLR tier instead of the blanket template instruction to name symbols. |
| At every tier, a 'what' requirement states what is needed at that level, not how it is met. | INCOSE Guide for Writing Requirements (2019 ed.), §4.9.1 R31 /ABSTRACTION/SOLUTIONFREE, mirror https://www.reusecompany.com/wp-content/uploads/2020/11/Incose-GfWR-2019.pdf (snippet fetched 2026-11-05; PDF not reached) | Design input, design-to 'what' requirements should state what needs to be stated for that level of the entity, not 'how' the requirement should be met. | Supports the skill's 'solution-freedom is tier-relative' framing; at LLR the 'how' that is legitimate is the decomposition choice, and the code remains the next level's 'how'. |
| 'Appropriate to level' is the published name for the detail-altitude characteristic. | INCOSE GtWR characteristic C2 Appropriate (v3/v4); INCOSE Webinar 171 'Appropriate Requirements: Writing Requirements at the Proper Level' (Wohling, 2024-02-21), https://incose.org/events-master-hidden/2024/02/21/default-calendar/webinar-171-appropriate-requirements-writing-requirements-at-the-proper-level ; ArgonDigital summary of the IW 2015 update, https://argondigital.com/blog/training/incose-guide-to-writing-requirements-updates-made-at-iw-2015 (snippets fetched 2026-11-05) | Appropriate – specific intent and amount of detail is appropriate to the level of the entity to which it refers. | Gives spine-questions §3 a one-line test for the 759-char-median LLR detail: 'is the amount of detail appropriate to the design level?' with a warn-only length advisory as its detector. |
| ISO/IEC/IEEE 29148's implementation-free characteristic hinges on the word 'unnecessary'. | ISO/IEC/IEEE 29148:2011 §5.2.5 characteristic 'Implementation free', paraphrased in a US National Archives IR quality-standards template, https://www.archives.gov/files/contracts/hipgfi/ir-templates/ir-quality-standards-strs-pdd.docx (snippet fetched 2026-11-05; standard text not reached; 2018 edition renames it under 'Appropriate', clause 5.2.5) | the requirement, while addressing what is necessary and sufficient in the system, avoids placing unnecessary constraints on the architectural design. | A fit criterion is a measure of the requirement's meaning, not the test, and its absence signals ambiguity. | Robertson & Robertson, Mastering the Requirements Process, 3rd ed. | A test case is defined by its preconditions, inputs and expected results. | ISO/IEC/IEEE 29119-1 definition of 'test case', via imbus glossary https://www.imbus.de/en/glossar/term/test-case and ASAM report https://report.asam.net/test-case (snippets fetched 2026-11-05; standard not reached) | set of preconditions, inputs (including actions, where applicable), and expected results, developed to drive the execution of a test item to meet test objectives | The TC template's `expected` instruction ('Cite ... by id') removes a defining element of a test case; `expected` must state the result. |
| The test case specification and the test procedure specification are separate documents. | ISO/IEC/IEEE 29119-3:2021 'Test documentation' (Test Case Specification as informative annex; 2013 ed. clause 7.3), https://www.iso.org/standard/79429.html and https://en.wikipedia.org/wiki/ISO/IEC_29119 (snippets fetched 2026-11-05; field list not reached — a secondary source lists identifier, objective, preconditions, inputs, steps, expected results, postconditions, environment, traceability) | Test Design Specification; Test Case Specification; Test Procedure Specification | The kit's `method` cell is carrying the procedure specification; keep objective/inputs/expected/traceability in the registry row and the procedure in the test. |

| Describe behaviour, not implementation; the test for wording is whether it would change with the implementation. | Cucumber documentation, 'Writing better Gherkin', https://cucumber.io/docs/bdd/better-gherkin/ (snippet fetched 2026-11-05; page not reached directly) | would this phrasing need to change if the implementation changed? | One-line test to print in the TC template comment for `expected` and `method`, and in AGENTS.template.md for test names. |

| Tests should map to behaviours, not methods, and prefer public APIs over implementation-detail classes. | Google Testing Blog, Testing on the Toilet: 'Test Behavior, Not Implementation' (Trenk, 2013-08-05) https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html ; 'Test Behaviors, Not Methods' (2014); 'Prefer Testing Public APIs Over Implementation-Detail Classes' (2015-01) (snippets fetched 2026-11-05; bodies not reached) | tests and public methods shouldn't have a 1:1 relationship | AGENTS.template.md has no test-authoring bar beyond red→green→refactor (line 41); these three titles are the bar in three lines. |
| Tests that mirror the implementation add no clarity and block refactoring. | Alex Eagle, Testing on the Toilet: 'Change-Detector Tests Considered Harmful', Google Testing Blog, 2015-01-27, https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html (snippet fetched 2026-11-05; body not reached) | do not add any clarity, and you cannot safely refactor code | README §5.1's baseline dict literals of every module's line count are change-detector tests by this definition — published grounds to retire them into warn-only steps. |
| Tests should be behavioural and structure-insensitive. | Kent Beck, 'Test Desiderata', Medium, 2019, https://medium.com/@kentbeck_7670/test-desiderata-94150638a4b3 ; newsletter 'Desirable Unit Tests' https://newsletter.kentbeck.com/p/desirable-unit-tests (snippets fetched 2026-11-05; full essay not reached; GitHub README needs add_repo) | Structure-insensitive — tests should not change their result if the structure of the code changes. | Name these two properties as the kit's test bar; a `::node` evidence pin and a symbol list in `detail` violate structure-insensitivity at the registry level. |
| Every observable behaviour becomes a dependency once enough users exist. | Hyrum Wright, 'Hyrum's Law', https://www.hyrumslaw.com and Software Engineering at Google (2020) (snippets via secondary pages fetched 2026-11-05; primary not reached) | With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody. | Every refusal sentence a test pins and every function name a registry pins is a frozen interface; assert tokens and outcomes, name files not functions. |
| Practitioners loosen exact error-message asserts to a key phrase or regex unless the wording is itself the contract. | xh/hoist-react issue #4775 'Review the unit test suite for enshrined behavior and brittle assertions', https://github.com/xh/hoist-react/issues/4775 ; discuss.python.org 'Asserting exact exception instances', https://discuss.python.org/t/asserting-exact-exception-instances/83763 ; Playwright brittle-text guide https://webcrawlerapi.com/glossary/playwright/how-to-fix-playwright-brittle-exact-text-assertions (snippets fetched 2026-11-05) | loosen them to a key phrase or a regex where the wording is not itself the contract | The kit's rule should be: pin wording only where an SN makes the wording the stakeholder contract; otherwise a stable token — this discharges README §5.2's 724 literal asserts by policy rather than by edit. |
| Testing one object through another is a named test smell: Indirect Testing. | van Deursen, Moonen, van den Bergh, Kok, 'Refactoring Test Code', CWI report SEN-R0119 (2001), Smell 8, https://core.ac.uk/download/301655481.pdf ; restated in Bavota et al.
