### Batch 1 (searched 2026-11-05)
- DO-178C LLR def (via Wikipedia/Parasoft snippet): "Software requirements derived from high-level requirements, derived requirements, and design constraints from which source code can be directly implemented without further information." https://en.wikipedia.org/wiki/DO-178C ; https://www.parasoft.com/learning-center/do-178c/unit-testing
- CAST-15 "Merging High-Level and Low-Level Requirements" (FAA CAST position paper, 2003): applicants "were combining High-Level and Low-Level Requirements for 'simple' products, but were not accomplishing all of the related objectives for both levels"; recommends not merging; superseded by DO-248C FAQ #81; content in EASA CM-SWCEH-002 (2012). https://en.wikipedia.org/wiki/CAST-15
- Wikipedia DO-178C: "the ambiguity about the concept of low-level requirements, may not be fully resolved."
- INCOSE GtWR v4 summary sheet R31 Solution Free: "Avoid stating implementation in a need statement or requirement statement unless there is rationale for constraining the design." https://www.incose.org/docs/default-source/working-groups/requirements-wg/guidetowritingrequirements/incose_rwg_gtwr_v4_summary_sheet.pdf
- GtWR 2019 (reusecompany pdf): "4.9.1 R31 - /ABSTRACTION/SOLUTIONFREE Design inputs avoid stating a solution unless there is rationale for constraining the design." ; "Design input, design-to 'what' requirements should state what needs to be stated for that level of the entity, not 'how' the requirement should be met." https://www.reusecompany.com/wp-content/uploads/2020/11/Incose-GfWR-2019.pdf
- GtWR characteristic C2 Appropriate: "specific intent and amount of detail is appropriate to the level of the entity to which it refers." (argondigital 2015 update; INCOSE webinar 171 "Appropriate Requirements: Writing Requirements at the Proper Level" 2024-02-21, Wohling) https://incose.org/events-master-hidden/2024/02/21/default-calendar/webinar-171-appropriate-requirements-writing-requirements-at-the-proper-level
- Hooks 1993 "Writing Good Requirements" (NCOSE proc.): "writing implementation (HOW) instead of requirements (WHAT)" among most common problems (via LSU course pdf) https://laspace.lsu.edu/laaces/wp-content/uploads/2021/01/R22.01_Writing_Good_Requirements.pdf
- 29148 "implementation free" paraphrase (archives.gov IR template): "the requirement, while addressing what is necessary and sufficient in the system, avoids placing unnecessary constraints on the architectural design. The objective is to be implementation-independent." https://www.archives.gov/files/contracts/hipgfi/ir-templates/ir-quality-standards-strs-pdd.docx ; 2018 ed clause 5.2.5 individual / 5.2.6 set
- Volere fit criterion: "an objective measure of the requirement's meaning; it is the criterion for evaluating whether or not a given solution fits the requirement" (Robertson & Robertson, Mastering the Requirements Process ch.12) https://www.oreilly.com/library/view/mastering-the-requirements/9780132942850/ch12.xhtml ; "if a fit criterion cannot be adequately specified, then the requirement is ambiguous, or ill understood" (reqview volere template)
- Kent Beck Test Desiderata (Medium 2019): "Behavioral — tests should be sensitive to changes in the behavior of the code under test. If the behavior changes, the test result should change." "Structure-insensitive — tests should not change their result if the structure of the code changes." https://medium.com/@kentbeck_7670/test-desiderata-94150638a4b3 ; 12 properties; newsletter "Desirable Unit Tests".
- SWE at Google ch12 (Winters/Manshreck/Wright 2020): "the ideal test is unchanging: after it's written, it never needs to change unless the requirements of the system under test change." (goodreads highlight). TotT "Test Behaviors, Not Methods" (2014): tests and public methods shouldn't have 1:1 relationship.
- Hyrum's Law (Software Engineering at Google / hyrumslaw.com): "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody."
- TotT "Change-Detector Tests Considered Harmful" (Alex Eagle, 2015-01-27): tests that mirror implementation "do not add any clarity, and you cannot safely refactor code" https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html ; also "Prefer Testing Public APIs Over Implementation-Detail Classes" (2015-01), "Test Behavior, Not Implementation" (2013-08) https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html ; "Only Verify State-Changing Method Calls" (2017-12)
- EARS original: Mavin, Wilkinson, Harwood, Novak, "Easy Approach to Requirements Syntax (EARS)", RE'09, IEEE, pp.317-322 (Rolls-Royce, jet engine control airworthiness regs); Big EARS RE'10; Easy EARS RE'11.
