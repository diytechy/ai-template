## SR-140 — Each acceptance is recorded by a copy riding its own approval commit


### SR SR-140
- **Rationale**
  - before: Attestation STATE is already the row's own Status - derive_gate computes the gate from those cells and reads no other source - so a separate ledger is a second home for a fact the row already carries, and three of its seven columns duplicated cells outright (Decision=ratified|meaning IS Status; superseded IS SupersededBy). What a ledger gets right is the BASELINE ITSELF: answering 'has this been ratified' by walking git for the newest commit where a row read Verified is sound only while every amendment flips its row in the same commit - which is neither the sanctioned staged-amendment path nor the ratification ladder, so the walk returns HEAD and the diff is empty BY CONSTRUCTION on exactly the rows a sitting exists to judge.
The record is therefore a whole-file copy of the accepted registries into docs/archive/last_approved/, riding the SAME reviewed commit as the approval. Three things follow. First, the commit, its date and its author come FROM that commit, so no cell has to carry them and no cell can lie about them. Second, the record is diffable by every git tool and by eye - a record only a script can read is a record only a script can audit. Third, the copy MUST ride the approval commit, because riding it is the only thing that makes "this copy is what was blessed" decidable. Anti-laundering rests on the MIRROR INVARIANT - any commit touching the record must leave it byte-identical to its live counterpart, so the only way to write text INTO the record is to write it live first, in a reviewed commit - together with the SEED RULES: the first copy refuses to create itself without an explicit seed, so the initial blessing cannot happen by accident, and an absent record is None rather than {} so it can never read as "re-bless everything with no diff shown".
ONE DECISION PER ROW, and the three clauses fail in different directions, so they separate cleanly: RECORDING an acceptance (this row), REPORTING text that has moved away from the record (SR-178), and REFUSING a record written from anything but the live text (SR-179). A record that exists and rides its approval commit while nothing ever compares live text against it satisfies this row and not SR-178; a comparison that reports drift faithfully against a record a hand edit wrote satisfies SR-178 and not SR-179. Three rows on one (SN-029, B-02) pair is what a need with three separable obligations looks like, and the alternative - one row whose partial pass has no id to report against - is the defect the split rule exists to prevent.
SN-029's DELEGATED-APPROVAL RECORD is this row's. Two of its four fields are supplied by the mechanism rather than by a cell: the ROW is in the copy, and the COMMIT is the approval commit. The transition (the copy's Status against live's) and the acting reviewer (the approval commit's author) belong HERE rather than on SR-139 because this row is the one that says what an acceptance record contains and where it lives, while SR-139 says which tiers are held. The query-distinguishability is the load-bearing part: a record that cannot separate a machine approval from a human one turns a released tier into an unauditable one, which is the failure the need exists to prevent.
