## SR-146 — Prompts are reviewable files with a per-session audit trail

> **Requirement.** Every prompt the delivered loop launches or an attended launcher renders as a review or critique brief shall be a shipped, reviewable file with strictly filled slots — listed by digest in a freshness-gated generated catalogue, each loop session recording which template it used and the fingerprint of what it rendered to.

> **Rationale.** Prose steers the sessions this loop launches and had been reviewable only by reading Python source, which makes the process trusted rather than inspectable. The audit trail is the part that makes the move useful rather than cosmetic: without a per-session digest, "which instruction did this session see" stays an inference. (The argv-vs-shell-string transport decision is design, and lives one tier down in LLR-163.) C-SEC-5 requires that content composed for dispatch to an external model runner carry a DECLARED inclusion rule rather than an implicit one — a prompt assembled inside source is an unreviewed egress path no write-side gate covers, and shipping it as a reviewable file with a digest is what makes that rule readable.

## SR-148 — Autonomous loop work selection: what it derives from, and in what order

> **Requirement.** The delivered loop content shall select exactly one work item for each assignment an unattended run admits from the repository's tracked registries and git history alone, in this order: ready adjudication rows first, as a stable partition applied at admission rather than by renumbering the ruled rank table; then unresolved handback records; then the earliest incomplete spine tier in SN-to-SR-to-LLR-to-TC order; then implementation work after test-case layout is complete — with the eligible set and its order deterministic, an item whose declared safety, policy or plan-mode inputs are missing, undeclared or contradictory failing closed for that item alone, operator holds applied only from the declared acceptance level, nothing admitted past an operator-held stop, no prose surface and no predefined track in the derivation, no hand-curated next-work or run-phase pointer surface shipped for any live instruction or executable surface to read, write, validate, generate or link, and the status surface a session reads generated and freshness-gated rather than hand-copied.

> **Rationale.** Without one precedence rule, the same repository can resume into implementation while returned obligations or prerequisite requirement tiers remain unresolved. ## SR-209 — Every commit the loop makes carries a checked provenance trailer

> **Requirement.** When a commit is made from a process the unattended loop started, or is merged in a lane the loop owns from the point the loop took that lane over, the delivered commit floor shall refuse it unless it carries a valid provenance trailer naming the loop and its session.

> **Rationale.** A status change on an operator-held rung can be told apart from an operator's only if every loop-made commit says it is one. Without a floor that holds every loop commit to it, a trailer could appear on only some of the loop's commits and a missing one would prove nothing. Where a commit is made, the condition is who made it, not when: a person committing in another checkout while the loop runs is not the loop. Where a lane merges, the floor sees commits, not processes, so it reads whose lane it is from the commits and judges every commit of a loop lane, a person's included: there an unmarked commit the loop made cannot be told from a person's, and a person's commit belongs in the person's own lane. The commits made before the loop took a lane over are exempt, since nothing then could have marked them. Refusing the unmarked commit at the floor makes the mark total, which is what lets a later check treat its absence as meaningful. The floor where a commit is made is local and a determined bypass defeats it, which is why the merge re-checks a loop lane and the history check stands behind both.

## SR-238 — A deadline or interruption ends the session process tree

> **Requirement.** When a declared deadline or coordinator interruption ends a session, the delivered coordinator shall end every process in the session process group on POSIX or session job on Windows.

> **Rationale.** A descendant can outlive the direct session child and keep editing the worktree handed to the next session. Ending only the direct child was rejected because it leaves that concurrent writer outside the coordinator's supervision. The bounded guarantee excludes a descendant that leaves the session process group and a process another service starts outside the session job: neither is ended, and the kill does not report it. A POSIX zombie under a PID 1 that never reaps keeps the group nonempty, so the kill raises after the bound. A descendant that denies the kill access to wait on it also makes the kill raise, rather than letting the coordinator continue without knowing whether it ended. Stopping is the need's cannot-proceed case, not a supervision fault: continuing would hand the worktree to the next session beside a writer that may still be live, and nothing can proceed safely past that. Two windows lie outside the guarantee, each sub-second and on no supported workflow's ordinary path: an interruption while the session is still being launched, before the coordinator supervises it, which can leave a running child; and a process that joins the session job while the kill takes its member list, which is terminated with the job but can still be ending, for milliseconds, when the coordinator continues.
