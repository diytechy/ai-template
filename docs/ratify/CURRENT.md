Keeping a separate serial resume path beside the dispatcher was rejected: two authorities over one decision drift, and the divergence surfaces as a run that resumes differently depending on how it was started.

- **Detail**
  - before: SR-179 is the anti-laundering half of the record, and its mechanism is a sibling of LLR-158's comparison basis rather than a part of LLR-173's record. staged_snapshot_findings(root, base, head) is a whole-commit rule, not a per-row one: in ANY commit that touches the last_accepted record, every touched file must be byte-identical to its live counterpart AS OF THAT SAME COMMIT. One comparison is what makes a hand edit, a partial copy and a copy-then-amend-live all fail, and it is why no separate co-mutation guard is owed - the abandoned on-row anchor design would have needed one. It reads the INDEX and the commit-ish alike (matching _spine_revs' prefix contract), so it fires at the hook where the act happens rather than after the fact. THE DELETION ARM is the half a first reading misses and is deliberately asymmetric: _snapshot_survives is the two-line tree probe that separates a registry removed WHILE THE REST OF THE RECORD STANDS (refused - deleting the copy deletes exactly the evidence the unanchored rule reads, which is cheaper laundering than forging one) from the record going away WHOLE (silent - retirement and a wholesale replacement are both legitimate, and a rule that fired on them would make its own design undeployable).   - after: SR-179's refusal, made where the act happens and asked again of history. In any commit that writes a registry's copy in the acceptance record, the copy must equal the copy that commit's act writes (LLR-245): the copy in the commit's parent - none when the parent holds none or holds one that does not parse - with the rows the act names taken from the live registry in the same commit and every other row placed as that rule places it. The rows the act names are the ids that the act-ledger entries the commit adds list as accepted or re-accepted; a commit that adds no entry names no row. That one comparison fails a hand edit, a partial copy, a copy-then-amend-live, an unnamed row's drift carried in, a named row copied with an edit and a row dropped that no act retired, and its finding names each such row, or names the file when the difference lies outside every row. A copy written in a record whose act ledger held no entry listing kept rows (LLR-361), by a commit that added none, was written whole, and is judged as it was written: byte-identical to its live registry in that commit, so a record written before the row-by-row write reads clean with no rewriting. At the pre-commit hook the rule judges the index against the last commit, the act-ledger entries a merge brings in naming their rows too, so a merge carries the other side's act; on every integrity run it judges each copy's last writing commit against that commit's parent, so a divergence that landed with the hook skipped stays reported. THE DELETION ARM is deliberately asymmetric: a registry's copy or the act ledger removed while the rest of the record stands is refused, since deleting a copy deletes the evidence the unanchored rule reads and deleting the ledger erases which acts were taken; the record removed whole passes, since retirement and a wholesale replacement are legitimate. The record's prose stamp has no live counterpart and is exempt, and the act ledger is exempt from the copy comparison for the same reason. Its findings join the always-on integrity floor.
- **Rationale**
  - before: The record is worthless if anything but a copy can write it, and "only a copy writes it" is a claim no per-row check can make - a per-row rule sees the row it is given and never the commit that wrote it. Placing the invariant on the COMMIT is what converts a convention into a decidable property. It lives in check_trajectory rather than in baseline_snapshot because the writer must not also be the judge of its own writes: the module that copies has every reason to believe its copy is faithful, and the guard exists for the cases where it is not.
  - after: The record is worthless if anything but a copy of live text can write it, and “only a copy writes it” is a claim about the commit that wrote the record, which a reader of one row cannot make. Judging each writing commit against its own parent, its own live text and the rows its own act-ledger entries name is what makes the claim decidable at the row. The judgement lives apart from the writer because the writer must not also be the judge of its own writes: the two share one statement of what an act writes, the writer applying it to the working tree and the judge re-deriving it from the committed trees, so a writer that took the wrong parent, the wrong live text or the wrong rows is refused. Judging a copy written before the row-by-row write by the rule it was written under keeps every existing record readable without a migration; the cost is that a whole-file copy written with no act behind it passes until the record's first row-by-row act, as it did before.

## SR-207 — An acceptance act carries into the record no drift it does not itself accept

> **Requirement.** The kit shall leave, in an acceptance act, the recorded text of every row the act does not accept, re-accept or retire whose accepted text, or whose adjudicated links, differ from its live text.

> **Rationale.** An acceptance act once refreshed a registry's record by copying the whole file, so it carried every row of the file as it then stood. The kit therefore refused the act while any row it did not accept or re-accept had drifted. That kept the record to what someone saw, but it coupled every row of a file: one unblessed amendment held every blessed amendment and every first acceptance in its registry until it was ruled or reverted. Leaving each such row at its recorded text keeps the same protection by construction, since an act cannot carry text it did not name, and removes the coupling: the drifted row stays visibly drifted and owed, and no longer stops the act. Adjudicated links are the links whose change goes to an adjudicator: a requirement's needs and boundary crossings, a design row's requirements and a test case's verified rows. They are held like accepted text because the record is what tells whether that change has been settled. A row's other trace cells, which no verdict judges, and a row claiming no acceptance follow the live text whenever an act writes their file, so the record stays comparable line by line with live. The rule holds for any number of tiers in one file.

## SR-212 — With the assumption gate on, interface-form requirements are bridged at their crossings and reached and bridged at the architecture rung

> **Requirement.** Where the assumption gate is enabled, the delivered harness shall fail, for each system requirement of interface form, the boundary gate when the requirement is not recorded as coincident and names a crossing on which no assumption it cites lands, and the architecture gate when no boundary interface reaches it or a reaching boundary interface neither records it as coincident nor bridges it by an assumption the requirement also cites.

> **Rationale.** A requirement meant to be met at an interface is not testable until that interface exists and its reading is either the outcome or carried by an assumption the requirement itself relies on. The frame's crossings are the first such interfaces: they are accepted with the frame at the boundary rung, before any interface row exists, and an assumption already names the crossing it lands on, so the requirement is judged against them there. Judging it again at the architecture rung, against the boundary interfaces that realize the crossings, keeps interfaces after the requirements they answer. Minting interface rows to match a count would produce seams with no contract behind them, so the check reports the gap rather than inventing the seam.

## SR-217 — A requirement implemented before its test cases were accepted is reported

> **Requirement.** The delivered harness shall report each system requirement accepted after the project's declared starting point whose implementation has landed on trunk while any of its test cases was not yet accepted for it, reading the order from the committed history.

> **Rationale.** Tests written after the code tend to describe what the code does rather than what was required, so the order is the evidence that a passing run means the requirement is met. The stage ladder puts test cases before implementation for a project as a whole, but not requirement by requirement, and the committed history is the one record of order that no cell can restate after the fact. Code declaring which requirement or design row it implements is the one event that marks an implementation landing. A requirement's acceptance is its entry into scope, so judging only requirements accepted after a declared starting point keeps a project that adopts the rule from being judged on history written before it; a project that declares none is judged whole. A test case is evidence for a requirement only once it is accepted while it names that requirement: dated from its own acceptance alone, a test case accepted for something else could be re-pointed at code already written and lend it an order it never had. A test case not yet accepted is the same gap at its widest, since its passing run shows only that the code does what unaccepted text says; the report names it with a warning rather than withholding the result, which a reviewer can still weigh.

## SR-248 — A design row past Drafted is discharged by a test case verifying it

> **Requirement.** The delivered harness shall report as undischarged each design-tier row past its Drafted status that no live test case verifies.

That claim is discharged by the evidence of the row's own kind: a test case verifying it, executable through its declared tests or an inspection, analysis or attestation through its declared evidence. A row still Drafted is being written and makes no such claim yet, so the rule reaches it once it leaves Drafted. Binding discharge to a code symbol the row names pointed down at the code, so every rename reopened an accepted row while the code's own back-links already stated the same link upward. Where a design row sits and which files realize it are obligations of their own (SR-249, SR-250).
