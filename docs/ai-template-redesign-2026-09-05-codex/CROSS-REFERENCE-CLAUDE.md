**Date:** 2026-09-05. **Comparison revision:** `32a08c24bd03ad2fd45a17ae53d82b29cadf21fa`. **Workstream:** `redesign-codex-crossref-2026-09-05`, isolated worktree `ai-template-wt-codex-crossref`. Proposal only: no runtime, policy, registry, test-selection, or approval changes.

Compared this directory's README, implementation packages, LLR/rendering supplement, and Fable dispositions with Claude's [revised PLAN](<../ai-template-redesign-2026-09-05 - claude/PLAN.md>), [spine census](<../ai-template-redesign-2026-09-05 - claude/A-spine-census.md>), [module map](<../ai-template-redesign-2026-09-05 - claude/B-module-map.md>), [external-tool survey](<../ai-template-redesign-2026-09-05 - claude/C-external-tools.md>), and [review dispositions](<../ai-template-redesign-2026-09-05 - claude/review-01-dispositions.md>). The reviewed revisions matter: several stronger claims in the initial Claude proposal were withdrawn. Neither that review nor the earlier Fable review reviewed the changes in this document.

## Overall assessment

The plans agree on the product: authoritative intake and consolidation, scheduler-owned admission, one WI per lane, controlled review, and a smaller harness. Both retain Git and migrate in slices rather than replacing the entire reusable kit. Claude gives more attention to common parsing/prompt boundaries, operator resumption, and whether a rewrite is necessary after recent fixes. This plan gives more explicit treatment to mutation authority, approval holds, exact evidence identity, recovery, and enabling contract amendments before live migration.

The most valuable correction to this plan is to make a kernel replacement conditional. A simpler architecture is an attractive hypothesis, not evidence that implementing it will outperform the repaired current loop. P0 now measures that loop before selecting retain, targeted repair, or replacement. Independently useful renderer and boundary improvements need not wait for a replacement decision.

One WI per lane remains a good target because it assigns one scope and acceptance decision to a worker. It is not a complete explanation of the existing complexity. Claude's module census attributes only about 100 code-only lines directly to batching; its larger figure includes documentation. Those are census estimates, not a reproduced benchmark here. More importantly, its cited single-row close failure demonstrates that reducing cardinality does not settle integration evidence. Scheduling simplicity and integration correctness must be evaluated separately.

## Where this plan retains a different position

**Authority and enablement.** Keep P1A's narrow, approved requirement/design/test amendments before enabling incompatible behavior. A decision to simplify does not invalidate existing normative obligations automatically. Keep current-trunk approval authority, conservative handling of unknown independence, held-work semantics, and one mutating coordinator. Do not adopt Phase 0's review/consolidation dial changes merely to improve baseline metrics. Those are separately authorized behavior experiments.

**Integration and migration.** Claude's close-before-review option is plausibly cheaper and is now a P5 comparison arm. Our candidate-tree/receipt proposal remains conditional on evidence that its total protocol is simpler and preserves provenance and restart behavior. Do not label retained refresh peeling as eliminated, or assume a review of an earlier base approves changed composed code. Alternating live runners is not a safe rollback specification by itself: require compatible state transitions, one writer, durable recovery, and preservation of accepted history.

**LLR meaning and identity.** LLRs may legitimately describe implementation mechanisms; the defect is treating those mechanisms as unchangeable, or giving unjustified detail normative force. Counts of amendments versus deletions do not measure how frequently designs were replaced, since a same-responsibility amendment can replace the mechanism. Keep the parent-clause test and ordinary approval rules. Do not require every meaningful design change to mint an ID, apply stakeholder-need wording rules indiscriminately to implementation contracts, or add a keyword ratchet for supposedly over-specific LLRs.

**Retirement and budgets.** Do not adopt target module counts, fixed code/test shrink percentages, or blanket removal of entire need classes as acceptance criteria. A classifier calling an obligation internally originated does not authorize its removal. Preserve bounded concurrency, subjective verification, accessibility, public compatibility, and every other approved acceptance clause unless the owner explicitly changes the obligation. Measure test families and actual runtime paths rather than equating line counts with burden.

**External tools.** Claude's landscape is useful as a candidate inventory, but a worktree helper, workflow library, or agent framework does not automatically replace this kit's approval and evidence semantics. No new dependency is selected in this cross-reference. Existing Git/CLI/provider adapters remain the default. A proposed replacement tool needs a bounded trial against one responsibility, supported-platform behavior, recovery, integration cost, and maintained upstream documentation. This review does not revalidate the survey's time-sensitive ecosystem or licensing claims and does not adopt its broad absence-of-alternatives claims.

## Source corrections and unresolved inconsistencies in Claude's plan

These are findings about the compared text, not edits to Claude's documents.

1. **Rendering smoke premise:** PLAN §0/§2.9/§4.7 attributes per-commit cost to `test_traj_graph` being outside `SLOW_MODULES`. [tests/conftest.py](../../tests/conftest.py) includes it in that set at both `a9bf6cee` and `32a08c24`. Full-suite/CI costs still matter; the claimed smoke saving must be measured anew.
2. **Automatic re-baselining remains in execution instructions:** §4.5, §8, and the review dispositions withdraw automatic re-baselining, while Phase 4 still prescribes it and §7 retains the decision prompt. Adopt the withdrawal, not the stale execution bullet. A weakened baseline is not evidence of reduced cost.
3. **Shared parsing is not shared failure policy:** §2.7 and revised Phase 2 preserve caller policy, while §4.1 still calls for one failure behavior. This plan adopts shared syntax with caller-specific decisions.
4. **Peeling scope:** §4.4 retains refresh handling; broader statements about removing the verdict peel overstate what moving mechanical close accomplishes. P5 compares complete protocols rather than names.
5. **Existing row history rules:** [repo-lock D-4](../../docs/repo-lock.md) requires deletion of superseded rows and preserves history in Git/log; it explicitly records removal of the spine's live `SupersededBy` mechanism. A new live supersession carrier would need justification and an amended ruling. [acceptance_record.py](../../project-trajectory/scripts/acceptance_record.py) already separates traced and approved cells, so reference-only moves need not be sold as a new normative-approval exception.

## Resulting implementation order

1. P0 records obligations, reproduces representative failures, establishes the downstream oracle, and measures the repaired loop under declared conditions. Select retain, targeted repair, or replacement from that evidence.
2. P2 common boundaries and P9R rendering extraction can proceed where independently justified, with their applicable contract amendments. Maintain full CI initially and preserve compatibility.
3. If replacement is justified, P1/P1A establish state and enabling contracts; P3/P4 implement intake/admission; P5 compares integration options before P6 hardens dispatch/recovery.
4. P7 adds controlled sessions and honest owner resumption. P8 demonstrates the selected complete loop. P9 retires only mapped obsolete mechanisms; P10 closes migration and compatibility obligations.

The updated README, IMPLEMENTATION, and LLR-AND-RENDERING documents are the operative proposal. The raw Fable review, dispositions, metadata, and Claude source plan remain intact. Historical Fable input hashes describe that earlier review, not these later edits. No implementation or live-loop operation is authorized by this comparison alone.
