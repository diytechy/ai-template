# WI-175 — Harden the .venv/interpreter boundary against coverage debris

> **ARCHIVED 2026-07-20 — WI-251 spec-lifecycle sweep.** Spec-of-record for **WI-175** (all `done`; deliverables in `docs/requirements/work-items.csv`, session records in `docs/log.md`). Absorb-verified before archiving: every durable decision has a live spine/architecture/process home (dispositions in the log, 2026-07-20 entry).

**Status: done (owner-directed, implemented 2026-07-15).** The owner noticed
thousands of `.coverage.DESKTOP-OFFICE.*` files stranded at the repo root and
asked whether a cleanup activity was missing. Investigation traced it to the
**wrong-interpreter** failure mode WI-105 already documented, and the owner asked
for a single WI carrying three hardening recommendations.

## What actually happened (the diagnosis)

The debris was one full `--cov` run's worth of parallel coverage fragments
(3259 files, 1192 PIDs, a 3-minute window), gitignored (`.coverage.*`) so it
never showed in `git status`. Root cause: the run used the **ambient global
interpreter** `C:\Python38\python.exe`, which carries **pytest-cov 4.1.0** — the
exact pre-5.0 version `.coveragerc` / WI-105 warn about, whose parallel-combine
races and strands debris. The repo's own **pinned `./.venv` was correct**
(pytest-cov 5.0.0) and would have combined cleanly, but the run bypassed it.

So this is **not a missing cleanup step** and **not a too-low pin** — WI-104's
pins (`~=7.0` on 3.9+, `~=5.0` on the 3.8 floor) already sit above the break, and
5.x is the ceiling on the 3.8 floor (pytest-cov 6.0 dropped 3.8). It is a
**wrong-interpreter** gap: nothing steered the coverage run onto `./.venv`.

## The three recommendations

### Rec 1 — prefer `./.venv` in the harness/hook (ALREADY SHIPPED — verify only)

The shipped pre-commit hook **already** probes and prefers `./.venv`
(`project-trajectory/hooks/pre-commit` lines ~36–56: it runs each venv candidate
before trusting it, handles the Windows Store alias, and falls back to a PATH
python), and `check.py` runs the product/coverage command under `sys.executable`
— which the hook has made the venv interpreter. So the **commit path is already
covered**. The only residual is a **direct, non-hook `--cov` run launched with a
global interpreter** — the local-call the owner explicitly disclaimed ("that's on
whoever is using the CLI").

**Considered and declined:** making `check.py` re-exec itself under `./.venv`
when present. It is a **kit-shipped** script with downstream blast radius (a
downstream repo may deliberately run a non-`.venv` interpreter, or name its env
differently), it would fix only the disclaimed local call, and Rec 2 + Rec 3
deliver the same intent (steer + warn) without magic re-exec. No code change for
Rec 1.

### Rec 2 — pin the interpreter for VS Code (`.vscode/settings.json`)

VS Code's Python extension auto-discovers `./.venv`, but only governs paths *it*
launches (Run/Debug, Test Explorer, its activated integrated terminals) — not the
agent's shell tool, git hooks, or a bare terminal, which is where the debris came
from. For the human-in-VS-Code path, pin `./.venv` as the default interpreter and
wire pytest as the test runner so Run/Test use the pinned toolchain, not a global
python.

### Rec 3 — ambient-interpreter debris warning in the meta `dev-setup`

`dev-setup --check` reports on `./.venv` once it exists (its `PY` prefers the
venv), so it never inspects the **ambient PATH python** — the one a bare
`python -m pytest` actually hits. Add a warn-only line (never changes the exit
code) that probes the PATH interpreter and, when it differs from `./.venv` and
carries a **pre-5.0 pytest-cov**, names it and points at `./.venv`. This turns
the silent trap into a printed warning at the exact moment a contributor is
inspecting their setup. Scoped to the **meta** twins
(`scripts/dev-setup.{sh,ps1}`); the downstream `dev-setup.template.*` is
deliberately untouched (the pre-5.0-race specificity is the meta suite's, not a
generic downstream property).

## Non-goals / follow-ups (not this WI)

- No standalone `.coverage.*` sweep target. WI-105 already ruled the pinned
  toolchain leaves zero debris and self-heals (erase-at-start); an unconditional
  sweep is a separate call the owner can make if the smoke-only cadence (no
  `--cov`, so no combine) ever proves to leave stragglers in practice.
- No change to the downstream-shipped `dev-setup.template.*` or `check.py`
  interpreter contract (downstream repos own their env discipline).
