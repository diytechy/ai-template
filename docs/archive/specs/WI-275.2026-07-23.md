# WI-275 — Windows shim-refusal-aware fixtures for the two SR-026 launch tests

**WI:** WI-275 · **Status:** queued · **Delivers:** SR-026 (test layer only —
no product change)

## Problem

Two tests are red on Windows at HEAD — verified 2026-07-23 on the dev box
(3.11.9 venv, pinned toolchain; full suite otherwise green: 1369 passed /
5 skipped / 2 failed) and verified **pre-existing** (identical failures on a
clean tree before the day's dial/filing commits). Both are green on
macOS/POSIX, which is why the owner's macOS runs never saw them:

1. `tests/test_agent_loop.py::test_cmd_shim_cli_spawns_on_windows` — the WI-120
   regression test (a `.cmd`-shim CLI must spawn via the which-resolved path).
2. `tests/test_session_stdin.py::test_run_session_codex_reads_last_message_not_transcript`
   — the WI-217 codex `--output-last-message` capture test (Windows arm builds
   a `codextest.cmd` shim).

Root cause is not the product: the H-4 BatBadBut hardening (repo-review
2026-07-21, remediated in `272a6e8`) added
`agent_session._validate_prompt_transport`, which **refuses prompt-in-argv
launches through a Windows batch shim** — `_batch_prompt_error` fires whenever
`stdin_input is None` and `argv[0]` resolves (directly or via `shutil.which`)
to `.cmd`/`.bat`. That refusal is deliberate, tested behavior. The two fixtures
predate it and collide with it:

- Test 1's `--agent-cmd` fixture template carries `-p {prompt}` — prompt-in-argv
  — so the launch it asserts must succeed is now (correctly) refused.
- Test 2 calls `al.run_session([str(launcher)], tmp_path, 30)` with no stdin
  delivery, so the guard fires on the bare `.cmd` launcher even though no
  prompt token is present — while the *real* codex rows deliver the prompt via
  stdin (`stdin_input is not None`, WI-216/217) and never trip it.

**Why this fronts the queue (Priority 1, the column's first use):** the branch
is unpushed, so CI — which runs the suite on Windows (3.11 + latest) — has
never seen these reds; on push the Windows legs go red, blocking the
`dualplan-routing-fix` merge path. Everything else about the fix is small.

## Approach

Test-layer only; the H-4 guard, `build_argv`, and `run_session` are untouched.
Make each fixture exercise its *original* concern through the transport the
product now prescribes:

- **Test 1 (WI-120 spawn):** drop `-p {prompt}` from the fixture's
  `--agent-cmd` template so the prompt rides stdin (the WI-216 path), and make
  the fake CLI read the prompt from stdin where its assertions need it. The
  `.cmd` shim still spawns through the which-resolved path — WI-120's
  CreateProcess concern stays fully tested — and the launch is now
  transport-legal. Optionally add the cheap negative arm: the *same* shim with
  a `{prompt}` template is refused with the H-4 message (locks both invariants
  in one place).
- **Test 2 (WI-217 capture):** call `run_session` the way the coordinator
  actually launches codex — with stdin prompt delivery (`stdin_input` not
  None), matching the real no-`{prompt}` codex CmdTemplate. The `.cmd` launcher
  then passes the guard and the `--output-last-message` capture assertion runs
  as designed. (Alternative if the signature makes that awkward: a native-exe
  launcher — e.g. a copied `sys.executable` named `codextest.exe` — but stdin
  delivery is truer to the seam under test; prefer it.)
- **POSIX arms unchanged** — both tests already pass there; the edits must not
  alter the non-Windows fixtures' behavior.
- Guard against silent weakening: neither fix may delete the WI-120/WI-217
  assertions or skip the tests on Windows — the point is that both invariants
  (spawn resolution, capture) hold *under the hardened transport rule*.

## Interfaces

No cross-module seam — acts only within `tests/test_agent_loop.py` and
`tests/test_session_stdin.py` (intra-module, test layer). Nearest seam for
reference: the
`build_argv`/`run_session` prompt-transport contract in
`project-trajectory/scripts/agent_session.py` (LLR-026, SR-026), unchanged.
