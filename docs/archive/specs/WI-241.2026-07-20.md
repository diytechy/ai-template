## Why

The embedded `REVIEWER_PROMPT` ([agent_loop.py:362-393](../../../project-trajectory/scripts/agent_loop.py#L362-L393))
already carries the load-bearing bones — independence, redaction of the
implementer's self-assessment, run-the-harness-yourself, the verdict machine
line. But the 2026-07-18/19 batch is a dataset: 7 of 11 builds shipped
defects that review caught, and nearly every catch traced to three behaviors
the hand-written review briefs contained and the embedded prompt lacks:

1. **Drive the real shipped code paths** — the WI-230 reviewer missed a live
   data-loss bug by probing git primitives instead of the shipped function;
   once briefs carried the lesson, reviewers *reproduced* defects instead of
   assessing plausibility.
2. **Severity-ordered failure-class targeting** — name the worst ways THIS
   change could fail (silent wrong content, fail-open, …) and hunt those
   first; caught the WI-231 marker-straddle and CSV-newline silent-content
   defects.
3. **Verdict discipline** — "an APPROVE must mean you tried to break it and
   failed"; map each Done-when item to its covering test or UNCOVERED; and
   confirm new tests fail on the pre-fix behavior (caught the
   "passes-its-tests, fails-its-requirement" class twice: WI-234's live
   WI-229 miss and WI-236's stride starvation).

The counter-constraint is real and binding (the model-specific prompting
guidance): additions must be behavioral constraints that materially change
output, never micro-steps or inflation. Three clauses, not an operating
manual.

## Scope

1. Amend `REVIEWER_PROMPT` with the three clauses in the prompt's existing
   voice — a few sentences total, byte-lean, no restructuring of the
   existing bones. The redaction, independence, and verdict-format text is
   untouched.
2. Add `docs/rubrics/code-review-adversarial.md`: the reusable brief
   structure for heavyweight reviews (subject framing, the method lesson,
   severity-ordered failure classes, the Done-when coverage map, re-verdict
   protocol) — kit product, so the practice outlives this conversation's
   lore. Keep it a one-page rubric in the style of the existing
   `docs/rubrics/*` files, and make it reachable (the orphan ratchet:
   check_docs must find a link path from a live surface — the rubric's
   natural anchors are the spec that files it and the review-policy /
   PROCESS_OPTIONS reviewer section; PROCESS_OPTIONS is byte-budgeted, so if
   a pointer belongs there it is ONE line, byte-guard reported).
3. Tests: the suite's existing prompt-content assertions (find them —
   grep tests for REVIEWER_PROMPT / prompt fragments) gain assertions that
   the three clauses are present (fragment match, not full-text brittleness)
   and that the redaction + verdict-format lines survived unchanged.

**Non-goals:** no per-model prompt variants (one neutral contract stands
until evidence says otherwise); no WORKER/CRITIQUE prompt changes; no
review-policy dial change (OI-7 owns cadence); no third-party skill
dependencies.

## Done-when

The three clauses are present in `REVIEWER_PROMPT` and asserted by tests;
the pre-existing redaction/verdict lines are byte-unchanged and asserted;
the rubric doc exists, matches the house rubric style, and is
link-reachable (doc-navigability green); PROCESS_OPTIONS byte delta (if
any) reported within budget; suite green.
