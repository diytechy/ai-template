# WI-126 — Per-WI routing hints: build-tier pin + plan-required flag (owner proposal)

> **ARCHIVED 2026-07-20 — WI-251 spec-lifecycle sweep.** Spec-of-record for **WI-126** (all `done`; deliverables in `docs/requirements/work-items.csv`, session records in `docs/log.md`). Absorb-verified before archiving: every durable decision has a live spine/architecture/process home (dispositions in the log, 2026-07-20 entry).

**Status: done — implemented 2026-07-13.** (1)+(2) adopted as recommended; the
plan-required flag was folded into `SpecRef` semantics, not mechanized as a
column. The owner asked
whether an explicit PLAN stage is sometimes unnecessary — if the spec is
documented sufficiently, don't spin up a separate planning session that re-pays
the same context reload — and proposed pinning each WI to a build tier at
creation plus a flag for whether additional planning is required.

## Facts first: the loop already avoids standing PLAN sessions

- **PLAN is bounce-only, not a stage.** The engine's default prompt: where
  `docs/plan.md` exists, a BUILD session that finds the plan exhausted/wrong
  sets `run-phase=PLAN` and stops; the PLAN session re-chunks and — budget
  allowing — **"continue[s] straight into the first block: the bounce governs
  who plans, not how much one session does."** Planning and building already
  share one session/context wherever possible.
- **This repo has never run a PLAN session** (zero PLAN rows in
  `iteration_index.md`; there is no `docs/plan.md` here). The de facto plan is
  the WI row + its `SpecRef` spec — BUILD sessions read it and plan inline in
  the same context. The owner's "if the spec is detailed enough, no separate
  planner" is the standing behavior, not a change.

## What genuinely doesn't exist: per-WI routing

Tier is per-**phase** (`AGENT_TIER_MAP` / `DEFAULT_PHASE_TIER`); the
coordinator routes a BUILD session without knowing which WI it will pick up.
So a docs-only WI and a spine-critical engine WI both ride the phase default
(medium since WI-121). The proposal's real substance:

1. **`BuildTier` column** (optional) on `work-items.csv`: `strong|medium|quick`,
   empty = phase default. The **starting** tier for that WI's build sessions —
   composes with tier-up-never-down (a contested review still re-raises; the
   pin can start a build *above* the phase default, never cap escalation).
2. **Coordinator WI-awareness**: to honor the pin, the coordinator must know
   the next WI. Cleanest fit is a declared **`docs/next-wi`** file in the
   existing declared-file idiom (`run-phase`, `run-state`) — the driver already
   updates status.md's Next action; one more line keeps the coordinator dumb
   and the driver authoritative. Absent file = today's phase-only routing
   (never-breaking).
3. **Plan-required flag**: recommend **folding into `SpecRef` semantics rather
   than a new column** — a WI whose `SpecRef` points at a filled spec *is*
   plan-ready; one that doesn't isn't. That signal already exists, is already
   what session-protocol tells the driver to read, and adding a parallel
   boolean would duplicate it (the anti-duplication rule). Only mechanize a
   flag if a downstream `docs/plan.md`-cadence repo proves to need the
   coordinator (not the driver) to make the PLAN/BUILD call.

## Recommendation

Adopt (1)+(2) as a small never-breaking feature when a ruling lands — the tier
pin is a real cost dial now that the phase default is medium (e.g. pin a
gate-closing slice like the current v2 closer to `strong`, let routine doc WIs
ride `quick`). Skip (3) as a column; keep SpecRef as the plan-readiness signal.
Columns parse via `csv.DictReader`, so extra columns are never-breaking for
every reader; the shipped `work-items.template.csv` would gain the documented
optional column (downstream additive, no migration).
