# WI-240 — Park/quarantine details must carry the failing step, not the first 200 chars

> **ARCHIVED 2026-07-20 — WI-251 spec-lifecycle sweep.** Spec-of-record for **WI-240** (all `done`; deliverables in `docs/requirements/work-items.csv`, session records in `docs/log.md`). Absorb-verified before archiving: every durable decision has a live spine/architecture/process home (dispositions in the log, 2026-07-20 entry).

**Branch:** dualplan-routing-fix · **Filed:** 2026-07-19 (third field bite of
the truncation) · **BuildTier:** quick · **SafetyClass:** ordinary.

## Why

Failure details journal as `detail[:200]` at every park/quarantine site. A
multi-step harness failure prints passing steps first, so the cap keeps the
FIRST step's banner and discards the actual failure: the WI-229 blocked-
disposition loop journaled `disposition commit failed: === derived-gate :
C:\...python.exe ...` for three runs while the real error —
`check_trajectory: blocked-ref WI-229: status=blocked but BlockRef is empty`
— was cut off. The same cap degraded the WI-219 park ("integration commit
failed: " — WI-233 fixed the empty half) and was flagged as a smell in the
WI-233 report. Diagnosis required replaying the transaction by hand each
time — the exact cost WI-233 was filed to eliminate.

## Scope

One shared helper (e.g. `_failure_tail(out, budget)`) used by every
`detail=...[:200]` site: prefer the LAST `FAIL`-marked step's block (the
harness banners are structured `=== <step> :` / `  FAIL  <step>`), else the
tail of the output, within a raised budget (~600 chars). Journal events keep
a bounded size; the full output already lands in the salvage/evidence paths
where they exist.

**Non-goals:** no unbounded details; no journal schema change.

## Done-when

Regressions prove: a multi-step hook failure journals the failing step's
name + message (the WI-229 field string drives the extractor); a single-line
failure passes through untouched; every existing `[:200]` site routes
through the helper (grep-census asserted). Suite green.
