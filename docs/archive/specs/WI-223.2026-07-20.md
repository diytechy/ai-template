## Why

Since WI-220, every registry-editing disposition runs `gen_trajectory.py`
(un-`--check`) via `_regenerate_disposition_artifacts`, and that generator
exits 1 on any work-items validation error — dangling predecessor, unknown
SR ref, cycle. A dual-plan SELECT files fresh child rows; if those rows trip
the validator, regen fails and the error path discards the *entire completed
round* (salvage keeps the DP-* artifacts, but the disposition converts to
`error` and the WI quarantines). Before WI-220 the round would have committed
and the inconsistency surfaced at the next gate run. Failing closed is
defensible for `integrate_train` (a broken registry must not integrate); for
the dual-plan path it newly couples an expensive round's survival to
validator strictness — a design decision nobody has ratified.

## Scope

Decide and implement one of:

1. **Ratify fail-closed** (status quo): document in the LLR-064 Detail +
   the dual-plan section of `PROCESS_OPTIONS.md` that a validation-failing
   SELECT quarantines, and add a regression pinning the behavior (round
   artifacts salvaged, error surfaced with the validator tail).
2. **Soften for dual-plan only:** on regen failure in
   `dual_plan_disposition`, still commit the round evidence (artifacts are
   honest even when views are stale) and page/flag instead of hard-resetting —
   the freshness hook exposure that motivated WI-220 #6 returns only if the
   *downstream* repo runs the hook in the staging worktree, so the trade-off
   must be argued explicitly.

Either way the chosen semantics get a test and one documentation home.

## Ruling — fail closed (2026-07-18)

Option 1 is ratified. A SELECT's filed rows and the generated views consumed by
the shipped freshness hook are one atomic disposition: if trajectory
validation rejects those rows, the integration ref must not advance. The
dispatcher returns `error` with the failing generator and validator tail,
resets the staging transaction, and salvages the `DP-*` round evidence under
`out/dispatch/salvage/<train>/` for diagnosis/recovery.

Softening only this call site would be misleading. In a downstream repo with
the kit hook enabled, the subsequent commit would still be rejected for stale
or invalid generated views; bypassing that hook would instead make a known
invalid registry authoritative. Fail-closed therefore gives the same outcome
with or without the hook, while WI-220/WI-222 salvage preserves the expensive
round artifacts rather than pretending the invalid decomposition landed.

**Non-goals:** no validator strictness changes in `gen_trajectory.py`; no
regen changes in the other two disposition paths.
