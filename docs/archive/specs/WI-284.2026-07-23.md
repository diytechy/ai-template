# WI-284 — stop the forward-only cascade: scrub done WIs from status.md at integrate

**WI:** WI-284 · **Status:** queued · **Priority 1** (actively degrades every
grind — see below) · **Delivers:** the integrator close transaction +
forward-only enforcement tier (no spine SR — harness layer)

## Problem

`docs/status.md` is **forward-only**: it must not name a `done` WI (their record
belongs in `log.md`), enforced by `check_trajectory.status_forward_only_findings`
via `tests/test_trajectory.py::test_forward_only_unit_over_the_real_meta_repo`,
which is in the **smoke tier** — i.e. the per-commit *and* per-train DONE bar.

The cascade (observed live, run `20260723T0202`): when a train integrates and
`integrate_train` flips its WI to `done`, it calls `generate_status`, which only
rewrites the `<!-- BEGIN GENERATED STATUS -->` marker block — the hand-authored
forward-only prose (the "Next action" list) is deliberately **not** regenerated
(confirmed: `agent_dispatch.generate_status` touches only the marker; the intent
below it is hand-authored). So the just-`done` id keeps living in the prose, the
forward-only test goes red, and — because every in-flight train bases off the
integration ref — **every subsequent train inherits that red in its DONE gate.**
This inherited-red is exactly what burned WI-276's 12-iteration budget (it
carried WI-275's lingering id) and it will recur on this relaunch as WI-281/283/…
integrate unless fixed. Today it clears only when a human prunes the prose — a
manual step autonomous sessions can't take (a worker won't edit status.md outside
its scope).

## Approach (pick one; a is preferred)

- **(a) Automate the discipline — scrub at integrate.** In `integrate_train`'s
  done-flip transaction, remove the newly-`done` WI id(s) from the hand-authored
  status.md prose before the disposition commit (a targeted token removal, or a
  regenerate of a delimited "next action" region). This makes status.md
  forward-only *by construction* at the moment of close, matching the memory-noted
  rule "closed-WI ids leave status.md at close." Guard: only scrub ids that are
  now `done`; never touch queued/deferred ids.
- **(b) Decouple the check tier (bleeding-stopper, small).** Move the
  forward-only assertion off the smoke/DONE bar onto the gate/`--strict` tier
  (`check_trajectory --strict` already computes it), so a transient lingering id
  is a *close-time* finding, not a blocker on unrelated trains. Keep the test but
  mark it non-smoke, or assert it only at G3. This stops the cascade immediately
  even without (a); the two compose well (a keeps hygiene, b removes the coupling).
- Regression: a fixture where integrating WI-N leaves status.md naming WI-N must
  NOT red a second train's DONE gate (proves the cascade is broken).

## Interfaces

No cross-module seam — intra-module (`agent_dispatch.integrate_train` /
`generate_status`, `check_trajectory.status_forward_only_findings`, and their
tests).

## Done-when

- [ ] Integrating a WI leaves status.md forward-only-clean (no manual prune), OR
      the forward-only check no longer reddens a per-train DONE gate — the
      cascade fixture proves it.
- [ ] The forward-only intent is still enforced somewhere (gate tier at minimum);
      not silently dropped.
- [ ] Commit bar green; row `done`, spec archived.
