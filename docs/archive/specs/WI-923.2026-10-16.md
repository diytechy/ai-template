## The defect

Drafted on 2026-10-15 for the attended coordinator (2026-10-15c), from a
defect seen in the smoke tier, and filed by it on trunk the same day
(coordinator-2026-10-15 D-004), before its scope critique.

**What failed.** On Windows 11 with Python 3.11.9, in the smoke tier at
`-n auto`, TC-329's
`test_two_concurrent_first_calls_mint_one_session_and_run_one_unretained`
failed once with `len(kept) == 1`. One of its two racing threads died
(`PytestUnhandledThreadExceptionWarning`). The traceback ran `keep_for` →
`store_lock` → `dir_lock` → `_try_lock` → `os.open(path, O_CREAT | O_EXCL |
O_WRONLY)`, which raised `PermissionError: [Errno 13]` on
`<store>/out/adjudicator/.lock`. The test passed 3 of 3 runs alone.

**The cause in the code** (`project-trajectory/scripts/session_keep.py` at
trunk `e474f51dd`):

- `_try_lock` (lines 312–325) makes the exclusive create at line 315 and
  reads only `FileExistsError` (line 316) as the lock held.
- `dir_lock`'s loop (lines 299–302) retries only a `False` return. Any other
  refusal of the create escapes `dir_lock`, `store_lock` (line 286) and every
  caller.
- `keep_for` catches only `StoreBusy` (line 1261), so the call crashes. That
  is the observed failure.

**The cause on the platform.** Windows refuses an exclusive create with
access denied (`EACCES`), not "exists", while the name's delete is still in
progress. Three probes, run in a scratch directory on the box that failed,
place the window:

- With another handle left open on the lock, the holder's delete still
  removes the name at once, and the next exclusive create succeeds. A handle
  held open is not the cause on this box.
- Contenders racing a holder that creates and deletes the lock in a loop met
  `EACCES` 1,156 times in 10 s, beside 15,136 "exists". The real `dir_lock`,
  taken and released by six threads for 10 s, let 106 `PermissionError`s
  escape, out of about 9,600 holds.
- When the holder moved the name away by rename before deleting it,
  contenders met no `EACCES`. The window is the delete of the lock's own name
  while that call runs.

Two calls delete the lock's name: the holder's release (`dir_lock`, line 307)
and the stale takeover (`_try_lock`, line 319).

**Blast radius.** The primitive serves two stores: the adjudicator store
(`store_lock`) and the coordinator lease (`coordinator_guard.py`, twelve
`dir_lock` sites). This repository runs adjudicator retention
(`[adjudicator] context_reset_pct = 55`) and arms the coordinator guard
(`[coordinator] context_guard_pct = 50`). A lost race:

- crashes a retained call's keep (`keep_for`; observed);
- escapes a finished call's bookkeeping, release and abandonment
  (`_apply_now` catches only `StoreBusy`, line 864). IF-248 says none of
  them raises `StoreBusy` and only a failed publication raises `OSError`;
  here the marker was published and the error is the lock's;
- escapes `take_warm_lease` (line 1743) into the dispatcher's keep-warm
  tick, which `dispatch._keep_warm` does not catch (keep-warm is off here);
- drops a coordinator-guard hook's work at once (`_hook_main` prints any
  exception and returns 0), where one retry would have taken the lock, and
  ends a guard CLI call with a traceback;
- turns the per-commit smoke bar red at random on Windows.

On POSIX a name leaves at once when it is deleted, so `EACCES` from the
create there means a permission fault, which does not clear.
