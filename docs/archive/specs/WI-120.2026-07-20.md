## Observation

Every review round of the 2026-07-12 run first routed REVIEW-A to
`OPENAI-TERRA` (the router correctly prefers a different family from the
`claude-fable-5` implementer) and the spawn failed instantly:

```
coordinator: session error: [WinError 2] The system cannot find the file specified
```

The loop degraded legally — cooled the row and re-routed to `ANTHROPIC-OPUS` —
so each failure cost only ~10 s. The real damage is **silent diversity loss**:
the cross-family review leg never actually runs, every "independent" review is
same-family (the documented degraded-legal mode has become the permanent mode),
plus one `ERROR` row per round in the index.

## Root cause (reproduced on the box, 2026-07-12)

- `opencode` is an npm-installed CLI: `%APPDATA%\npm\opencode` (sh),
  `opencode.cmd`, `opencode.ps1` — **no `opencode.exe` exists**.
- Preflight passes: `shutil.which("opencode")` honors `PATHEXT` and resolves
  `...\npm\opencode.CMD`, so the boot-time missing-CLI check is satisfied.
- Spawn fails: `run_session` calls `subprocess.run(argv)` with
  `argv[0] = "opencode"` (no `shell=True`), which hits `CreateProcess` — and
  CreateProcess resolves **only `.exe`/`.com`** against `PATH`, never
  `PATHEXT` script shims. `WinError 2`.

Reproduced in isolation (same Python, same box):
`subprocess.run(["opencode", "--version"])` → `[WinError 2]`;
`subprocess.run([shutil.which("opencode"), "--version"])` → exit 0,
`1.17.18`. So the preflight and the spawn use two different resolution rules;
any POSIX-shaped `CmdTemplate` whose Windows install is a `.cmd`/`.ps1` shim
passes preflight and then fails at every launch. The ANTHROPIC rows are immune
only because `claude.exe` is a real executable. **Unexplained residue:** the
WI-112 live-verify (status.md) records terra replying *through
`run_session`* earlier the same day — that sitting's exact argv should be
re-checked when this WI lands (the reproduction above is unambiguous about
what the coordinator itself spawns).

## Fix (landed)

`run_session` resolves `argv[0]` through `shutil.which` (against the session
env's `PATH` when a registry row declares one) **on Windows only** and hands
CreateProcess the resolved absolute path — CreateProcess runs an explicit
`...\x.cmd` fine (cmd.exe interposition is automatic for `.cmd`/`.bat`):

- `which` miss → `argv[0]` untouched (the existing OSError sentinel path and
  preflight message still own that failure).
- A `.ps1`-only resolution has no CreateProcess interposition → also left to
  the OSError path; no `powershell -File` hardcoding for one provider.
- POSIX spawn is byte-identical (the `os.name == "nt"` gate; execvp already
  resolves shims there).

Rejected: `shell=True` (quoting/injection surface on a template that carries a
whole prompt as one argument).
