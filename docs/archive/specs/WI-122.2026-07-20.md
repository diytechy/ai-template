## Selection principle (the design that shipped)

Tiering is **opt-out**, not opt-in: `tests/conftest.py`'s
`pytest_collection_modifyitems` marks **every** collected test `smoke` *unless*
its module is in `SLOW_MODULES`, in which case it is `slow`. `smoke` and `slow`
**partition** the suite (verified: 531 + 153 = 684, none in neither or both) —
so a **new test is in the commit bar by default**, and a test leaves the bar
only by an explicit `SLOW_MODULES` entry. This is what defends "never a false
green": forgetting to tier a test keeps it in the bar (slower), never drops it.

`SLOW_MODULES` = the nine heavy end-to-end modules (full pre-commit/pre-push
hook runs, full scaffold bootstraps, dev-setup, profile byte-compares, the
perf/design-flow gate-step scaffolds). They are per-commit **redundant**: the
commit hook re-exercises the hooks live every commit, and the close/CI gate
re-runs the whole suite. Everything else — the single-tool contract tests
(trace, registry integrity, check_docs, derive_gate, gen_trajectory, agent_loop
core, …) — stays in smoke.

Measured: smoke **~47 s / 531 cases** vs full **~66 s / 684**. The speedup is
modest (~30%) because the suite is subprocess-bound and already xdist-parallel;
the wall floor is spawn overhead + the heaviest remaining contract tests, not
raw test count. `check.py --tier smoke` is now meaningful for the meta too
(previously selected nothing) — the dogfood gap in "Facts" below is closed.

## Facts (as of filing)

- The **mechanism already exists**: `docs/stack.ini` declares
  `[tiers] smoke = -m smoke`, and `check.py --tier smoke` runs the subset and
  skips the coverage floor (tested in `test_check_harness.py`). The WI-071
  phase-cadence ruling already **rejected test-impact selection in favor of the
  declared smoke tier** — this WI is that ruling's meta-repo adoption.
- What's missing is **population + adoption**: the meta suite has **zero
  `@pytest.mark.smoke` marks** (the tier selects nothing here), and the
  commit bar (session-protocol skill + CLAUDE.md + the launcher prompt) names
  the full `[product] test` command — `pytest -q -n auto`, 679 tests, ~70 s
  after WI-075's ~6× xdist speedup.
- CI runs the full suite (3 OSes) on every push regardless; `docs/push-policy`
  is `human`, so pushes — and therefore CI — can lag many local commits.

## Proposal

1. Mark a smoke subset: the fast per-script unit tests plus every
   registry/harness-contract test (trace/check/derive_gate/agent_loop core) —
   the subset must still defend the "never a false green" claim for the
   artifacts a commit touches most.
2. Re-point the **commit bar** text (session-protocol skill + fan-out,
   CLAUDE.md, launcher prompts) at the smoke tier; the **full suite** runs at
   slice close or phase close (gate bar) and in CI.

## Honest counterweight (why this is queued, not done)

At ~70 s the full bar costs ~1 min per commit — a few minutes per session;
the dominant cost was the strong-tier BUILD sessions, addressed by WI-121.
The risk side is real: with `push-policy human`, a regression in an unmarked
test can ride **many** local commits before the next full run. Recommend
adopting only if per-commit time still bites after WI-121 is observed live,
and sizing the smoke set generously (contract tests in, only slow
subprocess-integration tests out).

## Follow-ups (not this WI)

- The nine `SLOW_MODULES` are a performance list, not a correctness one — if a
  cheap test is ever added to one of those modules it silently leaves the commit
  bar. Acceptable today (they are uniformly heavy); revisit if a module goes
  mixed.
- Whether the **kit template** should ship this opt-out convention (vs the
  current opt-in `smoke` tier it ships) is a separate call — this WI is the
  meta-repo adoption only; the shipped `PROCESS_OPTIONS.md` "Effort ruling"
  already sanctions `pytest -m smoke` per commit generically.
