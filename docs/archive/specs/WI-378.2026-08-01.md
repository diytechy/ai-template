# WI-378 — the ratification / verdict-freshness loop

**ARCHIVED 2026-08-01 at the close of WI-378.** Outcome: documentation only, as
the row's own reframing predicted — the freshness gate was left unweakened and
option (b) below stays set aside, on a driven census recorded in the WI's
`Deliverable` (`docs/work/complete/WI-378-ratify-verdict-freshness-loop.md`) and
in `docs/log.md`. One correction to the record below: firing #1's refusal was
caused by the **close ceremony alone** (`99a0596`, `docs/work/` only), not by the
ratifying flip — `8311c75` carried the verdict file in the same commit, so it
could not stale itself.

**WI:** WI-378 · **Status:** done · **Delivers:** process text (no SR change expected)

## Problem

Under `docs/gate-policy: autonomous`, an independent reviewer's **recorded
verdict is what ratifies** a re-attest window (`Modified` → `Verified`). But
performing that ratification is a commit on a path the freshness rule does not
exclude — so the act the verdict authorized **immediately stales the verdict
that authorized it**, and the merge queue refuses.

The rule is `integrate.py::_verdict_gate`: the verdict's last commit must be no
older than the branch's last non-review, non-fragment commit. Only
`docs/reviews/` and `docs/log.d/` are excluded.

The result is a loop with no exit inside one round: every autonomously-ratified
WI owes an **extra review round whose only job is to bless the bookkeeping the
previous round authorized** — and a successor who does not know this reads the
refusal as a defect in their own work.

### Driven evidence — it fired twice on WI-280, and the second is the worse case

| # | What happened | Why it matters |
|---|---|---|
| **1** | Rounds 1–2 granted ratification. The flip + `docs/gate` regen landed as `8311c75`, the close ceremony (spec → `archive/`, `SpecRef` cleared per R-F) as `99a0596`. Queue refused: *"`docs/reviews/WI-280-REVIEW-A.md` predates the branch's last code commit"*. | Arguably fair — these were real spine commits. Cost: a round-3 verdict. |
| **2** | Trunk moved (an unrelated WI filing regenerated the dashboard). The branch merged trunk and resolved two **generated** artifacts by regeneration — `ad2541d` altered **no WI-280 content whatsoever** (all seventeen artifacts verified blob-identical) — and still staled the APPROVE. | Not substance at all. Cost: a **fourth** round to bless a regeneration. |

The reviewer's framing is the one to design against:

> Under `autonomous`, the number of verdict rounds a WI owes is bounded by
> **trunk's commit rate**, not by its own risk.

It also observed that any exclusion list arguably wants **regenerated artifacts**
in it, since re-reviewing a generated file is re-reviewing the generator.

## Approach

> **REFRAMED 2026-07-31 by owner direction — read this before the options
> table below, which it largely supersedes.** Two rulings change the problem
> rather than the remedy:
>
> 1. **Spine WIs run in series and alone** (`docs/concurrency-v2.md` §2). If a
>    spine WI is the only thing touching trunk, **firing #2 cannot happen** —
>    there is no concurrent branch for trunk to move under. Firing #1 survives
>    but is tractable with ordering alone.
> 2. **Traceability is not ratified content** (`concurrency-v2.md` §3). Under
>    this ruling WI-280's window **should never have opened**: its 19 LLR
>    `Module` cells were pointers following code, not a scope change. Most
>    re-attest windows this gate ever fires on are spurious.
>
> Together these mean the freshness gate is not the thing to weaken — the
> concurrency and the over-triggering that made it expensive are. **Option (b)
> drops out**, and (c) becomes unnecessary. What remains worth doing is (a),
> the ordering documentation, which was always free.
>
> This WI therefore **depends on** the concurrency-v2 outcome (chiefly the
> WI-380 detector split) and should not be built before it. The table below is
> kept as the record of what was considered and why it was set aside.

The three candidates as originally framed:

| | Option | What changes | Pros | Cons |
|---|---|---|---|---|
| **(a)** | **Document the required ordering** | Prose only: process-options.md's verdict protocol + the `session-protocol` skill state that the close ceremony and any ratification land **before** the final verdict round. | No gate weakened; zero code risk; captures the mitigation already learned. | Does not fix firing #2 (trunk movement is outside the WI's control); leaves a real trap that costs a round each time it springs. |
| **(b)** | **Widen the freshness exclusion** | Add the bookkeeping paths that cannot change product behavior — `docs/work/`, `docs/ratify/`, `docs/gate`, and per the reviewer, regenerated artifacts. | Fixes both firings; narrower than it sounds — these are the paths the **RULING-6 audit already treats as bookkeeping**. | Weakens a fail-closed gate. Needs an argued boundary for "generated", or the exclusion becomes a hole a real change can hide in. |
| **(c)** | **Forward-looking ratification** | The reviewer records a ratification the subsequent flip commit **cites**, rather than one the flip invalidates. | Keeps the gate fail-closed and unmodified. | Most machinery; a verdict that blesses a not-yet-existing commit is a weaker claim, and it needs its own anti-abuse rule. |

**Superseded by the reframing above.** (a) still lands — it was always free.
(b) is set aside: with spine work serialised and the detector corrected, the
gate stops being expensive, so there is no longer a case for weakening it.
(c) is unnecessary for the same reason. What was going to be a
"how much do we weaken the gate" decision became "stop making the gate fire
spuriously", which is strictly better.

## Interfaces

No cross-module seam — this changes process text, and (if (b) is chosen) one
predicate inside `integrate.py`. The gate's contract itself
(`IF-080`) would need its Contract cell re-worded only under option (b).

## Practical mitigations already learned (true under every option)

- Do the **close ceremony and any ratification BEFORE** the final verdict round.
- Do **not commit trunk-side regenerations while a branch is awaiting merge** —
  that is what caused firing #2.

## Notes / open questions

- Both firings are on one WI in one session, so the **frequency** is unmeasured.
  After WI-380 lands, the honest first step is to check whether this fires at
  all any more — it may close as documentation only.
- The gate is doing something real: a verdict written against a tree that later
  changed genuinely was not a verdict on what merges. The reframing does not
  dispute that; it removes the cases where the tree changed in ways no reviewer
  would have concluded differently about.
