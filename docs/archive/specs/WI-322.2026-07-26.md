## The shape (ruled, not open)

```text
docs/requirements/open-items.csv      the source registry (one row per OI)
docs/open-items.html                  generated, the ONLY reading surface
docs/open-items.md                    GONE — here and from the kit scaffold
```

Same registry→generated-view pattern as `work-items.csv` → `PROJECT_STATE.html`.
OI state becomes queryable data; the pending projection becomes derived rows in
the same view instead of a text block inside a markdown file.

## Registry schema (proposed — finalize at build)

`OI-ID, Title, Status(pending|ruled), Raised, OneLine, Decision, BlastRadius,
Options, Recommendation, WI-Refs, RuledDate, RulingRef`

- `OI-N` ids stay stable and never renumber (standing rule).
- A **ruled** row keeps its id but drops out of the rendered *pending* section;
  the ruling's substance still appends to [log.md](../../log.md)'s Decisions —
  the log remains the decision record, `RulingRef` points at it. (Whether ruled
  rows stay in the CSV as tombstones or are removed after the log entry lands is
  a build-time call; leaning **stay**, since stable-id + queryability is the
  point of a registry.)
- Multi-option prose goes in the `Options` cell with the ` · ` separator
  convention `work-items.csv` already uses for lists-in-cells.

## The generated view

One `docs/open-items.html`, generated + freshness-gated like its siblings, <!-- path-ok: the deliverable, not yet built -->
carrying **both** of what the markdown file carried:

1. **Pending decision briefs** — one card per `Status=pending` row: one-line,
   decision, blast radius, options, recommendation, linked WI rows.
2. **The pending-owner-actions projection** — the derived section
   (`gen_trajectory._spine_pending` + friends), including the `Modified`
   re-attest rows **with their word-level before/after** (the depth that started
   OI-10): unchanged text collapsible, additions/deletions marked, both themes,
   per-cell "how much moved", and the **baseline revision printed on every
   section** — an empty section must read as *check the baseline*, never as
   *nothing changed*.

Generator home: build-time call between `gen_trajectory.py --status` growing an
`--open-items` output and a small sibling emitter. Note `gen_trajectory.py` is
5,236 lines under a size ratchet with WI-280 pending — a sibling module that
reuses its theme tokens is the likely honest answer. **Not** part of the
dashboard render surface: `open-items.html` must not join the
`perceptual-stale` watch paths.

## Accepted trade-offs (recorded in the ruling, not to be relitigated)

Brief prose is authored into CSV cells and diffs one-line-per-row in review;
agents read briefs through the CSV row, as they already do WI deliverables. The
`work-items.csv` precedent says both are livable. What would reopen the
decision: only an owner ruling.

## Hazards

- **The baseline is the whole ballgame** for the re-attest depth: no `--since`
  empties a pre-regime section, a bad `--since` fabricates one — the view must
  print its baseline (see the 2026-07-26 stale-brief entry in the log).
- **Sequence after the current sitting closes.** The SR/LLR/TC amendments in
  the checklist flip rows `Modified`; landing them mid-window sprawls the
  sitting the owner is trying to hold.
