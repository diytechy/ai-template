# WI-108 — Flaky `test_hook_honors_kit_scripts_dir_override` under max parallel + coverage

**Status: deferred.** A recorded observation with a candidate fix, parked until it
recurs often enough to reproduce (and therefore verify a fix against). Filed
2026-07-12 during the derived-gate phase close (WI-089…096).

## Observation

`tests/test_pre_commit_hook.py::test_hook_honors_kit_scripts_dir_override` failed
**once** inside the full `check.py --gate G3` gate bar (the `tests+coverage` step =
`pytest -q -n auto --cov …`). It has **not** reproduced since:

- 4× in isolation (3× standalone, 1× under `--cov`) — pass.
- The gate re-ran clean immediately after — 665 passed.
- A targeted diagnostic — **6 more full-suite runs** (4× `-n auto`, 2×
  oversubscribed `-n 32` to amplify contention) — **0/6 failures**; the target
  test never appeared in a failure.

Net: **1 failure in 8 full-suite runs (~12%), and unforce-able even under
oversubscription.** Run times swung 143 s → 238 s across identical runs — evidence
of heavy, uneven OS scheduling/subprocess contention on the box.

## Why it is not a feature defect

The test is unusually subprocess-heavy: one xdist worker running it fans out to
the pre-commit hook → `check.py --run-steps` (7 steps **in parallel**) → 7 Python
subprocesses, plus the `make_minimal_project` fixture (bootstrap / gen_arch_map /
gen_okf / derive_gate). Under `-n auto` (24 workers here) + coverage instrumentation
the box briefly runs many dozens of Python processes; Windows process creation is
expensive and transiently failure-prone under that load. Every scaffold is its own
`tmp_path`, so there is no cross-test shared state, and the derived-gate feature's
own tests are deterministic. The derived-gate effort marginally **raised** this
test's load (the hook batch went 6→7 parallel steps; one extra `derive_gate` spawn
in the fixture), a plausible nudge over an already-borderline threshold — but not a
proven cause, and not reproducible.

## Candidate hardening (only if the rate proves material)

Do **not** apply blind: the flake is unreproducible, so any fix is currently
unverifiable. When it recurs enough to reproduce, prefer, in order:

1. **Group the subprocess-heavy hook tests** so xdist does not run them
   concurrently with the rest of the fan-out: `@pytest.mark.xdist_group("hooks")`
   on the hook-spawning tests + `--dist loadgroup` in the declared `stack.ini`
   test command. Removes the amplification without changing shipped behavior.
2. **Trim the hook test's internal fan-out** — have the test-time hook invoke
   `check.py --run-steps … --jobs 1` (serial inside the hook) so one worker does
   not spawn 7 more. Needs a test-only lever (an env var the hook/check.py honors)
   — do NOT change the shipped hook's production parallelism for a test.

Reject: a retry-on-nonzero in the test (masks real failures).

## Done-when

- [ ] The flake is reproduced with a captured traceback naming the failing step,

- [ ] If reproduced: the chosen hardening lands and the repro no longer fails
      across ≥ 20 gate runs.
