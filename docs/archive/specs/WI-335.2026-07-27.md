## The constraint, and why worker counts cannot meet it

The owner's requirement is about the **machine**, not about pytest. A worker
count cannot deliver it, because machine load is:

```
concurrent runs  ×  workers per run  ×  child processes per worker  +  non-pytest work
```

`ptc`, `setx PYTEST_XDIST_AUTO_NUM_WORKERS` and the root conftest's
`pytest_xdist_auto_num_workers` hook all set the **middle term only**. Measured
2026-07-27 on this 24-thread box:

| | |
|---|---|
| worker cap works | `-n auto` gives **12/12** workers with the hook, **24/24** without |
| …and is not enough | a **12-worker** run measured **mean 59% / max 74% CPU**, with **42 python + 4 git** processes live |
| why | the slow tier is subprocess-per-test by design (`SLOW_MODULES`; `test_trace.py` alone has ~70 subprocess sites) |
| and it is per-process | two concurrent runs are back to 24 workers — normal under parallel WI dispatch, where each train worktree runs its own suite |

## What was built

A **named Windows job object with a hard CPU rate cap**, applied from the root
conftest's `pytest_configure`, plus a `BelowNormal` priority drop.

- **Hard cap** bounds the whole process tree — controller, every xdist worker,
  every `git`/`python` subprocess a test spawns — regardless of how many there
  are. Proven with a deterministic burner: 24 spinners measured **100%** CPU
  uncapped, **37.5% mean / 47% max** under a 25% cap.
- **Named**, so every process of ONE RUN joins the *same* job — controller,
  xdist workers, and the subprocesses the slow tier spawns per test.

  > **CORRECTED 2026-07-27 (WI-338, [127-REVIEW-A](../../reviews/127-REVIEW-A.md)
  > BLOCKER 1).** This bullet originally continued: *"N concurrent runs total the
  > cap instead of multiplying it — the failure the per-process levers could not
  > address."* That is **false**, and it was the headline claim. Windows permits
  > assignment only into a job that is empty or already in the process's own
  > parent job chain — so whether a second run shares depends on whether
  > something has already jobbed it. An unjobbed run JOINS and shares; a run
  > inside a sandbox/container/CI job cannot, and falls back to a private job at
  > the same percent, warning. (The first correction said "a different process
  > tree", which is also wrong — [128-REVIEW-A](../../reviews/128-REVIEW-A.md).) Measured: with a first
  > tree holding the job, two independent probes reported `PRIVATE` while a
  > **child** of the first reported `SHARED`. The delivered property is a
  > **tree-wide** ceiling for one run — which does answer the original problem
  > (a worker count bounds workers, not processes), but not the parallel-worktree
  > case this bullet named.
- **Priority** is the other half: the ceiling says how much the tests may take,
  `BelowNormal` says they yield it the instant anything in the foreground wants
  it. That is what actually keeps a desktop smooth.
- **Default 50%**, dialled by `PYTEST_CPU_CAP` (`off`/`0`/`100` disables).
- **CI opts out** (`env: PYTEST_CPU_CAP: "off"` in `test.yml` + `canary.yml`):
  ephemeral runners have no desktop to protect, have far fewer cores, and
  `test.yml` carries a smoke-budget job that enforces a wall-clock number.
- **POSIX degrades honestly** to `os.nice(5)`. There is no cgroup-free hard cap
  there, and the file must not claim a guarantee it cannot keep.
- **Never fatal.** Any failure warns and runs normally; a resource nicety must
  not be able to red a suite.

Wall-clock cost measured as **negligible on this suite** — `tests/test_trace.py`
ran 20.4 s capped vs 20.7 s uncapped — because it is subprocess/IO-bound rather
than CPU-bound. A CPU-bound suite would pay roughly in proportion.

## Two traps this paid for

1. **`JOB_OBJECT_CPU_RATE_CONTROL_HARD_CAP` is `0x4`, not `0x2`.** `0x2` is
   `WEIGHT_BASED`, which takes a `Weight` of 1–9 and rejects a rate outright —
   `ERROR_INVALID_PARAMETER`, from code that reads perfectly.
2. **`QueryInformationJobObject(NULL, …)` is the wrong instrument.** It reports
   the *immediate* job, and an xdist worker sits in a nested job, so the first
   version of the guard reported `ControlFlags=0` and failed **while the cap was
   working**. `IsProcessInJob` against the named handle asks the real question:
   is THIS process inside THAT job. It holds for controller and workers alike.

Also: ctypes needs explicit `argtypes`/`restype` on x64, or a `HANDLE` is passed
as a 32-bit int and truncates.
