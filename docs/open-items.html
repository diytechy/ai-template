OI-97How is a system requirement classified when it delivers its need jointly with other requirements?

One line

decide the assumption tier's class for a requirement that is one of several jointly delivering its need - approved SR-193 knows only bridged, coincident ("alone delivers its needs") and unclassified; recommendation (a), a declared joint-delivery class that names its sibling requirements

What is being decided

C2 (WI-655) asked that every SR carry da_refs or coincident. Approved SR-193 defines coincident as a waiver stating "why its own specification alone delivers its needs", and da_refs as the assumptions a requirement's argument relies on. Spine-acts batch C's adjudicator and Codex Sol held the waivers to that text. Many requirements do not alone deliver their need: they supply one part of it (a prerequisite, a measurement, one link of a verified chain), and the need is delivered by several requirements together. Their argument relies on other requirements, not on a premise about the world, so a DA would misstate it and a coincident waiver would be false. Wave-5 ruling 47 left nine such rows unclassified, SR-193's honest third state, which is reported without failing: SR-015, SR-024, SR-033, SR-111, SR-129, SR-174 and SR-177, and the labelled derived SR-223 and SR-225. The tier has no class for them, so C2's aim that every SR be classified cannot be met honestly as the vocabulary stands.

Blast radius

(a) adds one cell and one class to the assumption tier: SR-193 and its design and test rows are amended, assumption_rules classifies it, and the bridging report counts it. Adopters with the tier armed see a new class and no new failure. (b) leaves the nine rows reported as unclassified for good; the tier's gate, once armed, must tolerate them. (c) spends DA rows on premises that are really other requirements, which the batch-C adjudication ruled a misstatement.

Options
  • (a) ADD A JOINT-DELIVERY CLASS: a requirement names the sibling requirements that, with it, deliver the need (for example a delivered_with cell of SR ids), classified "joint", and checked that the siblings cite the same need. FOR: states the real relationship, and the check can verify it. AGAINST: one more cell and class in a tier still warn-only.
  • (b) ACCEPT UNCLASSIFIED as the honest state for contributing requirements, and scope C2's aim to requirements that alone deliver or rely on a world premise. FOR: no schema change. AGAINST: the report never clears, and "unclassified" then means both "not yet judged" and "judged: joint".
  • (c) USE DAs: write a DA per contributing requirement stating that its sibling requirements deliver the rest. FOR: no schema change. AGAINST: a DA is a premise about the world at a crossing; a sibling requirement is not one, and the batch-C adjudication returned exactly this shape.
Recommendation

(a): it names the relationship the nine rows actually have, so the tier's report can clear honestly, and it keeps DAs for premises about the world.

SR-224A skill whose description cannot say when to use it fails the skills-index checkapproval owed

Requirement

If a skill's description is shorter than the declared description floor, then the kit's skills-index check shall fail, naming that skill.

Rationale

A DERIVED requirement, and labelled so. SN-005 asks that agents and humans work from the same playbook; it does not name what a skill's description must carry, so this obligation arrives through the first-run-adopter lens rather than through the need's text. An agent reads only a skill's description to decide whether to load it, so a description too short to say when to use the skill is shipped guidance an adopter's agent never reads: the skill works only for someone who already knows it exists, the undocumented-knowledge failure that lens listens for. A length floor is a lexical proxy, not a proof that a description is good: it catches the one-line stub that cannot state a trigger and leaves the wording to review. A reviewer's judgement of every description was the alternative, and it lost as the only guard because nothing would re-ask it when a skill is added. Fed back to the need: SN-005's acceptance could name the skills' descriptions as part of the playbook; until it does, this row is derived and says so.

A record carries a lease {holder, until}: keep_for takes it for the adjudication's wall deadline plus 300 s, waits up to lease_wait seconds while another call holds it, and past that runs the adjudication unretained, saying why; keep_bookkeep and keep_abandon release it. A lease that EXPIRED without being released means its holder is still running past it or crashed, so the session is never reused: keep_for (and take_warm_lease) retires it with reason lease expired unreleased and drops the stale lease (retire_stale_lease), and the launch mints fresh. Rationale
Retention is one more thing a call does, not a second launch path, so resume, occupancy, reset and keep-warm all go through act and record, and the rules and the store sit in their own module beside the service rather than in the roles. The layer ships off because turning it on is the owner's decision after it has been verified on the machine it runs on, and at the off dial the launch must be exactly today's. The lock and the lease exist because a lane's worker and the dispatcher both reach the one store and the one transcript: a torn record or two calls resuming one session at once corrupts the state every later judgement reads. The clear point reads the queue and the lanes rather than the item alone because a draining session that retires while a successor of its own verdict is still queued breaks the round trip the layer exists for. The keep-warm ping is off the dispatcher's thread so a slow ping cannot stall the merges, and its record is on it so its commit is serialised with them. The dedicated homes keep a retained transcript out of a person's own sessions; credentials are provisioned into them by a person.
