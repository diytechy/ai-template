OI-53A dozen Approved spine rows name symbols that no longer exist, and no one may amend them mid-flight

rule how the batch of stale Approved LLR cells surfaced by the back-link campaign gets repaired - LLR-175's CodeSymbol names LaneState.note_session where the live class is RoutingState, LLR-011's names no real symbol for its write half, and the campaign skipped a further group (LLR-143/089/050/157/142/057/104/108/068 and LLR-172-adjacent) for the same reason: the tag is honest, the ROW is stale, and an Approved cell is the sitting's to amend, not a worker's

What is being decided

SURFACED BY A CAMPAIGN THAT WAS NOT LOOKING FOR IT. The back-link campaign wrote literal Implements: declarations onto 83 of 165 live LLR rows; the 2026-08-21 closing review then cross-checked every tag's ENCLOSING SYMBOL against its row's CodeSymbol and Module and read the rows behind all 14 mismatches. In every case the tag sits on a symbol that genuinely realises the row and the ROW is what has aged - a rename (LaneState -> RoutingState), a split, or a cell naming a function-local rather than a module-scope binding. Two were never banked at all (LLR-175, LLR-011); the rest were skipped by the campaign with the reason recorded.

WHY IT IS RULED RATHER THAN FIXED: the rows are Approved, and amending an Approved cell overrides an attestation the sitting made - the SR-006/LLR-060 precedent, held again twice in this program. CodeSymbol is a TRACED cell, so a correction does not arm the approved-snapshot drift detector; it is the ATTESTATION, not the machinery, that says a worker must not do it silently in the middle of unrelated work. The question is which repair instrument this batch gets: a sitting that amends them together, or a tracked repair row of the WI-482 class that does it under review.

Blast radius

Bounded and known: about a dozen CodeSymbol cells on Approved LLR rows, no requirement TEXT, no Status, no owner. Nothing mechanized fires on any of them today - check_trajectory's symbol resolution is warn-first, and the back-link coverage figure (83/165) is computed from the DECLARATIONS in source, not from these cells, so the campaign's number is unaffected either way. The cost of leaving them is the one this repo keeps paying: a registry cell naming a symbol nobody can find teaches its reader to stop trusting the column, and the next author to grep LaneState finds a requirement instead of a class.

Options
  • (a) A BATCH AMENDMENT SITTING - the owner reads the dozen together and re-blesses them in one Status-change commit. FOR: one act, one review, the attestation stays intact and visible; the rows are all one KIND of defect, which is what a batch is for. AGAINST: it needs the owner's time on a set of cells that gate nothing today.
  • (b) A TRACKED REPAIR ROW (the WI-482 class) - a WI that corrects the cells under the ordinary review round. FOR: it moves without a sitting, and the review round is a real check. AGAINST: it has a worker amending Approved cells, the precedent this repo has twice declined to set; if that is acceptable here it should be RULED so, not assumed by filing.
  • (c) LEAVE THEM AND RECORD - the tags are honest, the rows are stale, and the discrepancy is now written down in the review round and this row. FOR: zero cost; nothing is enforced on them. AGAINST: the record ages into folklore, and the next campaign re-discovers the same dozen and re-banks them, which has already happened once.
  • (d) MECHANIZE FIRST - promote the tag-vs-CodeSymbol cross-check the review ran by hand into check_trajectory (warn-first), so the population is measured continuously rather than by campaign. FOR: it answers "are there more?", which nobody can currently answer, and makes the burn-down visible. AGAINST: a new check on a warn-first surface that already carries several, and it repairs nothing on its own.
Recommendation

(a) FOR THE DOZEN, with (d) as its own small row afterwards. The batch is one kind of defect found by one pass, and a sitting that re-blesses them together costs less owner attention than a repair row's review round would - while keeping the rule this repo has already declined to bend twice. (d) is worth filing separately because the honest answer to "is that all of them?" today is "that is what one reviewer found by reading 165 rows", and the next campaign should inherit a measurement rather than a memory. (b) is a legitimate answer if the owner judges CodeSymbol too mechanical a cell to be worth a sitting - it is a traced cell, and the drift detector agrees - but that is precisely the judgment being asked for.

SR-180A design row is discharged only by a realization symbol that resolvesapproval owed

SR-IDSR-180
TitleA design row is discharged only by a realization symbol that resolves
SN-RefsSN-002;SN-003
Boundary-RefsB-05
RequirementIf none of the realization symbols a design-tier row names resolves within any implementation unit that same row names, then the delivered harness shall report that row as undischarged.
RationaleRealizes SN-002 — the chain from need to test is trustworthy because it is mechanically verified rather than manually asserted, and the bottom rung of that chain is the claim a design row makes that the code it names exists. Without this row the spine states a terminating condition for every tier except the one that decides when decomposition is finished: a reader learns from the registries when a need is answered, when a requirement is decomposed and when a test verifies it, and cannot learn from them when a design row is done. The condition that settles it is built and gates, so what the spine lacks is the statement, not the mechanism, and an adopter inherits the gate without inheriting any statement of what it demands. Realizes SN-003 in the row's altitude, which is the load-bearing half of the wording rather than a stylistic preference. The obligation names no language: a realization symbol, an implementation unit, and a rule that decides whether the one resolves in the other are terms every stack carries, and the resolution rule is read from the declared stack profile exactly as the harness commands are. A row naming one language's file extension would ship one stack's requirement to every adopter — and it would buy nothing, because the association is answerable off the shelf in any stack by a multi-language tag index that asks only whether a name exists in a unit. What has to hold is the association; the form it is recorded in is no part of the obligation, which is what lets the row sit at this altitude honestly. Two alternatives lost. Per-token exactness — every named token must resolve — asks a harsher question than discharge, and on real registries it reds rows for tokens that were never symbol claims: a local, an attribute, a prose fragment. The anchor validates the coarse claim (the code is real, at a unit that is real, under a name that is really there) and counts the fine misses, so tightening the cell's grammar stays available instead of being hidden behind a green. Folding the obligation into the documentation-drift row also lost: a design row is a specification, not a documentation surface, and an unresolved realization symbol is a completeness verdict rather than drift, so the fold would put two decisions in one row. Stated so it cannot be read in: nothing here obliges source code to carry a back-link naming the requirement it implements. That is the opposite direction, it rests on weaker evidence than this one, and it is a separate question this row neither states nor implies.
AcceptanceCriteriaA design-tier row naming a realization symbol that resolves in one of the implementation units the same row names is discharged; a row whose named symbols all fail to resolve is reported and gates at the declared release bar; a named symbol that fails to resolve beside a sibling on the same row that resolves is counted and never gates, so tightening the cell stays possible without reopening the gate. The unit cell is read as a union, never as a positional pairing with the symbol cell: a row naming several units is discharged by one symbol resolving in any one of them. A row naming only units the declared stack profile carries no resolution rule for is reported as skipped-with-reason and is not counted as discharged, so a row the harness cannot judge never reads as a pass; an example placeholder row is out of scope, so a freshly generated scaffold is silent here. The resolution rule is read off the declared stack profile rather than restated in this row; for the current profile it is a name bound at module scope, or defined at class scope, in a source module of that profile's language.
