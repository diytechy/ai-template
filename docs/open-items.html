OI-48Which component owns the shared kernel? The consolidated package is imported from all four, and the locked depth-0 frame has no answer

WI-448 consolidated the kit's duplicated helpers into one shipped package (scripts/kitlib/), and the package is imported by modules in EVERY one of CMP-006..009 - so no single Component tag is true; the row landed tagged with all four, which is honest about the usage and which the checker's own multi-membership rule treats as WARN-ONLY ("reports a question about the PARTITION, and no partition has been ruled yet, so it must not block"), but a four-way tag also SUPPRESSES the cross-component seam rule on every one of the package's edges, so the ruling is owed before the consolidation program adds more importers

Blast radius

SMALL TODAY, GROWING WITH THE PROGRAM - and that is the reason to rule it now rather than at the program's end.

  • Today: ONE LLR row (LLR-181) carries the four-way tag, and 11 shipped modules import the package. The only live cost is the suppressed seam rule on those edges plus four warn-only "connectivity undeclared" lines, the same tolerated family spec_move, lane, handback, traj_graph, traj_render and check_vocab already sit in.
  • With the program: the remaining consolidation slices (33 more _utf8_console copies, the derive_gate/trace spine-policy pair, the is_example triple) add importers from the same four components, so whatever is ruled here is applied N times if it is ruled late and once if it is ruled now.
  • What does NOT move under any option: the package's CONTENT. This is a question about which architectural unit owns a shared kernel, not about whether the kernel should exist - D-8 ruled that, and the duplication it removed is measured.
Options
  • (a) FOUR-WAY TAG, AS LANDED - the package is declared a member of every component that imports it. FOR: it is TRUE, it needs no new component against a locked frame, and the checker's designed response is exactly the warn-only partition advisory. AGAINST: it silences the cross-component seam rule on the package's edges, so a genuinely wrong import into kitlib would not be reported; and "owned by four" is the shape the one-home-per-behaviour constraint exists to refuse, even though here it describes callers rather than behaviour homes.
  • (b) ONE OWNING COMPONENT + DECLARED IF SEAMS - tag kitlib into one CMP (CMP-006 is the closest fit by content: the registry reader is its bulk) and declare an IF-### row for each cross-component import edge. FOR: keeps the seam rule live on every edge, which is what the rule is for; makes the shared kernel's consumers explicit. AGAINST: the edges are the WHOLE POINT of a shared helper package, so this declares ~11 seams that all say the same thing, and each new consolidation slice adds more - the seam registry starts describing library usage rather than architecture.
  • (c) A SHARED-KERNEL COMPONENT (CMP-010) - mint a fifth component whose job is exactly this, and let the seam rule police edges INTO it normally. FOR: it is what the partition actually lacks, and it is the standard answer (a kernel/common layer every unit may depend on). AGAINST: THE DEPTH-0 FRAME IS LOCKED AND OWNER-APPROVED at 4 entities - this is not a call an execution WI may make; and a kernel component invites exactly the junk-drawer growth the themed-module shape constraint was adopted to prevent.
  • (d) EXEMPT A DECLARED KERNEL FROM THE SEAM RULE - keep one owning component, and teach cross_component_findings that edges INTO a declared shared-kernel module are not seams. FOR: no frame change, no seam inflation, and the rule stays live for every OTHER edge. AGAINST: new shipped policy plus a new declared surface, for a question one tag currently answers warn-only.
Recommendation

RECOMMENDED: rule between (c) and (d), with (a) standing as the honest interim it already is.

The reconciling fact: (a) is not wrong about USAGE - the package really is used by all four - it is just silent about OWNERSHIP, and silence is what the multi-membership advisory was built to report rather than to settle. So nothing is broken today; what is owed is a decision before the program multiplies the instances.

(b) is the option to price carefully and probably decline: the seams it would declare are library calls, and a seam registry that lists every consumer of a shared helper stops distinguishing architecture from usage - the same over-tracing the kit's proportionality doctrine (SN-012) refuses elsewhere.

(c) is the textbook answer and the one the partition's own purpose points at - the owner's stated objective for the architecture is ONE HOME PER BEHAVIOUR, and a shared kernel is precisely a set of behaviours whose home is nowhere in a four-way functional cut. But the frame is LOCKED and APPROVED, so this is the owner's call and no one else's; if it is taken, the ids of the cut rows are spent and watermark-held, so CMP-010 is a real mint.

(d) is (c)'s answer without the frame change, and it is cheap if the kernel is DECLARED rather than inferred - one cell, not a heuristic. It is the better option if the owner wants the four-entity frame to stay literally four.

WHAT THIS ROW IS NOT: it is not a request to revisit D-8. The consolidation is ruled, executed and measured; only the architectural HOME of the result is open.

SR-IDSR-180
TitleA design row is discharged only by a realization symbol that resolves
SN-RefsSN-002;SN-003
Boundary-RefsB-05
RequirementIf none of the realization symbols a design-tier row names resolves within any implementation unit that same row names, then the delivered harness shall report that row as undischarged.
RationaleRealizes SN-002 — the chain from need to test is trustworthy because it is mechanically verified rather than manually asserted, and the bottom rung of that chain is the claim a design row makes that the code it names exists. Without this row the spine states a terminating condition for every tier except the one that decides when decomposition is finished: a reader learns from the registries when a need is answered, when a requirement is decomposed and when a test verifies it, and cannot learn from them when a design row is done. The condition that settles it is built and gates, so what the spine lacks is the statement, not the mechanism, and an adopter inherits the gate without inheriting any statement of what it demands. Realizes SN-003 in the row's altitude, which is the load-bearing half of the wording rather than a stylistic preference. The obligation names no language: a realization symbol, an implementation unit, and a rule that decides whether the one resolves in the other are terms every stack carries, and the resolution rule is read from the declared stack profile exactly as the harness commands are. A row naming one language's file extension would ship one stack's requirement to every adopter — and it would buy nothing, because the association is answerable off the shelf in any stack by a multi-language tag index that asks only whether a name exists in a unit. What has to hold is the association; the form it is recorded in is no part of the obligation, which is what lets the row sit at this altitude honestly. Two alternatives lost. Per-token exactness — every named token must resolve — asks a harsher question than discharge, and on real registries it reds rows for tokens that were never symbol claims: a local, an attribute, a prose fragment. The anchor validates the coarse claim (the code is real, at a unit that is real, under a name that is really there) and counts the fine misses, so tightening the cell's grammar stays available instead of being hidden behind a green. Folding the obligation into the documentation-drift row also lost: a design row is a specification, not a documentation surface, and an unresolved realization symbol is a completeness verdict rather than drift, so the fold would put two decisions in one row. Stated so it cannot be read in: nothing here obliges source code to carry a back-link naming the requirement it implements. That is the opposite direction, it rests on weaker evidence than this one, and it is a separate question this row neither states nor implies.
AcceptanceCriteriaA design-tier row naming a realization symbol that resolves in one of the implementation units the same row names is discharged; a row whose named symbols all fail to resolve is reported and gates at the declared release bar; a named symbol that fails to resolve beside a sibling on the same row that resolves is counted and never gates, so tightening the cell stays possible without reopening the gate. The unit cell is read as a union, never as a positional pairing with the symbol cell: a row naming several units is discharged by one symbol resolving in any one of them. A row naming only units the declared stack profile carries no resolution rule for is reported as skipped-with-reason and is not counted as discharged, so a row the harness cannot judge never reads as a pass; an example placeholder row is out of scope, so a freshly generated scaffold is silent here. The resolution rule is read off the declared stack profile rather than restated in this row; for the current profile it is a name bound at module scope, or defined at class scope, in a source module of that profile's language.
