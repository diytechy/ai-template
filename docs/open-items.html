OI-64The finding/severity/exit contract is restated in eleven-to-thirteen requirement rows and stated by none - does it become a requirement, or is the restatement accepted

One line

WI-508's blind architectural remap ran on two independent axes and both returned a module owning ZERO requirements, for the same subject: the shape of a finding, its severity class, strict-mode escalation, vacuity when an optional input is absent, declared carve-out markers, and how findings compose into an exit code. Eleven-to-thirteen SR rows each state a fragment of it as a secondary clause; no row takes it as its subject, so a new checker can violate it without failing anything.

What is being decided

Where this came from, and why it is not a worker's call

The remap's method is a blind re-derivation: an agent derives the minimal module map from the requirements alone, blind to the live layout, and the live map is diffed against it. Two agents ran it on deliberately different axes - one working backwards from the declared boundary outputs, one clustering obligations by shared signal and failure mode. They agree on 97.2% of SR pairs. Their single most striking agreement is one the arithmetic cannot even see, because it cannot be matched on requirement overlap: BOTH returned a module that owns no requirement at all, and both named the same subject.

Record: docs/plans/2026-08-25-blind-minimal-map-derivation.md (the returns and the measured agreement); docs/plans/2026-08-25-remap-alignment.md section 6 (this row's origin in the alignment pass).

The restating rows

Both teams enumerated them independently and the lists overlap almost exactly. The union: SR-149, SR-150, SR-157, SR-158, SR-159, SR-162, SR-163, SR-164, SR-167, SR-180, SR-181, SR-182, SR-015. Each invents its own phrasing for the same protocol - "warns by default and fails under --strict", "advisory classes never change the exit code", "the declared warn-or-gate severity for each class", "warn-first with --strict gating", "each as an advisory", "the declared warning-to-gating policy", "never gating".

The corpus concedes the hole in its own words

SR-158's acceptance already says it: "A class whose severity is stated at no declaration site is undeclared, and this row is unsatisfied until it is declared there." That is a row declaring itself unsatisfied for want of a declaration surface no row owns.

Three adjacent restatements the same teams counted, which a ruling should decide with it

  • "Naming the at-fault row and cell" - one behaviour, fifteen phrasings (SR-137, SR-138, SR-144, SR-149, SR-150, SR-157, SR-158, SR-159, SR-162, SR-163, SR-164, SR-165, SR-180, SR-181, SR-182).
  • "Every degrade is named, never silent" - eight rows (SR-006, SR-043, SR-138, SR-152, SR-154, SR-167, SR-173, SR-180), which is SN-008's honesty property and the single most-restated obligation in the corpus.
  • Vacuity, "an absent optional input costs nothing" - a clause in eight rows (SR-009, SR-070, SR-157, SR-159, SR-162, SR-167, SR-173, SR-180), the subject of none; SN-012 is the parent need.

These are the same contract seen from three sides. Ruling them separately would produce three partial rows.

What is NOT being proposed

No consolidation work is filed against this. Building a shared finding module before the obligation is stated installs a mechanism ahead of its requirement, which is the inversion the process exists to prevent - so the remap program filed this row and stopped, rather than minting module work off a requirements finding.

Blast radius

ONE ROW TO MINT OR DECLINE, AND A CITATION SWEEP IF IT IS MINTED. Minting is cheap in itself - one SR at the requirement tier, with its LLR/TC decomposition following the ordinary machinery under the declared dial. What is not free is the sweep: each of the thirteen restating rows would want its fragment replaced by a citation, and every one of them is Approved, so each edit is an amendment that overrides an attestation and re-opens the approval surface for that row. That is the owner's act by construction, and it is the reason this is a ruling rather than a task.

DOES IT CROSS THE KIT LINE? Yes, if minted: the contract is a property of the DELIVERED harness, not of this repository's instance, so the row ships and every adopter inherits the obligation. Against that: the behaviour it describes is already what the shipped checkers do, so the row would be stating a delivered property rather than requiring new work. The measurable risk is the opposite one - a row that states a contract the shipped checkers do not uniformly honour would be minting a known-red requirement, and nothing has measured uniformity across all thirteen.

WHAT IT COSTS TO LEAVE IT: the property every checking row assumes is enforced by nobody. A new checker can attribute a finding to no location, invent a fourth severity word, gate an advisory, or pass silently on an absent input, and no row fails - which is exactly the TEST-ENGINEER failure class (an obligation with no enforcer) applied to the enforcement layer itself. There is also a live instance of the same class one level down, found by this pass: three of the five declared exception-list readers drop a malformed declaring line silently while two report it, and the two record in their own docstrings why the three are wrong (filed as WI-519).

Options
  • (a) MINT THE ROW, SWEEP THE CITATIONS. One SR stating the contract - location attribution, a severity class from a closed vocabulary, one strict-mode escalation rule, declared carve-out markers, vacuity, and an exit code composed only from the gating classes - then replace each fragment with a citation as its row is next amended anyway. FOR: the most-restated obligation in the corpus gets a subject, and the restatements can then shrink instead of multiplying; it is what both independent derivations concluded. AGAINST: thirteen Approved rows eventually want an amendment each, and uniformity across the shipped checkers has not been measured, so the row could land red.
  • (b) MINT THE ROW, SWEEP NOTHING. State the contract, leave every existing fragment exactly where it is, and let new rows cite instead of restate. FOR: banks the subject at almost no cost and no re-attestation; the duplication stops GROWING even if it does not shrink. AGAINST: the corpus keeps thirteen statements of one thing, so the retrieval collision the doctrine names is unrelieved, and a fragment that drifts from the new row is now a contradiction rather than a repetition.
  • (c) MEASURE FIRST, THEN RULE. Before minting anything, measure whether the shipped checkers actually honour one contract - the severity words in use, whether every finding names a location, what each does with an absent optional input - and file the numbers. FOR: the WI-516 precedent for exactly this shape (measure, do not rewrite); it answers whether (a) would mint a green row or a red one, which no option above can currently say. AGAINST: a third pass before the question is answered, and the pattern where a measured number with no row to rule on becomes a forgotten one.
  • (d) DECLINE, AND RECORD WHY. Rule that the contract is a coding convention rather than a requirement, and that thirteen rows each stating their own disposition is the correct shape because disposition is genuinely per-row. FOR: it is a defensible position - the severity of a given class IS a per-row decision, and a single row could over-constrain rows whose needs differ; it costs nothing and closes the question honestly. AGAINST: it accepts that the property every checking row assumes has no enforcer, and it leaves SR-158 declaring itself unsatisfied with no path to satisfaction.

What the direction changes about the options: the mint target in (a)/(b) is re-read at the INTERFACE tier - the contract would be stated as an interface contract (wherever OI-63's re-ask puts contracts), NOT minted as a new SR or elevated to an LLR - and any statement must honour the one-definer rule: for a given interface expectation, EITHER the interface contract defines it OR the LLR does, never both. RECOMMENDED: (c) then (a) - measure, then mint, with (b) as the fallback if the measurement comes back ragged.

The reason is that (a)'s single unanswered question is decisive and cheap to answer. Everything about (a) is attractive except one thing nobody has measured: whether the thirteen rows describe ONE contract or three similar ones. If the shipped checkers already agree - same severity vocabulary, location on every finding, the same treatment of an absent input - then (a) mints a row that is green on the day it lands and the sweep is bookkeeping. If they do not, (a) mints a requirement the delivered harness fails, and the honest response to that discovery is a different piece of work entirely. The measurement is a read over the checkers this repository already ships, in the WI-516 shape that has now been run twice successfully.

(b) is the right answer for a ruler who wants the subject banked without opening thirteen attestations, and it is strictly better than (d) at the same price: a row that exists and is cited by new work stops the growth even if it never shrinks the backlog.

(d) should not be dismissed. Its argument is real - disposition IS per-row, and a contract row that fixed severity per class would over-constrain. But it can be answered within (a): the contract to state is the PROTOCOL (a finding names its location, its class comes from a closed vocabulary, an advisory never reaches the exit code, an absent optional input is vacuous and says so), not the per-class severity, which stays each row's own declaration.
