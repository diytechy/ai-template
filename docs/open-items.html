RUNG_TIERS in spine_rules maps every rung of the stage ladder, and only those, to the tiers whose in-work rows hold the repository at that rung, each named by its id prefix and the spine_stage keyword carrying its rows: DevStg-Needs to SN (sn_ids) and STK (stks); DevStg-Boundary to B (bifs), DA (das) and SUR (surs); DevStg-Reqs to SR (srs); DevStg-Arch to CMP (cmps); DevStg-LLReqs to LLR (llrs); DevStg-Tests to TC (tcs); DevStg-Impl to the evidence record (evidence_passed); DevStg-Release to none. A tier is named at one rung only. Over keyword arguments in which every tier is adopted, read and settled and the evidence passes, spine_stage returns DevStg-Release, and putting any one named tier in work returns the rung the table names for it. The keywords the table names, with sn_draft, cited_srs, have_bifs and have_cmps, which travel with a tier's rows, are exactly spine_stage's parameters. spine_stage does not read the table.
Rationale
A reader drawing the ladder that restates which tier holds which rung falls out of step with the derivation whenever a tier or a rung is added. Running spine_stage from the table would make that impossible, but its need-coverage arm sits after the requirement arm, so its arms are not a flat ladder; driving the function from a test holds the table to it instead, and a new parameter fails that test until the table names it.
