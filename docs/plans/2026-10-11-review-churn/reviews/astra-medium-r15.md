## Views for the owner

**Direction of F.** Keep F's core, with the revisions above. A exchanges roughly 527 existing code-side pairs for at least 508 authored pairs before headers, and makes every LLR pass through a seam. B adds a reviewer-dependent fitness migration; C improves the choice of seams but retains that allocation pressure. D is the least disruptive baseline; E usefully adds genuine delivered-artifact seams and fitness at touch, but its optional IF-to-LLR list adds another maintained allocation. F's distinction between an LLR constraining a boundary and a TC observing behaviour at another boundary is better motivated than A–C and potentially leaner than E. Its advantage depends on making those two relations precise, not on declaring that architecture contains the behavioural proof. Prefer that corrected F over E; do not approve its claimed derivations or mandatory stage-based partition as written.

**F-call 1 — ownership.** Choose authored, role-bearing component ownership on IFs, checked against typed ownership citations and file headers. That records design allocation independently of realization. Retain authored external identities such as IF-032's external:git and resolve shared file-channel production explicitly for IF-047. Generating both ownership and its purported check from one header would lose the independent comparison. OI-48's declared kernel remains singly owned and exempt from required helper seams; it is not an implicit external party.

**F-call 2 — stubs.** Do not require every future code file to exist at DevStg-Arch merely to draw architecture. IF/component design can precede implementation filenames. Where coordinated work genuinely needs a file allocation, a header-only stub is reasonable at design time, but specify its permitted content and exclude it from implementation evidence. F must not claim that Component plus Contract markers resolve an otherwise unlinked LLR. Record red-before at the test event without requiring a committed red build.

**F-call 3 — TC interface references.** Confirm the distinction of relations, not the current short wording. An LLR names the interface whose behaviour it constrains; a TC needs an explicit observation interface where it cannot be unambiguously derived from its verified obligation. Generated views can materialize both without maintaining an IF-side list. Exercise the rule on a same-interface TC, a dashboard-level integration TC, a TC spanning several LLRs/interfaces, and a kernel LLR observed through an outer interface.

**F-call 4 — ID continuity.** Confirm the placement beside never-reused and CLARITY/MEANING. The missed-external-citation test is more useful than a rename-only rule. Check semantics against the original purpose and recorded rationale, not a presumed census of all downstream links. I read WI-472 before considering the retirement of SR-180's chain; it protects language-agnostic realization discharge and explicitly does not establish a blanket backlink floor. Its successor must preserve that purpose or explicitly overrule it.

**F-call 5 — recursion.** Confirm acyclic, single-parent component containment and derived ancestry; the current kit already has PartOf machinery, so this is partly a change of use and constraints rather than an entirely new field. Do not confirm recursive LLR semantics by implication. Prefer direct SR-root links for flat obligations unless the W3/Gilbert trial demonstrates a need for parent LLRs. Where aggregate LLRs really are needed, an authored refinement edge earns its upkeep by identifying the obligation to prove; containment cannot replace it. Keep the four-component depth-0 constraint here specific to this repo, not an adopter rule.

**F-call 6 — descent.** Confirm the state-or-source test as an antidote to invented quantitative requirements: LLR-292's non-overlap property is independently decidable, while a guessed spacing constant usually is not. Add the missing separation between behavioural decomposition and structural partition. A stakeholder-describable mode is evidence that behaviour needs specifying, not sufficient evidence that another component or interface is needed. Shared services and hidden implementation decisions can supply the more sustainable partition.

**F-call 7 — checks and vocabulary.** A and C are reasonable advisory experiments after the input semantics exist; B should wait for a real condition-table use case and its migration. A can validate declared labels but cannot infer complete behavioural partitions from today's prose data cells. C must include requestor and file-channel edges and report missing endpoint information rather than assuming the import graph is complete. Keep the research's useful arithmetic distinction: 8 cases remain 8 for the two-output example; 48 versus 22 depends on a genuinely complete narrow intermediate channel. Its “verified,” “record only” and “unverified” citations should retain those qualifications when adopted; the README's collective “confirmed with sources” is too broad.

**Open row — WI if_refs.** Prefer derivation where the WI explicitly names touched LLRs, but do not pretend current sr_refs or an unstructured spec always supplies that set. Shared IF use is potential conflict, not a dependency or overlap proof; keep needs authored. An optional explicit IF scope can earn its place for architecture-only changes that have no touched LLR, provided it is not a mandatory duplicate list on every WI.

**Open row — decomposition (a)/(b) and parent LLRs.** The current ladder implements terminal LLRs beneath recursively scoped requirements, so (b) is a substantive process migration. Test it on Gilbert SR-012's rig obligations and their tests, not just the software lane diagram. The experiment must show that every former SR obligation, parent proof and signed approval remains accounted for. Defer that migration without blocking the independently useful sparse-link and wording changes.

**Open row — module.** Use source module/file for software and realization artifact for the broader category. Gilbert ASSET-001 is a pinned fetched directory; its assets and procurement rows are acquisition records, not automatically source files or behavioural parents. Neither a universal one-file definition nor an unqualified physical “module” improves orientation here.

**Open row — consumer/requestor roles.** Settle this before mechanizing F's LCA or check C. IF-175 has six requestors and no consumers; the distinction is not cosmetic. Typed local citations can derive realization-role views while component-level architectural endpoints and external IDs remain independently authored. Preserve the existing semantic relationship review in reviewer.template.md; class compatibility alone cannot show that a producer supplies what a consumer expects.

**Open row — interactive dashboard evidence.** Test the emitted document for structural and geometric claims, including LLR-292, but use executed interaction evidence for interaction claims. A browser harness earns a dependency-ledger entry if interaction is part of the delivered contract; an explicit independent inspection can cover a bounded manual claim. Parsing handler text is not evidence of either runtime interaction or its absence. Do not weaken the requirement solely to retain stdlib-only testing; stdlib preference governs kit scripts, while test dependencies already have a declaration path.

**Open row — IF data cells.** Classify genuine boundaries versus helper usage before rewriting the reported 114 code-naming cells. An id and a schema can describe an interface without a code carrier, but domain constraints and compatibility still need independent judgement. Retire helper-only rows only after reading their original rationale; IF-175 is a concrete warning that something looking like a library call can encode an important shared semantic boundary. Keep the delivered-dashboard IF and judge the other proposed delivered seams individually.
