## Item 11: views for the owner

**Call 1, code points only to interfaces.** Prefer one trace, but not by retiring `Implements:` before its replacement is checkable. Three things it carries today have no IF-side substitute in the plan: the minimum profile (a one-module project has no IF registry, PROCESS.md:27, §8 skip), the test-first and coverage checks that count LLR ids in code, and the 73 LLRs (302 − 229) that no code tags today, which the IF route would not reach either. Keeping both tags indefinitely is the dual path the owner's rule forbids; the sustainable form is one coordinated migration whose gate is "every LLR reachable through a code-cited IF or declared unreachable with a reason", after which `Implements:` is deleted in the same WI.

**Call 2, interfaces name the LLRs or SRs they carry.** Confirm for LLRs only. The SR half already has a derivable home (SR `boundary_refs` ↔ IF crossing cells; MAJOR above), and OI-112's option (b) proposes the opposite direction for the same relation, so the owner should rule the direction once (IF → requirement, never requirement → IF, consistent with ruling 5's "point up") and close OI-112 with it. An authored IF → LLR list is a claim; its check is the reviewer's correspondence check plus a structural one: every carried LLR has a TC, and the TC's `verifies` names the IF or a module the IF owns. Overruling OI-67 and the 2026-09-23 decision explicitly is right, with the "verified by nothing" objection answered by that check, not by removing the join.

**Call 3, every LLR carried by an interface.** Do not mint `call` seams to satisfy a rule. The 55 (reproduced exactly: 55 of 302 whose `module` owns no IF) split into kernel-resident rows (OI-48 ruled those edges non-seams), rows carried by a seam another module owns, and rows that are really internal design notes. The first two need no new row; the third is the item 5 contract-voice problem and should be reframed or retired after its rationale is read. The honest rule is "every *leaf* LLR is carried by an interface or declares why it is internal", with the declaration a closed allowance, not a per-helper IF.

**Call 4, files declare their component; LLR → CMP checked or derived.** Confirm the file header for software source files only (not PART, ASSET or boundary files, which carry a `Component` cell already), and keep LLR → CMP authored. Deriving both the LLR's component and the IF's component from the same header leaves nothing to check the header against; the 2026-08-13 WI-441 re-tag shows the authored cell was once a copy of the module map, which is an argument for checking it, not for deleting it. IF → CMP derived from a unique, role-identified owner is fine for internal seams; external-owned IFs need an authored participating component.

**Call 5, IF approval.** No new status; IF rows already sit under `DevStg-Arch` authority (`kitlib/authority.py:90`) with `Drafted · Approved`. Rule that a row carrying LLR ids is spine content: its first approval and any change to its carried list go through the sitting (OI-112 option (a)), while generated cells (owner, consumers from code) never reopen it. That is the one place the two open items meet.

**Call 6, contracts cited only where served (query 1).** Nothing mandates a contract per function today, and nothing can: bodies are parsed from the module docstring only. The mechanical bound on an over-claim today is the registry's authored `owner` cell (stray-declaration error under `--strict`); keep that cell authored and role-bearing, and the check stays independent. The other candidates are weaker: a TC exercising the citing symbol proves reachability, not realization; a component declared in the same file is the citer's own claim. Review alone is not acceptable for the structural half (ids live, roles declared, owner unique) and is acceptable, and unavoidable, for the semantic half; that is consistent with item 1, which closes syntax, not meaning.

**Call 7, work items name their interfaces (query 2).** `if_refs` beside `sr_refs`, optional, ids only; never instead. They answer different questions (what obligation the row delivers; which seams it changes), 7 of 31 queued rows have no requirement and process rows will never have a seam, and the consolidation census is advisory by design ("Often correct; worth seeing", `check_trajectory.py:1606`). Keep `needs` authored and acyclic as today (`check_trajectory.py:872-878`); IF provider/consumer order is runtime dataflow, not build order (a consumer can be prepared before its provider switches), so use it to *warn* on a missing edge, never to derive one. The 2026-07-14 deferral was on migration cost; the cost is one optional list cell plus a resolve check, which the blast-radius query now earns.

**Call 8, decomposition (a) or (b).** See the section below; recommendation (b), with conditions.

**Call 9, terminology.** Keep "module" for the software source file, use the kit's existing "realization artifact" (PROCESS.md:578, OI-20: a code symbol or a part source) for the bound unit, and leave part, asset and component as they are. "One file in git" is true of a module and of a designed part source, false of a bought part and a fetched asset, and §10's "one module, one repo" sense should be reworded to "sub-system" where it survives.

**Call 10, IF roles and external owners.** Author the owner id (module path or `external:` party), one per row, and generate `consumers` and `requestors` from a typed consumer citation. That keeps the only independent check of an over-claimed owner citation (call 6) and gives an external-owned row a home for its CMP (the authored far-side module's component).

**Owner's query 1.** Confirmed: no check or PROCESS text requires a contract per function; the per-module pressure is three warn-only connectivity messages and §8's header-first mint for modules with seams. The "every shipped module carries `Implements:`" rule exists nowhere today: `[checks] backlink_coverage_min` is a share of live LLR rows (template 0, this repo 50; `check.py:610-625` arms `--strict-backlinks` at DevStg-Impl, although PROCESS.md:181-188 says DevStg-Tests, a small doc/code drift outside this plan). Under item 11 it becomes "every source file declares a component and either states a contract or a closed internal standing"; the mechanical refusal of an over-claim is the authored owner cell (above). Review alone is not acceptable for the structural checks and is the right instrument for realization.

**Owner's query 2.** The WI schema (`kitlib/registry.py:111-135`: `sr_refs`, `needs`, `adjudicates` as lists) has no interface cell; `sr_refs` is dangling-checked at warning level only. Requirement rows express parents (`sn_refs`, `sr_refs`) and joint-delivery siblings (`delivered_with`, defined as "a statement about the requirement's own delivery argument", never order); no SR cell names a parent SR or a component scope and no LLR cell names a parent LLR (`kitlib/spine.py:886-924`). So the queue can mirror SR → LLR, one level, and the sub-scope recursion PROCESS.md §4 promises is carried only by CMP `part_of`, which is empty on all four live CMP rows. An IF is a split *candidate* for item 3, not S1's unit: one deliverable often owns several seams and two independent deliverables can share one; `if_refs` makes S4's "two or more IF seams" countable, but the count measures surface, not independence.

**Decomposition alternatives.** *(a)* SRs at every component scope, terminal LLR. Strengths: one obligation tier with one form rule (one shall, applied to the interface at that component level), the DevStg-Reqs/DevStg-Arch recursion as written, a natural fit for physical assemblies (a sub-assembly spec is a requirement, not a design detail), and the LLR floor stays a binding check. Weaknesses: the recursion is unexpressed (no parent-SR or scope cell), SR ids multiply with depth, and the churn the owner expects (an LLR that needs breaking down must be re-minted as an SR, with approval ancestry re-sat) is real. *(b)* SRs only at the boundary, LLRs recursive. Strengths: the SR set is fixed by the boundary and only a boundary change moves it; architectural refinement adds children without changing any id's tier; and the IF → requirement link becomes tier-determined (a crossing IF carries an SR, an internal seam carries an LLR), which is cleaner than call 2's "LLR or SR" list. Weaknesses: "LLR" then names two kinds of row, an allocation node and a bound leaf, and every rule that assumes the leaf must learn the difference; an aggregate LLR has no realization artifact, which contradicts PROCESS.md:578's definition of the tier. **Migration cost of (b):** a parent link on LLR (one home: `sr_refs` for roots or a new `llr_refs` for children, never both), acyclicity and root-reachability in `coherence.py:172-175` (today "LLR has no SR parent" and "references unknown" would reject every child), transitive "SR has no LLR" (:146-152), the ancestor-aware triangle rule (`trace.py:1608-1617`), approval ancestry (WI-850's parent-first rule), `derive_stage`/founded derivations, the PROCESS.md:571-578 and :614-624 text ("TERMINAL", "the tier does not recurse"), the templates and `kitlib/spine.py`, the dashboard trace matrix, a RESYNC entry with a migration script, and adopters: Gilbert is on the legacy CSV spine at kit `0fc58fb` with a pending resync, so the column is cheap but the rule change lands on a repo whose only sub-scope obligations today are SRs (SR-012's rig) bound to LLR part sources; under (b) those SRs would become parent LLRs with no artifact. The 2026-08-13 form rule is tier-neutral (it ties each shall to an interface at its own level), so it holds under both. Item 11's discharge rule is leaf-only under either reading; under (b) a parent is discharged by all its children and an integration TC, never by a citation. **Recommendation: (b)**, on condition that leaf versus aggregate is derived from having children (never authored), that a parent has exactly one parent link, that discharge is leaf-by-realization and parent-by-children, and that it ships in item 5's schema WI as one RESYNC entry. If the owner wants the smaller step first, (a) plus a `parent` cell on SR removes the unexpressed-recursion defect alone, but leaves the tier-change churn.

Software source file is the only sense the plan's definition fits; Gilbert shows physical parts are either LLR-bound parametric sources (the same mechanism) or PART/ASSET rows with no tracked file.
