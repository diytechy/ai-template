# W3 Autonomy — independent decomposition dry run

This critique uses only Documents 1 and 2 supplied in the brief. Module names below omit `scripts/` and `.py` unless needed. No repository, linked rubric source, requirement body, or full interface contract was consulted. A statement marked **inference** is a proposed interpretation or design, rather than a fact supplied by the bundle.

There are **three candidates**: C0 retains W3 whole; C1 extracts the provider execution mechanism; C2 extracts the governing protocol vocabulary. C1 is the strongest next cut to investigate. The bundle supports that preference, but does not establish an approvable decomposition: it lacks a semantic dependency table, complete interface forms, change history, and recorded stopping boundaries. C2 identifies a plausible decision family but has materially greater shared-definition and contract costs. A split following Flow 4's stages is considered and rejected as a rationale, rather than counted as a fourth developed candidate.

## What the evidence establishes

`CMP-008` has no children. Its notes enumerate the coordinator's constituent modules instead of identifying a hidden decision. W3's generated membership is the union of files named by its LLRs, not a declaration of exclusive architectural ownership. Consequently, the 78 files, 290 internal import edges, 65 internal IF rows, and 121 boundary IF rows describe the current projection; they do not establish 78 architectural responsibilities or 186 distinct semantic dependencies. Twenty-six files also belong to other components under that projection. In particular, treating `acceptance_record`, `check`, `check_trajectory`, or `bootstrap` as exclusively W3-owned would contradict Document 2 §3b.

The definition of an internal interface also requires only one W3 far-side endpoint. Thus IF-175 is classified internal even though `gen_verdict_rollup` is an external reader. IF-046 similarly includes external readers. Every candidate must classify individual endpoint crossings, not merely flip the row's existing internal/boundary label.

The import graph is evidence of access, not of semantic influence. For example, `agent_loop -> session_service` and IF-246 establish a call relationship; they do not prove that every field of `Call` affects every field of `Outcome`. The bundle supplies no output × input table or choice counts. None of the candidates can honestly claim A4(b)'s sum-of-case-counts reduction.

The shared-kernel convention is also material. Document 2 §1 puts `kitlib/config`, `git`, `registry`, and other core modules under CMP-006's declared kernel rather than individual interface rows. High in-degree for `kitlib/config` (28), `git` (19), and `spine` (19) therefore cannot automatically be read as W3-local coupling to eliminate. The rubric's literal A6 rule and that kernel convention need reconciliation; this critique does not silently exempt kernel crossings.

## C0 — keep W3 whole

**Allocation.** Retain all current W3 membership and external ownership arrangements. Add no child component or internal boundary.

**Hidden decision and cohesion.** The best available umbrella is how an unattended coordinator advances work while preserving the kit's admission, judgment, and close obligations. This is an **inference** from Flow 4 and the Flow 1/5/6 titles, not the decision named by CMP-008. Flow 4 gives a real reason to keep some behavior together: `dispatch` admission, `integrate` claim and merge, `handback` partial closure, and `intake` post-merge effects preserve a station-cycle protocol. LLR-151, LLR-154, LLR-161, and LLR-340 name related constraints, although their bodies are unavailable.

That umbrella is weak evidence that provider CLI adaptation, verdict-binding grammar, link-aware moves, transcript ingestion, and station scheduling all change for one reason. The docstrings explicitly identify different decisions: `session_adapters` owns CLI differences; `kitlib/verdict` owns governing-verdict carriage and tree binding; `spec_move` owns an indivisible move-and-relink operation. Keeping them in one component allows all changes to remain inside W3, but that is a tautological blast-radius result, not evidence of internal cohesion.

**Dependencies.** C0 removes or narrows none of the 290 import edges. It leaves the broad coordinator surfaces IF-065 (`agent_common`), IF-090 (`intake`), IF-173 (`integrate`), IF-175 (`kitlib/verdict`), and IF-246 (`session_service`) internal where the current projection says so. It preserves the Flow 4 transaction boundary around post-merge intake without adding a component crossing between `integrate` and `intake`.

**Costs.** Zero new boundary interfaces, shared services, file moves, or child allocations. Existing contracts, mode classes, and the dependency table still require assessment; staying whole does not waive A2–A6 or A8. The cost of retaining heterogeneous responsibilities is a potential larger review and change scope (**inference**); file size alone does not establish that cost or a defect.

**Stopping record.** C0 cannot currently record that further decomposition fails the rubric's tests. `session_adapters` has a named decision and independently checkable obligations (LLR-266–268 and LLR-352), while `plan_round` has a named lifecycle and observable dispositions (LLR-070, IF-058). Neither is merely a paraphrase or an invented number. Their existence defeats an unsupported blanket A8 stop, although it does not compel making either a child. C0 remains viable only if a completed A1/A4/A7 comparison shows their boundary costs outweigh the isolation gained. That evidence is absent.

## C1 — isolate provider execution mechanisms

**Allocation.** Create one child, provisionally **Provider execution**, containing `session_adapters`, `agent_session`, and `kitlib/winjob`. A second child, **Coordination**, contains the rest of the current W3 membership, retaining the existing co-membership of the 26 shared files. These are proposed component allocations, not a demand to move directories. Policy, routing, retention, brief construction, and recording remain in Coordination: `agent_route`, `agent_policy`, `session_service`, `session_keep`, and `usage_ingest` are not assigned to the provider mechanism.

**Decisions hidden and cohesion.** Provider execution hides provider invocation, provider output interpretation, and platform process containment. The evidence is unusually direct: `session_adapters` says it is the only place CLI differences live; `agent_session` owns argv/stdin construction, launch and capture; `kitlib/winjob` owns Windows job-object helpers. Grouping them treats runner representation and execution mechanics as one mechanism family (**inference**). It does not claim routing escalation or retained-session policy is the same decision: `agent_route` and `session_keep` explicitly name those separate responsibilities.

**Change probes, all inferred rather than observed frequencies:**

| Likely change suggested by the bundle | C0 | C1 | Evidence and limit |
|---|---|---|---|
| A provider changes its structured usage/compaction representation while the normalized contract remains stable | W3 | Provider execution | Adapter docstring; LLR-266–268; IF-245/266. A changed normalized meaning would also affect consumers. |
| Windows job containment implementation changes without changing launch guarantees | W3 | Provider execution | `agent_session -> kitlib/winjob`, IF-302, LLR-026. No platform change history is supplied. |
| Review escalation or blackout policy changes within the current launch contract | W3 | Coordination | `agent_route` fixed escalation; `agent_policy` blackout; IF-044/291; Flow 5. A new launch capability could still require both children. |

These probes identify distinct change reasons; they do not prove the rubric's unspecified “most changes” threshold.

**Dependency gain.** The graph shows no import from the three extracted modules back into the residual W3: `session_adapters` imports no kit module, `agent_session` imports only `kitlib/winjob`, and `kitlib/winjob` imports none. The resulting child-to-child import direction is triangular. Its incoming graph edges are exactly:

- `agent_common`, `agent_brief`, `agent_loop`, `agent_route`, `plan_runner`, and `session_service -> agent_session`;
- `agent_route`, `session_service`, and `usage_ingest -> session_adapters`.

That is nine former internal import edges made explicit at the child boundary; none disappears merely because the files are assigned differently. `agent_session -> kitlib/winjob` stays internal. The gain is structural separation of provider mechanics from registry/station imports: these three modules currently have no edges to `intake`, `integrate`, `schedule`, `acceptance_record`, or the shared registry kernel. The cut preserves that absence as an architectural restriction (**proposed rule**). It is an A4(a) blast-radius and proof argument, not a measured removal of semantic table cells.

Extend endpoint coverage for graph readers `agent_common`, `agent_brief`, and `agent_route`, or establish that their imported information has a different meaning and needs a separate row. The bundle cannot distinguish those alternatives. |

Thus the known design exposes **three existing rows at a new child boundary** and relocates responsibility for one existing outer interface. It introduces **zero known new semantic interfaces**, subject to resolving IF-064's unmatched import readers. That qualification matters: imports reveal a coverage question, not enough information to invent an exact missing schema. Full forms and any unreported file/environment handoffs must be checked before asserting an exhaustive implemented contract inventory. IF-245 and IF-266 must also be checked for whether they carry distinct meanings or duplicate compaction information; their abbreviated summaries cannot decide B2.

The price is three boundary contracts to declare and test, including shared provider definitions, plus component/LLR allocation and outer-interface ownership edits. Physical file moves are unnecessary. LLR-026 spans both launch and platform helpers, and other provider LLRs need allocation by obligation, rather than mechanically assigning all of `session_service`'s LLRs to this child. Tests must establish that normalized answers are sufficient for consumers; the current IF-064 summary lists symbols rather than a complete typed request/answer.

**Stopping point.** Provider execution is a provisional leaf, not an automatic A8 stop. A candidate child for Windows containment has its own source-backed pass/fail (LLR-026, IF-302), so tests 2–4 do not justify dismissing it. A further provider-adaptation versus process-launch split also has independent observable behavior (IF-245/266 versus IF-064). A1/A7 may nevertheless favor keeping these mechanisms together because `agent_session -> kitlib/winjob` is a single local dependency and no supplied change history demonstrates a benefit from exposing it. That is a boundary-cost decision, which A8 currently does not offer as a stopping category. Individual provider implementations beneath `session_adapters` are implementation detail unless evidence establishes distinct component obligations; the bundle does not list their internal structure.

Coordination is **not a justified final leaf**. Its `plan_round` lifecycle, `kitlib/verdict` semantics, and `observation_cadence` policy are further candidates requiring assessment. C1 is a useful first cut, not a claim that a two-leaf tree finishes W3's decomposition.

## C2 — isolate governing protocol vocabulary

**Allocation.** Create **Governing protocol** containing nine modules: `kitlib/verdict`, `station`, `sitting`, `done_when`, `dispute`, `adoption`, `decisions`, `plan_pass`, and `provenance`. **Coordination and effects** contains every other current W3 member, with existing other-component memberships preserved. The two children distinguish what constitutes admissible evidence and records from the orchestration and writes that use them. This grouping and its name are **inferences**; the nine docstrings name several separate definitions, not one pre-existing component.

**Decisions hidden and cohesion.** The child hides record identity, binding, grammar, and interpretation: governing verdict/tree identity (IF-175); Done-when comparison and blessing (IF-242/286); combined sitting identity/findings (IF-287); dispute grammar (IF-290); adoption disposition (IF-294); delegated decisions (IF-255/256); loop attribution (IF-194); and plan-pass record grammar (`kitlib/plan_pass` docstring). Those definitions are read by multiple orchestration and gate consumers. Centralizing their ownership respects A6; it does not require replacing them with a new runtime “verdict service.”

Cohesion is mixed. `done_when -> decisions, sitting`, `sitting -> verdict`, and `verdict -> station` support a connected evidence vocabulary. But `adoption`, `dispute`, and `provenance` have no W3 imports, and the bundle does not show that their definitions change together. “All records” can become another administrative grouping. A split into one component per grammar would multiply shared boundary definitions, so C2 must justify its family-level boundary rather than assume either extreme is correct.

**Change probes, inferred:**

- A compatible change in how a verdict artifact is located or bound to a tree could remain in Governing protocol (`kitlib/verdict`, IF-175, LLR-207). A changed validity rule may alter the behavior required of `integrate`, `acceptance_record`, and `review_brief`; information hiding cannot promise those changes remain local.
- A station merge strategy or post-merge intake implementation could remain in Coordination and effects (`integrate -> intake`, IF-090/173/186; Flow 4), provided its record contracts remain stable.
- A new kind of combined adjudication could touch both `kitlib/sitting`/`dispute` and `adjudicate_brief`/`adjudicate_act`/`review_brief` (IF-287/290/296 and LLR-310/315/338). This is a plausible cross-cutting change grounded in named responsibilities, and counts against claiming uniformly high cohesion.

**Dependencies gained and retained.** The extracted modules' graph dependencies stay within the group or go to CMP-006 kernel modules: `kitlib/config`, `git`, and `registry`. None imports a residual W3 orchestrator. That is a promising one-way import structure. Many formerly local readers become boundary readers: for example, `integrate -> verdict, done_when, decisions, provenance, station`; `acceptance_record -> decisions, done_when, sitting, verdict`; and `review_brief -> dispute, done_when, plan_pass, verdict`.

The interface evidence prevents declaring the full dependency relation triangular. IF-046 names `kitlib/verdict` as a requestor of residual `score_reviews`, although the graph lists no such import. Either this is an actual reverse information dependency or an inconsistency to resolve. No claim of isolation may discard it. Raw review files also remain available to `integrate`, `score_reviews`, `review_brief`, and `kitlib/verdict` through IF-047. Thus a verdict intermediate is demonstrably not the only declared channel available to these consumers; A4(b)'s sufficiency premise is unestablished. No case reduction is claimed.

Reallocating acceptance, approval, and close obligations cannot be completed from LLR titles alone. Boundary testing increases sharply: schema consumers, file consumers, bindings to tree identity, and the possible scoring back-edge all need coverage. Relative to C1, this buys a more broadly used policy boundary at substantially greater declaration and verification cost.

**Stopping point.** Governing protocol cannot honestly be declared indivisible. `dispute`, `adoption`, and `plan_pass` each name a distinct grammar and independently judgeable obligation (LLR-314, LLR-335, LLR-337). Their candidate child boundaries do not fail A8's paraphrase or no-pass/fail tests. Conversely, record fields and grammar alternatives are not automatically further components: an enumerated verdict case earns behavior, not a separate owner. Keeping them within one protocol component requires an A1/A7 cohesion-versus-interface-cost record, which A8 does not currently accommodate. Coordination and effects also retains identifiable lifecycle/policy candidates, so neither proposed child has a fully justified final stopping record.

## Comparison and preferred direction

| Criterion | C0: whole | C1: provider execution | C2: governing protocol |
|---|---|---|---|
| Hidden decision | Broad coordinator policy, inferred | Provider representation and launch mechanics, supported by docstrings | Evidence/record semantics, supported individually but family cohesion inferred |
| Structural gain | None | Nine import edges become explicit, no reverse child import | Many vocabulary dependencies become explicit; import direction is promising, IF-046 challenges semantic direction |
| Case-count gain | Not established | Not established | Not established; IF-047 supplies raw side channels |
| Shared definitions exposed | No additional child surfaces | Provider vocabulary and compaction, IF-245/266 | Verdict, sitting, Done-when, decisions, provenance, adoption, dispute, station, plan-pass |
| Known interface cost | Zero new child contracts | Three existing rows gain child crossings; IF-064 endpoint gap | Nine internal rows gain child crossings; IF-046/093 endpoint work; new plan-pass surface; conditional station/kernel surfaces |
| Physical relocation | None | None required | None required |
| Final stopping justification | Missing | Missing for residual scope and optional mechanism subcuts | Missing for both children |

**Preferred direction: C1, provisionally.** It has the strongest explicit information-hiding evidence (`session_adapters`' own responsibility statement), an acyclic provider-facing import boundary, no new shared-kernel dependency, and the smallest known contract expansion. C0 avoids boundary costs but supplies no convincing common change reason for all W3 responsibilities. C2 may ultimately be worthwhile, particularly for single-owner protocol semantics, but the bundle exposes an unresolved scoring dependency, widespread shared-definition readers, and uncertain kernel/station contracts. C1 beats C2 on the evidence/cost balance available here; this does not establish that C2 should never follow it.

A Flow 4 stage split is not justified by ordering alone. `dispatch`, `lane`, `integrate`, `handback`, and `intake` already exchange work, but the graph includes `dispatch -> intake, integrate, handback, lane`, `handback -> intake, integrate`, `lane -> integrate`, and `integrate -> intake, bookkeeping, schedule`. The corresponding surfaces include IF-090/136/137/173/186. These are multiple cross-stage accesses, rather than a simple chain of stage-local inputs and outputs. They demand a decision-based argument and an explicit interface inventory before a stage-aligned cut can earn its place.

In particular, `integrate`, `dispatch`, and `agent_loop` share verdict access (IF-175), `integrate` and `intake` share acceptance access (IF-091), and many writers share provenance (IF-194). Flow 4 expressly keeps post-merge intake inside the held slot; turning that handoff into an independently managed service could endanger the stated atomicity (**inference**), while a synchronous component call could preserve it. A stage cut would need to price those definitions and preserve that invariant. The evidence does not show that changing one shared representation necessarily touches every stage, so B4 is a risk to investigate, not a proved present defect.

### Missing questions that changed the answer

1. **What is architecture ownership here?** The bundle explicitly derives membership from LLR module references and permits overlap. The rubric assumes a component tree without saying whether a shared file has one implementation owner, multiple obligation allocations, or a declared kernel role. Add an ownership/allocation model before scoring boundaries; otherwise C2 could accidentally reassign CMP-006 responsibilities.
2. **Which invariants must survive a cut?** Flow 4's held merge slot, tree-attested bar, hook checks before claim, and one bookkeeping commit are architectural constraints. Add an invariant-preservation check for transaction scope, lock order, failure/retry ownership and durable effects. This is distinct from banning stage cuts or requiring sparse imports.
3. **What evidence is adequate for an audit versus a fresh design?** The rubric accepts generated code reports but wants change likelihood and dependency semantics those reports do not establish. Add an evidence checklist with explicit “not supplied/not assessable” outcomes. Missing full IF forms in a condensed bundle should not automatically become a verdict that the original contracts lack coverage.
4. **What is the cost of enforceability and migration?** A component label alone does not prevent new imports or side-channel reads. Add proposed access constraints and how boundary tests establish them. Require a migration/allocation plan when existing approved rows or tests would change, without demanding unnecessary file moves.
5. **What counts as one interface or one case?** C2 demonstrates that existing rows, new endpoint crossings, shared schema definitions and new semantic surfaces have different costs. Add separate counts and an explicit unknown remainder; never turn the 186 current rows or 290 imports into a case count.

These gaps can be handled by clarifying A4/A6/A7/A8 rather than immediately adding failure anchors. A new failure pattern for cuts that break a required transaction/failure invariant would be useful if future cases substantiate it; this bundle establishes the need to ask, not a current violating cut.
