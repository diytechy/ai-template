## 1. The three record states, and how the migrator tells them apart

The migrator reads the record before its first step, at both of its entry points (its command and `spellings_owed`, the report the vocabulary check calls), from files alone:

| State | Read from the record | What the run does |
|---|---|---|
| **A. Before the row-by-row write** | No act ledger, under either directory name, holds an `[[act]]` entry carrying the key `kept`. A ledger that does not parse reads as holding none. | Today's behaviour, unchanged (section 4). |
| **B. Row by row, current vocabulary** | An entry carries `kept` (an empty list included), and none of the earlier-vocabulary signals below is present. | The steps run; the record step writes no copy (section 2). |
| **C. Row by row, earlier vocabulary** | An entry carries `kept`, and at least one signal is present: (a) the earlier directory `docs/archive/last_approved/` exists; (b) an `[[act]]` entry in either ledger carries an earlier key (`approved`, `reattested`); (c) a registry copy under either directory name is one the registry step's own rewrite would change, or cannot prove (a copy that does not parse included). | Nothing runs and nothing is written; the run exits 1 (section 3). |

**Why these readings.** The row-by-row reading is the kit's own (M5), restated in the migrator because the migrator imports nothing from the kit (LLR-369's rationale: it must run while the kit's scripts cannot yet read the repository). A parity test holds the two readings together over the same ledger texts (section 6), so a change to the kit's reading reddens it. Signal (c) is the registry step's rewrite itself, run read-only over the record's copies, so the detection and the step that would write cannot disagree: in state B no copy owes a respelling by construction, and the registry step's walk of the record writes nothing.

**D3 holds.** Every earlier spelling the detection reads (the earlier directory name, the earlier ledger keys, the registry carriers' earlier fields and values) is one the migrator already holds as its own constants (`RECORD_DIRS`, `LEDGER_KEYS`, `FIELDS`, `VALUES`). No core module changes: the mirror judges (`acceptance_record`, `record_rows`) are untouched, and the vocabulary check receives the refusal through the existing IF-312 seam (`spellings_owed`), with no new reader. The key `kept` is current vocabulary, not an earlier spelling.

## 2. The skip (state B)

The record step runs as it already does for the vocabulary check's report (`record(root, check, copies=False)`): it writes no registry copy. Since state B means the directory and the ledger keys are already current, the step moves nothing and respells nothing, so it writes no record file at all. Consequences, each tested (section 6):

- A run for other files (a binding, a policy key, a work item) rewrites those and leaves every byte of the record as it was: kept rows keep their recorded text and pending drift stays pending.
- Check mode names no copy as owed: in a repository with nothing else stored in an earlier spelling it prints "nothing stored in an earlier spelling" and exits 0, kept rows and drifted rows present. On this repository that is the M1 run turning from exit 1 to exit 0.
- The commit holding the run's writes touches no record file, so the hook's registry-integrity step (the staged mirror check inside `trace.py --strict-integrity`) and the committed-history check have nothing of the record to judge and report nothing.
- D13's absorption is untouched in state A, where the operator ruled it; in state B nothing is absorbed, which is the ruling's refined (c).

## 3. The refusal (state C)

- **Where.** At the top of `main` and of `spellings_owed`, before the first step, so before the registry step's walk of the record (M4). Nothing is written before it, because the detection only reads.
- **Scope.** The whole run, not only the record's files (decision D3): no step runs, so no binding, live registry, policy file or record file is written. A run that respelled the live registries and left the record would put live and record in two vocabularies: a live row reading `Accepted` beside its recorded copy reading `Approved`, which the current scripts read as an acceptance the record does not hold.
- **Exit and modes.** Exit 1, in check mode too.
- **Message.** One line per file or directory holding an earlier spelling, then one naming the ledger that makes the record row by row, each printed as `migrate_vocabulary: acceptance record NOT rewritten: <line>`:
  - `docs/archive/last_approved: the record's earlier directory name`
  - `<ledger>: act entries keyed approved, reattested` (the keys found)
  - `<copy>: stores an earlier spelling` or `<copy>: <the carrier's own reason>` (for example "it does not parse (...)")
  - `<ledger>: an act entry lists the rows an act kept, so the record is judged row by row and nothing is written; the migrator rewrites a record only before its first row-by-row act (RESYNC_PACK.md, "An acceptance act records only the rows it names; a drifted row no longer blocks its registry"): restore the record to before that act, run the migrator, then take the act again`
- **The vocabulary check.** `spellings_owed` returns exactly those lines, prefixed `acceptance record cannot be rewritten: ` as its other problems are, and nothing else, so the check reports the refusal at its own severity and `--check` and the report stay worded alike (IF-312's "one line ... per file that cannot be rewritten safely"; every line names a path). IF-312 is not amended.
- **Coverage bound.** The promise reaches records the kit's own routes produced: acts through the snapshot command (its seed included) and the migrator's own earlier runs. The git-backed tests build the record each judges through those routes (M2, M3): the snapshot writer's seed and acts, and the migrator's own run over an earlier kit's record (modelled by the fixture the existing record tests already use, since no earlier kit is at hand to write one). A hand-edited copy, ledger or stamp is outside it; the in-process tests use hand-written fixtures only to drive each signal, not to extend the promise.

## 4. Pre-row-by-row records (state A)

Unchanged: the record moves from its earlier name, the ledger's keys are respelled, each copy is written equal to live and every absorbed accepted cell is named; both names present, or a ledger edit that cannot be proved, leaves the record untouched and fails the run. Every existing record test (`_record` with the `LEDGER` fixture, which carries no `kept`) keeps passing unchanged, and so does `test_old_kit_resync.py`, whose old-kit record carries none.

`rationale`:

> The kit's vocabulary was unified so that one word names one thing, and the core scripts hold no reader of an earlier spelling. A repository that still stores one would then read as if the value were absent, so a purpose-built migrator is the path from an earlier kit and the one place the earlier spellings are known. It rewrites whole values in known places and proves each rewrite by parsing the file again, because a migration that guessed inside prose, or changed a cell it was not asked to change, would alter a record nobody reviewed. Its record step writes each copy equal to live, absorbing the drift then pending and naming each accepted cell it absorbs, which a record judged as whole files accepts. Once the record's act ledger lists the rows an act kept, each later copy is judged at the row, and a copy written equal to live would carry a kept row's text into the record with no act. So the migrator then writes no copy, and a record that still stores an earlier spelling stops the run whole: respelling the live registries beside an unrespelled record would leave the two in different vocabularies, and the current scripts would read an accepted live row as an acceptance the record does not hold. The way out is the one the re-sync guidance gives, running the migrator before the record's first row-by-row act.
