## Notes

- **No clause excluded.** All of C1–C7 are covered above.
- **[B2] addressed in P3:** the revision splits C3 into its two degraded branches — pool-degraded (one family enabled) and runtime-degraded (two families routed, one nonresponsive at launch). P3 now owns both as an explicit fallback entry point plus tests for the runtime branch: the nonresponse signal is the typed session outcome the coordinator already captures on IF-041, threaded to `agent_route` after the existing `failure_action()` win-stay/lose-shift retries are exhausted, and the fallback's contract is two *fresh* same-family sessions with a recorded reason. P3 stays a pure selection/fallback library (no session launching), so its seams remain IF-044/IF-045; P6 owns the launch-and-feed-back loop, which its row now names. No new WI — the fix is a contract completion, not new scope.
- **Declared C7 split:** P1 owns the round-total-budget semantics (a cap in the state machine, exhaustion following `docs/gate-policy`); P6 owns per-session limit/telemetry inheritance, which it gets structurally by launching every hat session through the existing IF-041 session path rather than a new invocation route. Neither half is deliverable by the other row.
- **C4 boundary:** P4 is the sole owner of C4. P2's brief templates carry a coverage-report slot as part of their input allowlist (a C2 construction concern); producing and routing the report into that slot, and the bounce/page disposition, are P4's deliverable. This is a template-parameter relationship, not an artifact dependency, so no P4↔P2 edge exists.
- **Assumption — trigger declaration:** the dual-plan trigger rides an existing WI-registry field surfaced through the schedule library (IF-054/IF-055 read path), consistent with SR-058's fail-closed classification (a dual-plan WI never packs into a multi-WI traincar). If a new registry column proves necessary, its `check_trajectory` tolerance is inside P6's scope, not a separate WI.
- **Assumption — paging mechanics exist:** `agent_loop` already exposes typed NEEDS-HUMAN-style outcomes (IF-015); P1/P4/P6 map round failures onto that existing surface per `docs/gate-policy` rather than building a new paging channel.
- **Assumption — WI-190 deliverables are stable:** `plan_coverage.py` (SR-044, IF-057) and the `--prompt-map`/`AGENT_PROMPT_MAP` override exist as shipped; this plan extends, never re-implements, them.
- **Edge honesty:** P4→P1 exists because the adapter emits P1's typed step-outcome constants (a consumed artifact). P2, P3, and P5 are deliberately edge-free — P3's fallback entry takes the session outcome as a plain parameter, so it remains testable standalone — leaving P6 as the single integration fan-in.
