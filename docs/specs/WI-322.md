# WI-322 — Retire the aggregate open-items document for one generated view

**Status: queued**, and **gated on OI-10** — this spec builds whichever option
the owner rules; it does not pick one. The brief, the measured blast radius, the
options and the recommendation live in [open-items.md](../open-items.md)'s
`OI-10` section.

## How this got here

The owner opened the first re-attestation sitting, read the generated **Pending
owner actions** block, and could not act from it. Two things underneath, one a
design choice and one not:

1. **Four lines for six rows** — correct (the SR is the attestation unit, so a
   `Modified` LLR/TC rides its owning SR's line;
   `gen_trajectory._spine_pending`) but nothing on the line *says* so, and it
   reads as a projection that lost two rows.
2. **The line is a pointer, not a brief.** It names the command that produces
   the before/after — while this file's own header promises *"the context needed
   to rule"*. The depth that makes a re-attest readable is a **word-level
   diff**, and markdown cannot express one.

The owner's direction went further than the format: *retire `open-items.md`
entirely; a single HTML reference view is sufficient.*

## What this WI must not get wrong

`open-items.md` is **two things wearing one name** — a generated projection and
a set of hand-authored briefs. A generated view needs a source, so the build
must land the source decision first (OI-10) and only then the renderer. Building
the view over an unstated source is how the aggregate file grows back.

It is also a **shipped artifact**, so this is a kit version bump:
`OPEN_ITEMS.template.md` is a `bootstrap.py` MAPPING destination, 11 kit-doc
references describe it, 7 test modules assert it, one SR/LLR/TC row names it,
and `agent_dispatch.py` both treats it as a status-map marker and refreshes its
pending block every dispatch loop. Each of those is a migration step, not a
find-and-replace.

## Scope, once ruled

- **The source** ruled by OI-10 becomes the single home for brief prose; the
  rendered view is generated from it and never hand-edited.
- **The generator owns the surface** — regenerated by one command and
  freshness-gated by the harness `status-map` step, exactly as the pending block
  is today. The status-map marker in `agent_dispatch.py` moves with it.
- **The attestation-unit fact becomes visible:** a projected SR line states how
  many chain rows re-attest with it, and names them.
- **The word-level diff is the payload:** unchanged text collapsible, additions
  and deletions marked, both themes, a per-cell "how much moved" figure, and the
  **baseline revision printed on every section**.
- **No second source of truth.** The view derives from the same CSV comparison
  `trace.py --ratify` performs; if the two ever disagree, the brief is
  authoritative and the renderer is the defect.
- **The kit migration ships with it:** template, MAPPING, the 11 doc references,
  the test modules, the SR/LLR/TC rows, and a note in `ADOPTING.md` §6 telling an
  adopting repo what to do with the `docs/open-items.md` it already has.

## Hazard to carry into the build

The baseline is the whole ballgame. `--ratify modified` with no `--since`
returns an EMPTY section for a row amended while it still read `Verified`
(SR-052 and SR-053 today), and a bad `--since` fabricates one. A rendered view
inherits both failure modes and makes them prettier, so it must show the
baseline it diffed against and say plainly when a section is empty.

## Done-when

- [ ] Brief prose has exactly one home, per the OI-10 ruling.
- [ ] One generated view renders every pending decision **and** every `Modified`
      row — including the chain rows that ride an SR's line — with per-cell
      before/after.
- [ ] The baseline revision is stated on every section, and an empty section
      reads as *check the baseline*, never as *nothing changed*.
- [ ] `docs/status.md` points at the view in one place; the aggregate
      `docs/open-items.md` is gone from this repo **and** from the kit's
      scaffold surface, with `test_bootstrap.py`'s file lists and the kit
      contents in `README.md` updated to match.
- [ ] `ADOPTING.md` carries the migration note for a repo that already scaffolded
      the old file.
