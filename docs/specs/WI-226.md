## Stage 1 characterization (2026-07-18)

This is the behavior model for the extraction. It was read from
`agent_dispatch.dispatch_run` and checked against the dispatcher, train,
integration, recovery, migration, review, and dual-plan tests. The model is
descriptive: it does not add a state or change a policy.

### State carried by the loop

The coordinator state is the tuple below. A transition may update more than one
component, but the durable Git evidence remains authoritative after a crash.

| Component | Values / meaning |
|---|---|
| integration relation | absent cold start; equal; development strictly ahead; integration strictly ahead; diverged |
| active lanes | train ID to worker process, reserved WIs, base SHA, worktree, spine flag, open log handle |
| parked lanes | `resume`, `waiting`, `ready-to-integrate`, `blocked`, `train-end`, `integrated`, `blocked-done`, `needs-human`, `needs-re-review`, `rework`, `dual-paged`, or `quarantined` |
| excluded WIs | unreadable or unprovable reservation evidence, held out of the schedulable frontier for this run |
| controls | pause reason, blackout window, gate policy, worker ceiling, and pending human ask |
| frontier | registry rows at the integration ref, evaluated against reservations and exclusions, then packed into traincars |

### Phases and transitions

1. **Launch / preflight.** Parse jobs and the dual-prompt map, validate the
   agent command, acquire the single-coordinator lock, read declared policies,
   require a development branch, apply the migration ceiling, and reconcile the
   legacy compatibility window. Any parse, preflight, lock, or detached-HEAD
   failure exits `EXIT_PREFLIGHT` without dispatching.
2. **Integration-ref reconciliation.** A cold start creates the integration
   ref. Equal heads require no ref change. Development strictly ahead advances
   the integration ref by CAS. Integration strictly ahead resumes publication.
   Divergence records both heads and exits `EXIT_NEEDS_HUMAN`; neither history
   is rewritten.
3. **Durable-train reconstruction.** Reservation refs are grouped by train.
   Unreadable reservations are excluded. A train already marked done at the
   integration ref releases stale reservations and becomes `integrated`.
   Missing train branches or foreign WI claims quarantine only the affected
   ownership set. Otherwise branch evidence classifies the train as `blocked`,
   `ready-to-integrate`, or `resume`.
4. **Dynamic refill loop.** Every pass recomputes pause/blackout controls and
   the frontier from the integration ref. When dispatch is allowed, due
   `resume`/`waiting` lanes start before new reservations. New ordinary cars
   fill free lanes; a spine/protected car waits for all other lanes to drain and
   then runs alone. A dual-plan car runs synchronously and is never packed with
   another WI. `SELECTED` releases its reservation and republishes; `PAGE`
   either sets the human ask or releases and excludes the WI according to gate
   policy; an error quarantines it.
5. **Worker completion.** `EXIT_DONE` parks a train
   `ready-to-integrate` (and attended spine work raises the human ask).
   `EXIT_BLOCKED`/`EXIT_TRAIN_END` preserve built or blocked constituents but
   release unstarted ones. `EXIT_WAITING` records a retry deadline.
   `EXIT_NEEDS_HUMAN` raises the human ask. Any other exit quarantines the
   train. Each exit triggers a fresh pass.
6. **Serialized integration.** In sorted train-ID order, only
   `ready-to-integrate` and `blocked` lanes enter their respective disposition
   transaction. A human ask gates both. `integrated` becomes `integrated` or
   `blocked-done`; `recompose` forces a rescan; every other result is parked and
   journaled. Any integration-ref movement is followed by a publication
   attempt and a fresh frontier scan.
7. **Idle and terminal decisions.** With no active lane: pause exits
   `EXIT_PAUSED`; a human ask exits `EXIT_NEEDS_HUMAN`; blackout plus available
   work waits; only rate-limited lanes exit `EXIT_WAITING`; no dispatchable or
   waiting lane drains the loop. Final attention states exit `EXIT_STALL`;
   queued work or deferred publication remains `RUNNING` and exits
   `EXIT_DONE`; blocked registry rows produce `BLOCKED`/`EXIT_BLOCKED`; the
   fully drained case produces `DONE`/`EXIT_DONE`.

### Effect points and crash authority

| Effect family | Operations in `dispatch_run` or its existing seam | Durable authority / recovery rule |
|---|---|---|
| Git refs | create/CAS integration ref, reserve/release WI refs, create/read train refs, publish development ref | refs plus registry rows at the integration ref; CAS failure never overwrites a concurrent head |
| worktrees | lease train worktrees; publication syncs the selected checkout | train branch and reservation evidence reconstruct state if `out/dispatch` is deleted |
| sessions | `subprocess.Popen` worker; synchronous dual-plan round; poll and close log | worker commits/trailers and train branch evidence, not the process table |
| journal | append reason-coded events, train snapshots, manifest, telemetry, and worker logs | diagnostic evidence only; deletion must not prevent reconstruction |
| run-state | write `docs/run-state` and render the marker-gated stop banner | generated terminal projection; never the integration authority |

The recovery tests exercise faults after reservation creation, immediately
before and after integration CAS, after publication intent, and between
development CAS and worktree sync. The integration tests cover dirty-checkout
deferral and divergent/non-descendant refusal. Dispatcher/train tests cover
dynamic refill, genuine overlap, spine serialization, attended ratification,
pause, migration exclusion, early train end, and join-from-integration-head.
Dual-plan tests cover SELECT and both attended/autonomous PAGE paths.

### Stage 2 extraction contract and measurable target

The pure boundaries will decide: integration-head relationship action,
reconstructed-train classification, dispatch permission and retry eligibility,
worker-exit disposition, integration candidate/result disposition, idle-loop
action, and terminal run-state. They receive values and return values only;
Git, filesystem, subprocess, clock/sleep, journal, console, and run-state effects
remain in orchestration/effect seams.

The committed WI-225 starting census is `dispatch_run = 84` with 52 over-limit
functions repo-wide. Stage 2 must reduce `dispatch_run` to **40 or less**, add no
new function above the pinned threshold 10, and re-stamp the exact census
downward. Stage 3 is a test-only boundary split: it must preserve that reduced
census while moving direct decision tests out of end-to-end effect modules.
