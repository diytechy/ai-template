# WI-110 — Effort-level selection for agent sessions

**Status: EXECUTED 2026-07-14** (the static-pin half). Filed deferred
2026-07-12 at the WI-109 sitting; **re-queued 2026-07-14** by owner directive
(intake item 2, [owner-intake-2026-07-14.md](owner-intake-2026-07-14.md)):
"Opus implementation should be set to extra high." The deferral's "wait for
evidence" is superseded by the explicit ruling for the OPUS static pin; the
per-phase effort map and computed selection **remain deferred** (see below).

## What shipped (WI-110, this session)

1. **OPUS → `xhigh`.** The `ANTHROPIC-OPUS` row in
   [`docs/agents.csv`](../agents.csv) pins `CLAUDE_CODE_EFFORT_LEVEL=xhigh`
   (was `high`) via its `Env` cell — one cell. The env route (not the `--effort`
   flag) was already chosen at WI-109 because an unread env var is a no-op on
   older CLIs while an unknown flag fails the session; `xhigh` composes the same
   way. FABLE/SONNET stay `high`. The value reaches the session because
   `agent_route.parse_env` merges the `Env` cell over the launch environment,
   and the WI-124 telemetry (`agent_loop`) reads `CLAUDE_CODE_EFFORT_LEVEL` back
   into the log header's `effort` field — so every OPUS BUILD row now records
   `effort=xhigh`.

2. **The default question, resolved.** WI-109 recorded `high` as the Opus 4.8
   default; the owner-intake draft called `xhigh` the default — a contradiction
   this WI had to settle. Live check (claude CLI 2.1.201, this repo's driver
   env): with no explicit pin the ambient `CLAUDE_CODE_EFFORT_LEVEL` resolves to
   **`high`**, so `xhigh` is a genuine dial-up above the default, not a no-op.
   `xhigh` is a valid live level (the owner's global `~/.claude/settings.json`
   already carries `"effortLevel": "xhigh"`; the ladder is
   `low/medium/high/xhigh/max`, `xhigh` between `high` and `max`).

3. **Before/after evidence (WI-124 s/turn telemetry).** *Before* baseline (OPUS
   at `high`, from the WI-124 log): opus iteration reviews **15.5 / 11.6 s/turn**
   at ~high-context volumes. *After* is captured automatically going forward —
   the next OPUS BUILD/review session logs `effort=xhigh` with its own `s/turn`
   and `Ctx/turn`, so the delta is read from `iteration_index.md`, not guessed.
   This WI arms the measurement; it does not fabricate an "after" number it did
   not run. (A dedicated gate-bearing `xhigh` vs `high` A/B is available if the
   telemetry shows the pace delta is worth a controlled session.)

4. **OpenAI effort — answered.** Yes, OpenAI exposes reasoning effort. Live
   check (opencode 1.17.18): `opencode run --variant <level>` — "model variant
   (provider-specific reasoning effort, e.g., high, max, minimal)". So it is a
   **CLI flag** (correcting the intake draft's "config-file-only, needs an
   `opencode.json`" guess), which would go in the OPENAI rows' `CmdTemplate`
   (`--variant …`), **not** an `Env` cell. Left **unwired** this WI: the review
   legs are gate-bearing and "route hard work up" would favor a dial-up, but the
   WI-124 s/turn telemetry is claude-JSON-specific, so an OpenAI effort change
   can't be measured before/after the way the OPUS one can. Wiring it is a
   follow-up gated on opencode telemetry parity, not this owner directive.

## Still deferred (un-defer triggers unchanged)

The owner ratified the **static OPUS pin only**. These stay future work:

2. **Per-phase effort map** — an `AGENT_EFFORT_MAP`/`--effort-map` sibling of
   `AGENT_TIER_MAP` (PROCESS_OPTIONS "Per-phase effort", WI-049). Natural shape:
   effort as a per-phase declared value merged into the row `Env` at launch, so
   it composes with the pair-row model without a schema change. Un-defer when
   iteration logs show phase-effort variance a single static pin can't serve.

3. **Computed selection (speculative)** — derive effort from session signals
   (gate-bearing vs docs-only WI, spec size, retry/escalation state — e.g. a
   lose-shift retry runs `xhigh`). Do not build until the logs show variance a
   static map can't serve.

## Un-defer when (for #2/#3)

- iteration logs show sessions failing in ways plausibly effort-bound
  (fabrication at low reasoning depth, stalls on hard refactors), or
- a second provider's knob (opencode `--variant`) is worth unifying behind one
  map with telemetry parity to measure it.
