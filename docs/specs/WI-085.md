# WI-085 — Process reference view in `PROJECT_STATE.html`

**Status: queued** (filed 2026-07-12; re-entered at G1 under the derived-gate
model 2026-07-12 — its SR is **SR-050** (`Phase=v2`), drafted in the live spine
by the `[v2]-[g1]` batch (WI-116); dev runs after `[v2]-[g2]` (WI-117), and the
owner's batch ratification is queued per `single-ratify`).

## Goal

A new dashboard tab beside What / When / How-SW / How-physical / Knowledge that
explains *how this project is built* as a visual reference: at what point each
artifact is created, how the agent-resume loop runs, and how per-WI slices build
into campaigns and gate checks.

## Content — three linked panels, one tab

1. **Artifact lifecycle × gates** — Vision → SN (G1) → SR (G1→G2) → LLR +
   architecture (G2) → TC (G2→G3) → code+tests (G3) → G-Release, each stage
   linking to its `PROCESS.md` section and this project's live tier count.
2. **The resume loop** — the high-level `agent_loop.py` managed-mode flow: read
   status → PLAN → BUILD → REVIEW-A/B → (CRITIQUE) → INTEGRATE → commit →
   hook/gate → repeat, with the DESIGN-CHECK / page-human escalation edges.
3. **Slices → campaigns → gates** — a per-WI slice ends at the **commit bar**; a
   campaign closes at the **gate bar** (`check.py --gate`); CI runs it every push.

## Owner rulings (2026-07-12)

- **A new SR is required.** This is a genuinely new dashboard facet (a
  process/method view, not project *state*), so mint a new SR under
  `SN-021`/`SN-010` (the single-artifact family) at implementation — it rides
  the re-attestation.
- **Duplication is bounded, but may be necessary *within the view*.** SSOT by
  linking-out is preferred, but the *relationships this view draws* (lifecycle
  ordering ↔ gates ↔ loop ↔ campaigns) are not cleanly stated in one single
  place elsewhere, so a bounded restatement **inside the view only** is
  acceptable where no single doc already expresses the relationship. Link where a
  canonical home exists; restate-in-view only where one does not.
- **Generated is the ideal; static-authored is the tenable fallback.** Prefer a
  data-derived render (current gate from `docs/gate`, tier counts from the spine,
  campaigns from `work-items.csv`). If the relationships resist clean generation,
  a hand-authored diagram is acceptable — with the verification consequence below.

## Verification — the TC depends on generated vs. static

- **If generated (data-derived):** a normal **Test** TC — byte-deterministic
  render, `--check`-stable, links resolve, the current-gate highlight reflects
  `docs/gate`, counts match the registries (the WI-070 Knowledge-tab test shape).
- **If NOT generated (static authored diagram):** a **Critique** TC — an
  independent agent verifies that the rendered diagram elements actually follow
  the process this project follows (fidelity to `PROCESS.md` + the real loop),
  since no data join proves it. This is exactly the `Critique` verification value
  (WI-068): a code-produced artifact whose *faithfulness* is a subjective
  judgment against the SN/SR intent + `PROCESS.md`, adjudicated against a rubric.

## Implementation shape

- New `process_panel()` in `gen_trajectory.py` + a tab registered in `build_html`
  (the WI-070 Knowledge-tab pattern: nav button + `<section id="process">`),
  reusing `_layered_layout()` where a panel has ranked nodes.
- Fully self-contained conditional panel (inline style/script/data) so a
  bundle-/data-less repo renders byte-identically; sorted inputs, no clocks (the
  git as-of stamp is already excluded from `--check`).
