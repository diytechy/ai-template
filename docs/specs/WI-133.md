# WI-133 — Dev-slice batching: a `;`-joined `docs/next-wi` batch, one session, one review

**Owner-directed 2026-07-13** (the session-economics question): attended
sessions naturally close several WIs in one context, but the unattended loop
runs **one WI per session** — per spin-up that's a full context re-upload plus
a per-slice review round, paid even for trivial off-spine slices. The
constraint is **convention, not mechanics**: the loop already reviews a
session's *whole commit range* (`impl_range = commits`, one REVIEW round per
committing BUILD session), and pre-dev work already batches via the
`[phase]-[g*]` archetype (WI-093, demonstrated by WI-116/WI-117). Only the
G2→G3 dev slices lack a batching form. This WI extends the existing batch
concept to the cheap dev tail — **without touching the review dial** (that's
WI-123 / OI-7, deliberately separate).

## Design

**Syntax.** `docs/next-wi`'s value line may carry a **`;`-joined ordered
batch** of WI ids (`WI-098;WI-103`) — the registry's `;`-join convention,
still one value on the last line (the `run-phase` idiom unchanged).

**Semantics.** One BUILD session executes the batch **in order**, committing
per WI (logical commits, the session-protocol rule); the loop's existing
session-range review means the batch takes **one review round**, amortizing
the spin-up. A single id stays **byte-identical** to WI-126.

**Eligibility (advisory, never enforced).** A batch should hold only
**independent, off-spine** dev slices: each member queued, **empty
`SR-Refs`**, **no hard edge between members**. The coordinator prints one
`dev-batch advisory` line per violation (a spine-touching member; a member
hard-depending on another member) and proceeds — LOUD, never fatal, matching
the WI-126 pin's failure style. Spine-touching slices stay strictly per-slice
("series for dev" keeps its rationale: a bounded single-WI diff is where the
per-slice reviewer earns most).

**Tier pin composition.** With a batch, the `BuildTier` pin becomes the
**strongest** member pin (route up, never down — the loop's standing ethos);
members without a row or with an empty/invalid `BuildTier` contribute no pin
(invalid/unknown ones are named in the loud line). The escalation override
(tier-up-never-down) still wins after the pin, exactly as for a single id.

**No new SR** — same class and precedent as WI-126/WI-129 (routing
convenience + advisory warns, non-gating). No loop-dispatch change (the
one-review-per-session behavior is pre-existing); no `review-policy` change.

## Slices (one WI)

1. `agent_loop.py`: `_next_wi_ids()` parse; `build_tier_pin()` batch-aware
   (single-id paths byte-identical, exact legacy strings); new
   `batch_advisories()`; the BUILD route branch prints the advisories.
2. Docs, single-homed: PROCESS_OPTIONS "Unattended operation" (the WI-126
   bullet gains the batching block) + one cross-ref sentence at "Parallel for
   pre-dev, series for dev"; the meta launchers' `AGENT_PROMPT` next-wi
   phrase; the `session-protocol` skill's maintain-next-wi line (source +
   byte-identical fan-outs); the meta `docs/next-wi` header comment.
3. Tests (`test_agent_loop_review.py`): batch pin routes strongest; unknown
   member named but the batch still pins; advisories fire (spine member +
   intra-batch hard edge) and never block; single-id tests unchanged.
