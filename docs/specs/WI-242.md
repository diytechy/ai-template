# WI-242 — Dogfood-sync: adopt the template registry columns + pin the structural surfaces

**Branch:** dualplan-routing-fix · **Filed:** 2026-07-19 (owner question:
"do we need to dogfood the template functions so this repo can't drift from
its own template?") · **BuildTier:** medium · **SafetyClass:** high-risk
(registry schema migration + harness gate).

## Why

The kit's own repo has drifted structurally from what it ships. Quantified
2026-07-19: `work-items.template.csv` carries 17 columns; the live
`docs/requirements/work-items.csv` carries 10 — missing `CritiqueBudget`,
`CritiqueExhaustion`, `Priority`, `Exclusive`, `BlockRef`, `EstTokens`,
`PlanMode`. Each absence has a consequence: BlockRef cost three broken runs
(the WI-229 blocked-exit loop, cured by WI-238's adopt-on-demand); PlanMode
makes dual-plan undeclarable here; Priority/Exclusive silently degrade
scheduling to defaults. Beyond the registry, the root launchers
(`agent-resume.{cmd,command,sh}`) and dev-setup scripts
(`scripts/dev-setup.{cmd,command,ps1,sh}`) are template COPIES that can
drift structurally (the WI-217 `{prompt}` episode). The Python engine
itself cannot drift — one `agent_loop.py`, invoked directly by the
launchers — and the skills surface is already sync-gated
(`gen_skills_index --check-agents`). The rule this WI enforces:
**values may diverge (owner dials, filled rows, enabled sets); structure
must not (schema headers, command contracts, declared-section shapes).**

## Scope

1. **One-time registry migration:** extend the live `work-items.csv` header
   to the template's full 17 columns, in template order. Existing rows stay
   width-stable (the WI-238 ragged-row pattern — every consumer is a
   DictReader reading an absent/empty cell identically); no row VALUES
   change. Must be behavior-neutral: an empty new cell must mean exactly
   what the absent column meant (verify each consumer: schedule's
   Priority/Exclusive, plan_runner's PlanMode, the critique dials,
   blocked-row BlockRef validation on non-blocked rows).
2. **The `dogfood-sync` structural check** — a test (suite = harness via
   tests+coverage) asserting, for THIS repo:
   - each live registry's header is a prefix-ordered superset match of its
     template's header (start with work-items; include the other
     registries whose templates declare headers — census them);
   - each root launcher/dev-setup copy structurally matches its template:
     the engine-invocation line, the exported-variable set, and the
     AGENT_CMD/stdin contract shape — explicitly NOT the owner-dial VALUES
     (AGENT_TIER_MAP/AGENT_PREFER_MAP/AGENT_JOBS values may differ; their
     PRESENCE/export must match);
   - live `docs/stack.ini` declares every SECTION the template declares
     (keys/values free to differ).
   Failures name the drifted surface and the template line. Skills stay
   with their existing gate (no duplication).
3. Record the structure-vs-values rule where the working agreement lives
   (one sentence in CLAUDE.md's principles or the session-protocol skill —
   whichever already discusses dogfooding; smallest single-source edit).

**Non-goals:** no downstream resync changes (ADOPTING §6 owns adopter
copies); no auto-sync writers (the check FAILS, a human/WI syncs); no
launcher value harmonization; no PROCESS.md changes.

## Done-when

The live registry carries the 17 template columns with all pre-existing
rows byte-stable except the header; a scheduler/plan/critique behavior-
neutrality regression proves empty-cell == absent-column for every consumer
the new columns feed; the dogfood-sync test fails on (a) a removed live
column, (b) a launcher engine-line edit, (c) a template section the live
stack.ini lacks — each proven by temporary mutation — and passes on the
migrated repo; the rule sentence is placed; complete G3 harness green.
