# WI-1006 — A ruled open item has action planned, done or handed on (spec of record)

**WI:** WI-1006 · **Status:** queued · **Delivers:** SR-148, through a new design row, LLR-370 (settled at the scope critique, 2026-11-19)

Filed on the owner's request, 2026-11-15. The row keeps its Context and
Done-when, which stay the one home of what closes it.

## Why

Ruling an open item takes it off `open-items.html`. What the ruling asked for
then lives only in the work items that cite it, and nothing checks that any
do. An item can be ruled and its action never planned, and every check keeps
passing. The ruling sync (WI-790) holds only the ruling's own commit: it makes
that commit rewrite the Done-when of each open row whose `needs` cited the
item. A ruling with no citing row, or one whose follow-on work was filed
later as another open item, is never judged.

## Why text and not `needs`

In practice the ruling's commit drops the item from the citing row's `needs`
(OI-129's ruling, `0032ffdd8`: "both rows drop their needs on the item"). The
link that survives is the item's id in the row's text, because the
registry header asks the new Done-when to cite the item. So the check matches
`OI-<n>` (leading zeros ignored) in work-item spec text, not edges.

## The rule

A `ruled` item is **covered** when any of these holds:

1. A work item under an open status directory (draft, queued, active,
   deferred) or under `complete/` names it. Cancelled, partial and
   restructured rows do not count.
2. Another open item names it in any cell but the historical `wi_refs`, and
   that item is `pending`, or is `ruled` and itself covered. Follow the chain,
   and treat a cycle with no covered member as uncovered.
3. Its `follow_up` cell is set. The cell says what carried the ruling out
   when no work item did, such as a commit or a log entry. Where the ruling
   asked for no change, it reads `follow_up = "none — <why>"`, the same
   "none — why" form the log fragments' `Deferred open items:` line already
   uses.

Anything else is a finding, warn-only, naming the item and its title.

### What is matched, exactly

Closed at the scope critique (finding S3):

- **The token.** `OI-` and a run of digits, read as a number, so leading
  zeros are ignored. No letter, digit or underscore may come before it and no
  digit after it: `(?<![A-Za-z0-9_])OI-0*(\d+)(?![0-9])`, the same boundary
  `trace.py`'s ruling-name match uses. So `OI-035` names OI-35, while
  `OI-350` and `XOI-35` do not. Case counts: a lower-case log anchor such as
  `#oi-35` is not a mention.
- **A work item's text.** The whole file of each `WI-*.md` under a status
  directory of `docs/work/` or `docs/archive/work/`, front matter and body.
  The status is the directory, as the registry reader reads it, and a file in
  any other directory counts for nothing. The `specref` target is not read.
  The ruling sync asks the citing row's own Done-when to cite the item, and a
  spec of record shared by several rows would otherwise cover for each of
  them. The `-000` example row counts for nothing.
- **An open item's text.** Every cell of the row except its id and the
  historical `wi_refs`, so a `follow_up` cell counts too. An item that names
  itself does not cover itself.
- **Statuses.** A status is trimmed and compared in lower case, as every
  open-items reader compares it. Only a `ruled` item is judged. As a citer, a
  `pending` item covers, a `ruled` item covers when it is itself covered, and
  any other status covers nothing. A light-spine repository's `implemented`
  closes its own item; what it should mean for the items it names is WI-1012's
  to settle.
- **"Later".** The row's "a later open item" describes the usual case. The
  rule compares neither ids nor dates, which is why two ruled items can name
  each other. Such a cycle is covered only when one of its members is covered
  some other way.
- **`follow_up`.** Set when its text is not blank after trimming. The carrier
  already refuses an explicit empty string, and a cell of spaces reads as
  unset.
- **`-000` rows** of the open-items registry are never judged and never
  cover anything.
- **No registry** is vacuous: the report says so and exits 0. **A registry
  that does not parse** stops the report with the carrier's refusal and a
  nonzero exit, as every open-items reader stops. That refusal is not a
  finding, and it is the one way the report moves the audit's exit code.

## Measured with a prototype

At `7fa851f33`, over this repo's 115 `ruled` items:

| Reading | Items |
|---|---:|
| a complete row names it | 91 |
| an open row names it | 15 |
| handed on through a later open item | 5 |
| uncovered | 4 |

The four uncovered items are OI-35 (carried out in its own ruling commit),
OI-79 (its only link is the historical `wi_refs` cell, naming WI-569), and
OI-89 and OI-90 (each confirmed things as they were). None needs work, which
is the case `follow_up` exists for.

## Bounds

- A text match counts any mention as cover, so 91 is an upper bound on rows
  that actually carried out a ruling. Whether a row does what the ruling said
  stays a reviewer's question.
- Rule 2 cannot tell a real follow-up from a later item that only mentions an
  earlier one. No `ruling_ref` names another item today (0 of 94), so the
  template's ask that a follow-up name its predecessor is what keeps rule 2
  honest.
- Reading rules 1 and 2 together with the open rows also gives an "answered,
  not yet applied" list. Rendering it is out of this row's scope.
- This row's own Done-when names the four items, so under rule 1 this row
  covers them while it is open and after it closes. The four are therefore
  judged with this row's file set aside. Each gains a `follow_up` cell only
  where a commit, a work item or a log entry shows what carried its ruling
  out.

## Architectural delta

Settled at the scope critique (finding S5):

- **The anchor:** SR-148 (Accepted). Its two design rows on operator
  decisions already sit there: LLR-298 (the ruling sync) and LLR-299 (pending
  citation integrity). SR-148's derivation reads only the tracked registries,
  so a ruling whose action no work item or open item carries is work it can
  never select. A new design row, LLR-370 (Drafted), states the check. Its
  test cases are TC-430 and TC-431 (Drafted). No SR is minted. WI-790 recorded
  that no SR states the coupling between operator decisions and the work that
  cites them, and this row leaves that gap where it was.
- **The contract:** IF-073, the open-items registry format, gains the
  optional `follow_up` cell and the cover rule, in its row of record and in
  the registry's `Contract IF-073:` header. No other interface moves.
- **The modules**, each already a reader of the registry:
  - `kitlib/spine.py` holds the token and the rule, a pure function over
    rows, beside `open_item_queue`;
  - `pending.py` does the read: the registry through `spine_carrier`
    (IF-073's carrier) and the work-item text through `kitlib.registry`
    (IF-023's reader), beside its own open-items queue projection;
  - `gen_open_items.py --ruled-cover` prints the report, warn-only, and exits
    0.

  Each import already exists, so no seam is added and no interface row is
  minted.
- **Shipping:** the three modules and the open-items template ship, so the
  RESYNC entry is owed: a new optional key, nothing forced. This repository's
  `docs/stack.ini` `[run] audit` (IF-049) runs the report before the smoke
  budget. The shipped `stack.ini.template` declares no audit action, so an
  adopter adds the line to its own menu if it wants the report.
- **Unchanged:** no flow, component or boundary. `docs/open-items.html` does
  not render the report.

## Interfaces

Reads the open-items registry through `spine_carrier` (IF-073's carrier) and
the work-item registry through `kitlib.registry` (IF-023). It adds a step to
the `[run] audit` line of `docs/stack.ini` (IF-048/IF-049). No new seam.
