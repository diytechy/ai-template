# WI-227 — Run-menu trailing arguments: decide the contract, then quote it (repo-review-2026-07-18 M-06)

**Branch:** dualplan-routing-fix · **Filed:** 2026-07-18 (review M-06) ·
**BuildTier:** medium · **SafetyClass:** ordinary (launcher convenience
layer; not the dispatcher).

## Why

`run_menu.py:116` concatenates trailing user arguments into a shell command
string unquoted. An argument containing spaces or shell metacharacters
splits or executes differently than the user intended, and Windows
(`cmd.exe`) vs POSIX quoting rules differ, so a naive quoting patch is
unsafe without deciding what the contract *is*. The review deliberately left
this unfixed pending that decision (§0 table).

## Scope

1. **Decide the contract** (recorded in this spec as a ruling section,
   WI-223-style): either trailing arguments are a **trusted shell fragment**
   (documented as such — the user owns quoting; the kit passes it through
   verbatim on both platforms) or they are **data arguments** (the kit
   appends them as argv items with per-platform quoting, never re-parsed by
   a shell). The recommendation is data-arguments: menu entries are the
   trusted recipes; user-supplied trailing args are values.
2. **Implement** the ruled semantics explicitly — argv-append or documented
   passthrough — with tests covering spaces, quotes, and `&`/`|`
   metacharacters on both Windows and POSIX (skip-guarded like the suite's
   existing shell-dependent tests).

**Non-goals:** no menu-format redesign; no change to how the menu's own
recipe lines execute.

## Ruling — data arguments (2026-07-18)

Option (2) is ratified: **trailing arguments are data values, not shell text.**
The declared `[run]` recipe stays the trusted shell line (`shell=True`, pipes,
`&&`, redirects — unchanged); each trailing arg the launcher forwards
(`run_menu.py <name> arg…`, the old `exec $RUN_CMD "$@"`) is appended *quoted for
the platform shell* so it reaches the program as exactly one literal token —
never re-split on whitespace and never re-parsed as a shell operator. POSIX uses
`shlex.quote`; Windows wraps each token in double quotes with the
cmd.exe/MSVCRT backslash-quote escaping, which makes separators and redirects
(`&` `|` `<` `>` `(` `)` `^`) inside the quotes literal.

Data-arguments is right because the menu recipe is the trusted recipe and the
launcher's `"$@"` is a value an evaluator types (a path with spaces, a filter
containing `&`); a value must not silently become part of the command grammar.
Passthrough-verbatim would instead make every trailing arg a shell injection the
user has to hand-quote differently per platform — the exact cross-platform trap
the review flagged.

Two Windows-only residual limits remain, rooted in cmd.exe's own parser rather
than fixable by more escaping, and are therefore **documented, not fought**
(SafetyClass is ordinary — a convenience layer): (a) a `%VAR%` in a value is
still expanded, because a single `cmd /c` command string cannot suppress cmd.exe
environment expansion; (b) a literal double quote *combined with* a separator in
one value can re-expose that separator, the known cmd.exe-vs-MSVCRT quote-state
disagreement. POSIX (`shlex.quote`) has neither — it neutralizes `$`, backticks,
and every metacharacter totally. Both limits are recorded in the `run_menu.py`
module docstring, the home an adopter reads.

**Non-goals (ruling):** no attempt at a perfect cmd.exe universal-quoter; no
change to how the recipe lines themselves execute.

## Done-when

regression tests proven failing pre-fix under the ruled semantics; smoke bar
green per commit, full suite at close.
