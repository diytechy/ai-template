# WI-274 — dev-setup stale-venv recovery + single-home coordinator dials

**WI:** WI-274 · **Status:** queued · **Delivers:** SR-032 (part A), SR-026 (part B)

Two dev-environment ergonomics gaps, filed together (owner directive
2026-07-23): both are "the declared value lives in the wrong number of places"
problems surfaced by the same day's hands-on work.

## Part A — dev-setup cannot recover a stale `.venv`

### Problem

`scripts/dev-setup.{ps1,sh}` cannot bring an existing sub-3.11 `.venv` to the
Python 3.11 floor the repo now declares (WI-262/WI-270) — the environment the
declared test command actually runs through. Three verified gaps
(meta-repo dev box, 2026-07-23: `.venv` = Python **3.8.10**, Python **3.12**
installed and listed by `py -0p`):

1. **No recovery path.** `-Install`/`--install` fail closed on a sub-3.11
   `.venv`: *"move or remove that environment, then rerun"*
   (`scripts/dev-setup.ps1` ~line 135, `scripts/dev-setup.sh` ~line 150).
   Consent-first is right, but no *consented* recreate is ever offered — manual
   deletion is the only way forward.
2. **`-Check` never names the stale venv.** `$venvSupported` (ps1) / the `PY`
   probe (sh) silently fall back to the ambient interpreter; the report
   describes *that* environment with no line saying `.venv` exists but is below
   the floor. The one signal a contributor gets is misleading
   (`[missing] runtime (python) — install Python 3.11+`).
3. **Discovery is shadowed by the stale venv itself.** The candidate list
   (`py`, `python`, `python3`) never tries version-pinned forms, so when the
   stale venv is active / first on PATH (VS Code auto-activation — exactly
   where a contributor runs dev-setup), **every** candidate resolves to the
   venv's 3.8 and `-Install` dies with *"Python 3.11+ not found on PATH"* even
   though 3.12 is installed (`py -3.12` works). Verified live.

Net: SR-032's AC ("the scaffolded onboard/dev-setup scripts run to a green
setup") is unmet whenever a pre-floor `.venv` exists. The kit-shipped
`project-trajectory/scripts/setup.{ps1,sh}` carry the same fail-closed
"move or remove" pattern (setup.ps1:37 / setup.sh:29) — whether the fix ships
downstream is a **deliberate decision in this WI** (downstream migration
surface; flag, don't silently drift — `tests/test_dogfood_sync.py`).

### Approach

Smallest change preserving the consent-first posture, in both scripts
(behavior parity, per-script idiom):

- **(a) Consented recreate.** On `-Install`/`--install` with a sub-3.11
  `.venv`: offer `Recreate ./.venv with <interpreter> (Python <ver>)? [y/N]` —
  on yes, remove the old venv, `venv` afresh with the discovered 3.11+
  interpreter, then the pinned `requirements-dev.txt` install (same path as
  the fresh-create branch). Decline keeps today's fail-closed message and
  exit 1. Non-interactive `read` failure declines gracefully (the existing
  `offer_cli` pattern).
- **(b) Explicit stale report.** `-Check`/`--check` emit a dedicated line when
  `.venv` exists below the floor (e.g. `[stale] .venv is Python 3.8.10 —
  below the 3.11 floor; rerun -Install to recreate it`) instead of silently
  describing the ambient interpreter.
- **(c) Version-pinned discovery.** Append pinned candidates after the bare
  ones: Windows `py -3.13`/`py -3.12`/`py -3.11` (each still floor-checked);
  POSIX `python3.13`/`python3.12`/`python3.11`. A stale venv on PATH can then
  never hide an installed 3.11+ from the recreate offer.
- **Tests** in `tests/test_onboard_devsetup.py`, following its existing
  patterns (the 3.11-floor text assertion is already there): recreate offer
  present in both scripts, stale-venv report line present, pinned candidates
  probed, decline path stays fail-closed.
- **Downstream call:** decide + record whether `setup.{ps1,sh}` (scaffold-time,
  where a pre-existing `.venv` is far rarer) get the same offer; default
  conservative — meta-repo `dev-setup` only, with the decision noted in the
  close deliverable.

## Part B — coordinator dials declared once, not per launcher

### Problem

`AGENT_JOBS`, the fallback `AGENT_MODEL`/`AGENT_MODEL_MAP`, and the
`AGENT_CMD*` templates are declared as env slots in **each** launcher:
`agent-resume.cmd`, `agent-resume.sh`, and (`AGENT_JOBS` only)
`agent-resume.command`. A one-dial owner change therefore edits the same value
in up to three files — the 2026-07-22 dial turn (Fable→Opus strong + serial
default) touched exactly this surface. The duplication is *not* inherent: the
per-platform launchers must exist (cmd can't source sh; double-click entry
points), but the **values** live there only because env slots were the original
config mechanism. The repo has already escaped this twice:

- model **routing** moved to `docs/agents.csv` + `docs/agents-enabled` (the
  env maps are now the declared legacy *fallback*);
- the `run.*` launchers are thin because `run_menu.py` reads
  `docs/stack.ini [run]` (IF-048/IF-049);
- `subagent_gate` reads a declared file **with a launcher env override**
  (IF-038) — the precedence pattern part B needs.

### Approach

Let the destination read the dials: `agent_loop.py` (or `agent_common`, where
the declared-surface reads already live — IF-065) reads a declared config
section at boot — **IF-068 (Proposed**, filed with this WI**)** — with
precedence **CLI flag > `AGENT_*` env > declared file > built-in default**.
The env slots keep working (nothing breaks, the L-22 inherited-value fix stays
honored); the launchers shrink to platform plumbing (consent banner, `cd`,
exec) plus a comment pointing at the declared home; the `.command` `AGENT_JOBS`
slot can drop entirely.

Design calls left to the build session (recorded in IF-068's notes):

- **Home:** an `[agent-loop]` section in the existing `docs/stack.ini` (one
  declared-config home, IF-049 precedent) vs a sibling declared file next to
  `docs/agents-enabled`. Lean stack.ini — one fewer file, same parser.
- **Scope of migration:** move `AGENT_JOBS` + the fallback model dials first;
  the `AGENT_CMD*` templates may stay launcher-side (they are genuinely
  per-platform strings).
- **Downstream disposition (decided; 002-REVIEW-A rework):** `agent_loop.py`
  ships the *capability* — it reads `docs/stack.ini [agent-loop]` with the IF-068
  precedence, so any downstream repo can adopt the single home the moment it wants
  one. The launcher-**template** migration is **deliberately DEFERRED**: the three
  `agent-resume.template.*` launchers keep their `AGENT_*` dial slots
  (`AGENT_JOBS="${AGENT_JOBS:-2}"` etc.) as the fresh-adopter dial home.
  *Rationale* — a fresh scaffold ships *placeholder* dials it fills once and
  rarely turns, so the three-file-edit pain the single home removes is a
  heavy-dial-turner's problem (this meta-repo's), not a fresh adopter's;
  migrating would relocate the load-bearing "parallel-by-default at two workers"
  guidance off the file a double-clicking user actually opens, for no
  fresh-scaffold benefit — and IF-068 is fail-soft, so nothing breaks either way.
  *Migration guidance is shipped in-place*: `stack.ini.template`'s commented
  `[agent-loop]` block (now framed as the opt-in single home) plus a pointer
  comment by the `AGENT_JOBS` slot in `agent-resume.template.{sh,cmd}` both name
  the opt-in home and the precedence — a downstream repo moves to it exactly as
  this meta-repo's own launchers did (uncomment `[agent-loop]`, blank the launcher
  slots). `agent-resume.template.command` is a pure delegator with no dial slots,
  so it needs no change.

**Trade-off accepted:** a double-clicking user no longer sees the dials in the
file they clicked — mitigated by the launcher comment naming the declared home.
Overhead is modest (stdlib `configparser`, one precedence rule, tests) against
a recurring three-file edit for every dial turn.
