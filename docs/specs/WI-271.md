# WI-271 — Footprint-aware `staged_findings` (close the re-attestation false-positive)

**Status: deferred.** Filed 2026-07-22 from the WI-270 close (owner-directed). A
refinement to a **warn-tier, non-gating** check; deferred because the warn still
earns its keep today (see Deferral).

## The gap

`check_trajectory.staged_findings` (`project-trajectory/scripts/check_trajectory.py`
— "the no-validation-delta warn") is a pre-commit heuristic: when a commit flips a
WI to `done` that shares an SR-Ref with a previously-`done` WI (a *follow-up* on an
already-delivered SR), and the staged diff (`git diff --cached`) touches neither
`docs/test/test-cases.csv` nor `tests/`, it warns "the validation chain did not
change." It is scoped to the **single staged commit** and is a deliberate no-op at
gate time (no git context).

That scope **false-positives on the build → review → close workflow** for
re-attestation / follow-up WIs. The chain change lands in the *implementation*
commit (while the WI is `active`), but the *close* commit — the one that flips
`active → done` and so trips the follow-up detection — is bookkeeping-only, so its
staged diff shows no chain file.

**Worked evidence (WI-270):** WI-270 re-attested SR-034/SR-035 (delivered long ago
by the done WI-020), changing TC-035 in impl commit `a9e2b45`; the close commit
`74de359` was docs-only, so the warn fired even though the chain genuinely changed.
(WI-268, closed the same way, did NOT fire — SR-108 had no prior *done* deliverer,
so it wasn't a follow-up. The trigger is specific to re-attestation of an
established SR.)

## The fix (rigorous — footprint-aware)

Widen "did the chain change?" from the single staged commit to the **WI's build
footprint**: for each follow-up WI closing in this commit, check whether
`test-cases.csv` or a `tests/` file changed anywhere in the commit range from the
WI's build-base to HEAD (plus the staged tree), not just `git diff --cached`. If
the chain changed during the WI's build, do not warn.

Design points for the builder:

- **Build-base determination.** Options: the commit where the WI row last entered
  `active`/`queued` (walk `git log`/`-L` on the WI row), the WI's first-appearance
  commit, or a bounded N-commit look-back. Prefer the tightest honest bound; a
  bounded look-back is a safe floor.
- **Preserve the fail-safes.** Stdlib-only; a **silent no-op when git context is
  absent** (the current gate-time behavior); the genuine one-commit paper-close
  (queued/deferred → done in a single commit with no chain change) must still warn.
- The cheaper `was == "active"` exemption (an active WI's impl already landed) is a
  reasonable first cut, but the footprint range check is what **fully closes** the
  gap (it also covers a WI that flips queued → done in one commit while its chain
  change rode an immediately-prior commit).

## Deferral

The warn is **non-gating** (a hook-only advisory) and **still earns its keep
today**: an over-trigger costs a moment's investigation — a human confirms the
close is legitimate — which is the *lesser evil* than an under-trigger that lets a
real paper-close through. So this is false-positive **noise reduction**, not a
correctness fix. **Un-defer trigger:** the false-positive rate grows noisy enough
to erode the signal (operators reflexively dismissing the warn), or an owner call.

## Done-when (on un-defer)

- [ ] A re-attestation / split-close follow-up whose chain changed in an earlier
      (build) commit no longer warns on its bookkeeping close.
- [ ] A genuine one-commit paper-close (follow-up → done with no chain change
      anywhere in its footprint) still warns.
- [ ] A regression proves both (a WI-270-shape case goes green; a synthetic
      paper-close goes red) and pins the git-absent silent no-op.
- [ ] Stdlib-only; no gate-time behavior change (still a no-op at G3).
