# WI-286 — worker/integrator worktrees run the ambient interpreter, not the venv

**WI:** WI-286 · **Status:** queued · **Delivers:** the unattended worktree
launch env (harness layer; sibling of WI-274) — no new spine SR

## Problem

The dispatcher runs each train in its own git worktree
(`C:\Projects\ai-template-trains\<train>`) and each worker session shells out to
run the harness (pytest, `check.py`, the generators). The Python those commands
resolve is whatever is **ambient on the session's PATH** — nothing points a
worktree session at the repo's `./.venv`. In run `20260723T0202` every worker
inherited the launch shell's interpreter (**Python 3.8**, below the declared 3.11
floor); it happened not to break because 3.8 passed most tests, but:

- it is **below the WI-262/WI-270 floor** the repo declares and CI enforces, so a
  3.11-only idiom would pass locally in a worktree and only fail in CI;
- a worktree has **no `.venv`** of its own, so a bare `python -m pytest` there
  resolves to a system interpreter that may lack the pinned dev tools
  (`requirements-dev.txt`) — the pytest-cov/xdist the bar assumes;
- it compounds WI-285: once the integrator bar actually runs, it must run under a
  floor-satisfying, pinned interpreter or it re-imports this fragility.

This is the walk-away-run twin of WI-274 part A (which fixes the *primary*
checkout's stale venv): the same "which Python runs the harness" question, at the
per-worktree boundary the dispatcher owns.

## Approach

- **Point worktree sessions at a floor-satisfying, pinned interpreter.** Options
  to weigh in the build (record the choice):
  - have the dispatcher pass the primary repo's `./.venv` interpreter into the
    worktree session env (e.g. prepend `<root>/.venv/Scripts` to PATH, or set the
    harness `{py}` to an absolute venv path) — the worktrees share the root venv,
    no per-worktree install;
  - or create/reuse a per-worktree venv (heavier; likely unnecessary since the
    kit is stdlib-only and only the *tests* need the pinned tools).
    Lean: share the root venv by absolute path — one pinned toolchain, zero
    per-train install cost.
- **Preflight the interpreter floor** at worker/integrator launch: refuse (or
  loudly warn + record) when the resolved harness Python is < 3.11, so a
  below-floor run never silently produces a green.
- Tests: a worktree session resolves the intended interpreter; a sub-3.11
  resolution is caught at preflight (mirrors WI-274's discovery tests).

## Interfaces

No cross-module seam — intra-module (`agent_dispatch` worktree/session env +
preflight, and tests). Sibling scope: WI-274 (dev-setup/venv) and WI-285
(integrator bar) share the "which Python runs the harness" concern.

## Resolution

**Shared root `.venv`, not a per-worktree venv.** The lean the spec preferred is
what shipped: the kit is stdlib-only, so only the *tests* need the pinned tools
(`requirements-dev.txt`), and creating a venv per train would pay a real install
cost per dispatch for zero benefit. Instead the dispatcher **shares the root
`.venv` by absolute path**. Three coordinated moves, all in the dispatcher (the
one process that owns the primary checkout and leases the worktrees):

- `agent_common.venv_python(root)` / `harness_python(root)` resolve the repo's
  own `.venv` interpreter (probing both `bin/python` and `Scripts/python.exe`).
- `agent_dispatch._activate_root_venv(root)` prepends that `.venv`'s bin dir to
  the dispatcher's own `PATH` (and sets `VIRTUAL_ENV`) once at launch, so every
  child inherits it — the worker's agent `python -m pytest`, the pre-commit floor
  (whose `$REPO_ROOT/.venv` probe misses in a venv-less worktree and falls through
  to `PATH`), the integrator's staging commits, and `./scripts/check.sh`.
- `_run_combined_bar`'s `{py}` resolves through `harness_python(root)` too, so the
  composed-tree bar runs the `.venv` even when the dispatcher was itself launched
  on ambient Python (closing the ambient-3.8 hole WI-285's `{py}=sys.executable`
  would otherwise re-import — the interaction WI-285 flagged).

**Preflight, fail-closed.** `_harness_floor_failures(root)` folds into the same
preflight failure list `dispatch_run` already gates on (joined with `+`, so no
new branch touches `dispatch_run`'s complexity baseline). It refuses when the
resolved harness interpreter is `< MIN_PYTHON` (3.11) — a below-floor `.venv`
(points at `dev-setup --install`, WI-274), a below-floor ambient interpreter when
no `.venv` exists, or a `.venv` that cannot be run to report a version. The check
targets the **harness** interpreter, not the dispatcher's own orchestration
interpreter, so a stdlib-only dispatcher launched on an older Python with a proper
3.11 `.venv` still passes — the venv is what runs the tests.

**Why the floor lives in the dispatcher, not the shared `preflight()`.** A worker
process runs `agent_loop.py` under the dispatcher's own interpreter (which may be
ambient) while its *harness children* resolve the injected `.venv`; checking the
worker's own `sys.version_info` in the shared `preflight()` would false-refuse a
worker whose harness is in fact floor-satisfying. The dispatcher gates every
worker launch and injects the venv they use, so validating once there — at
"integrator launch", which also gates worker launch — is both correct and
sufficient.

**Template / downstream.** No new schema or migration. `agent_dispatch.py` /
`agent_common.py` are kit scripts that ship downstream verbatim, so an adopter
gets this fix on re-sync with no action; the setup scripts already create `.venv`
at the 3.11 floor. `MIN_PYTHON` mirrors the `(3, 11)` the setup scripts hardcode;
an adopter deliberately targeting an older product runtime lowers it alongside
`setup.{sh,ps1}`'s own check (noted at the constant).

**Known residue (not this WI).** The dispatcher's own orchestration interpreter is
still whatever the launcher resolves (bare `python`); WI-274 owns pointing the
launcher at the venv. The floor here guarantees only that the *harness* runs
floor-satisfying, which is the false-green surface this WI targets.
