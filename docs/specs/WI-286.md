# WI-286 — worker/integrator worktrees run the ambient interpreter, not the venv

**WI:** WI-286 · **Status:** queued · **Delivers:** the unattended worktree
launch env (harness layer; sibling of WI-274) — no new spine SR

## Problem

The dispatcher runs each train in its own git worktree
(`C:\Projects\ai-template-trains\<train>`) and each worker session shells out to
run the harness (pytest, `check.py`, the generators). The Python those commands
resolve is whatever is **ambient on the session's PATH** — nothing points a
worktree session at the repo's `./.venv`. In run `20260723T0202` every worker
inherited the launch shell's interpreter (**Python 3.8**, below the declared 3.11
floor); it happened not to break because 3.8 passed most tests, but:

- it is **below the WI-262/WI-270 floor** the repo declares and CI enforces, so a
  3.11-only idiom would pass locally in a worktree and only fail in CI;
- a worktree has **no `.venv`** of its own, so a bare `python -m pytest` there
  resolves to a system interpreter that may lack the pinned dev tools
  (`requirements-dev.txt`) — the pytest-cov/xdist the bar assumes;
- it compounds WI-285: once the integrator bar actually runs, it must run under a
  floor-satisfying, pinned interpreter or it re-imports this fragility.

This is the walk-away-run twin of WI-274 part A (which fixes the *primary*
checkout's stale venv): the same "which Python runs the harness" question, at the
per-worktree boundary the dispatcher owns.

## Approach

- **Point worktree sessions at a floor-satisfying, pinned interpreter.** Options
  to weigh in the build (record the choice):
  - have the dispatcher pass the primary repo's `./.venv` interpreter into the
    worktree session env (e.g. prepend `<root>/.venv/Scripts` to PATH, or set the
    harness `{py}` to an absolute venv path) — the worktrees share the root venv,
    no per-worktree install;
  - or create/reuse a per-worktree venv (heavier; likely unnecessary since the
    kit is stdlib-only and only the *tests* need the pinned tools).
    Lean: share the root venv by absolute path — one pinned toolchain, zero
    per-train install cost.
- **Preflight the interpreter floor** at worker/integrator launch: refuse (or
  loudly warn + record) when the resolved harness Python is < 3.11, so a
  below-floor run never silently produces a green.
- Tests: a worktree session resolves the intended interpreter; a sub-3.11
  resolution is caught at preflight (mirrors WI-274's discovery tests).

## Interfaces

No cross-module seam — intra-module (`agent_dispatch` worktree/session env +
preflight, and tests). Sibling scope: WI-274 (dev-setup/venv) and WI-285
(integrator bar) share the "which Python runs the harness" concern.

## Done-when

      interpreter for the harness (verified: the run does not silently use
      ambient 3.8).
- [ ] A below-floor interpreter is caught at preflight, not after a false green.
