# WI-337 — the duplicate-code census is line-ending-sensitive, and the committed one now fails CI

**Status: queued** (`P1`, found 2026-07-27 while reconciling
[127-REVIEW-A](../reviews/127-REVIEW-A.md)'s duplicate counts against my own).

## The defect

`check_dupes.py` fingerprints a token window. Its tokenizer sees the source's
**line endings**, so the same file produces **different fingerprints** on a CRLF
checkout than on an LF one — and `docs/dupes-allow` records fingerprints. The
census therefore cannot be valid on Windows and Linux at the same time.

Measured 2026-07-27, same command (`check_dupes.py --src project-trajectory/scripts`),
counting reported duplicate blocks:

| source tree | census | blocks reported |
|---|---|---|
| fresh LF worktree @ `1b65c4d` | the pre-WI-334 census | **18** |
| this Windows CRLF working tree | the same census | **85** |
| fresh LF worktree @ `ffa7377` | **the re-stamped census** | **128** |

`project-trajectory/scripts/trace.py` carries **2,703 CR bytes** in the Windows
working tree and **0** in a worktree checkout — that is the whole mechanism.

## Why it is P1

**`ffa7377` shipped a census generated on a CRLF tree.** The `dupes` step is
G3-only and the derived gate is G3, so the first Linux CI run — or any fresh
clone — reds with 128 unsanctioned blocks. The branch has never been pushed, so
this has not fired yet; pushing without fixing it will.

It also silently invalidated the previous state: the old census was LF-based
(correct for CI, wrong on a Windows working tree). The re-stamp inverted which
environment is broken rather than fixing either.

## What this invalidates in the record

The "86 blocks" figure in the WI-334 deliverable, `docs/dupes-allow`'s comment
trail and the `ffa7377` commit message is **a CRLF-tree observation reported as
if it were the tool's canonical count**. The review's "18" is the LF figure.
Neither is wrong for its environment; presenting either as *the* number is.
The classification built on it ("MOST are the CLI preamble") is separately
refuted — see **WI-338**, whose spec-of-record is
[127-REVIEW-A](../reviews/127-REVIEW-A.md) itself.

## Done when

- [ ] `check_dupes.py` normalizes line endings before tokenizing, so a
      fingerprint is a property of the CODE and not of the checkout. Prefer
      normalizing at the read (`newline=None` / strip `\r`) over post-processing
      tokens.
- [ ] The census is regenerated on the normalized basis and **verified in BOTH**
      a CRLF working tree and an LF worktree — the same count in each. A fix
      asserted on one platform is the bug repeated.
- [ ] A guard that would have caught this: feed the tokenizer the same source
      with `\n` and with `\r\n` and assert the fingerprints are equal.
      Mutation-prove it by removing the normalization.
- [ ] The false counts corrected wherever they were signed: the WI-334
      `Deliverable`, `docs/dupes-allow`'s comment trail, `docs/log.md`'s
      2026-07-27 WI-333+334 entry, and the `ffa7377` commit message (a follow-up
      note in the log — history is not rewritten).
- [ ] Confirm no OTHER kit checker fingerprints or hashes raw source with the
      same flaw (`check_stubs.py`, `gen_arch_map.py`, the ratchet tests).
