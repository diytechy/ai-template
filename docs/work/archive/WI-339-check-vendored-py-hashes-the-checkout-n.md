## Deliverable

DONE 2026-07-28. content_digest(data) -> (digest, normalized) is what both sides of the comparison now go through: CRLF and lone CR collapse to LF for text, binary is hashed exactly as it is, and the WARN line NAMES which rule it applied - a comparison that silently changes its own basis is how the original defect stayed invisible. Both sides get the same treatment because the fetched remote may itself be served with either ending. THE CARE THE SPEC ASKED FOR, and the reason this is not WI-337 again: a vendored file may legitimately be BINARY, and stripping CR bytes from a PNG or an archive would corrupt the comparison - the opposite failure. looks_binary() sniffs a NUL byte (git's own heuristic) rather than trusting the extension, because an unknown extension must not silently opt a file OUT of the fix and a genuine binary must not be normalized into a false match. Empty content is text. Guards (6, tests/test_check_vendored.py) - one per Done-when clause: the same content matches across LF/CRLF/lone-CR; genuinely DIFFERENT content still differs, asserted twice (the spec's own words - both directions or it is half a guard, since a normalization that collapsed everything would pass the first test and be worthless); a binary file is sniffed, not normalized, and hashes byte-exact, with a PNG fixture that carries CRLF INSIDE its binary content on purpose; ordinary and EMPTY text take the normalizing path; and the mutation proof lives INSIDE the suite - it restates the pre-WI-339 raw-bytes predicate and asserts the defect reproduces before asserting the fix, so a successor can re-derive it rather than take a session's word for a hand-run mutation.
