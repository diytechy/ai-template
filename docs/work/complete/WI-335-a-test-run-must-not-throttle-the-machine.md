## Deliverable

Root conftest.py gains pytest_configure -> a NAMED Windows job object with a HARD CPU rate cap (default 50%, PYTEST_CPU_CAP dials it, off/0/100 disables) plus a BelowNormal priority drop. The job bounds the whole tree (controller + every xdist worker + every subprocess they spawn) and, because it is NAMED, every pytest process joins the SAME job - so N concurrent runs and N train worktrees share ONE ceiling instead of multiplying it. Proven with a burner: 24 spinners = 100% CPU uncapped, 37.5% mean / 47% max under a 25% cap; probed live from an unrelated process mid-suite (ControlFlags=0x5, CpuRate=5000). Wall-clock cost negligible here (test_trace.py 20.4s capped vs 20.7s uncapped) because the suite is subprocess/IO-bound. CI opts out in test.yml + canary.yml (no desktop to protect, fewer cores, and a wall-clock smoke-budget job). POSIX degrades honestly to os.nice(5) - no cgroup-free hard cap exists there. Never fatal: any failure warns and the suite runs normally. Guards in tests/test_cpu_cap.py, all mutation-proven (flag 0x4->0x2 fails; not applying the cap fails; default 50->90 fails - that last one exposed a self-referential guard that had passed while the guarantee was withdrawn). TWO TRAPS PAID: HARD_CAP is 0x4 not 0x2 (0x2 is WEIGHT_BASED and rejects a rate), and QueryInformationJobObject(NULL) reports the IMMEDIATE job so it reads ControlFlags=0 inside an xdist worker's nested job - IsProcessInJob against the named handle is the correct instrument. || CORRECTED 2026-07-27 (WI-338 + 127-REVIEW-A BLOCKER 1). The 'every concurrent run joins the same named job and shares ONE ceiling / N runs total the cap' claim above is FALSE and was the headline of this WI. Windows permits assignment only into a job that is EMPTY or already in the process's own parent job chain, so a second run from a different process tree cannot join a job the first has populated: it falls back to a private job at the same percent and warns on stderr. Concurrent runs therefore MULTIPLY the cap - two can total ~100%. Measured directly: with a first tree holding the named job, two independent probes both reported PRIVATE while a CHILD of the first reported SHARED. Two further narrowings: an API failure leaves the run UNCAPPED, and POSIX's os.nice(5) is a priority bump, not a cap at all. What IS delivered - a tree-wide ceiling for ONE run, covering the xdist workers and the slow tier's per-test subprocesses - still answers the original problem that a worker count bounds workers and not processes, and the 50% default is unchanged. Now pinned by tests/test_cpu_cap.py::test_a_second_independent_run_gets_its_own_ceiling (first tree SHARED, child SHARED, independent second tree PRIVATE and warning), mutation-proven both ways; the pre-existing live-process test's OR over shared/private is kept but its comment no longer reads as 'asserts both' (MAJOR 2).
