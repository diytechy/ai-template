## Deliverable

FOLDED INTO WI-498 slice 4 and closed there (commit named in
docs/log.d/2026-08-21-wi498-stage-unification.md, "Slice 4"). The defect this
row filed is fixed, and on the NEW carrier rather than the one the row named —
which is the whole reason it folded: the ruled stage-unification plan (§5 item
4) re-keys both event detectors off `docs/gate` in the same change, so fixing
the reader against `docs/gate` first would have been work done twice and a
migration entry owed twice.

What landed:

- `intake._gate_moved` → **`_stage_moved`**: a two-point delta of `docs/stage`'s
  headline `stage` FIELD across the two git trees, parsed through
  `kitlib.stage.parse`. Not "the first non-comment line" as this row proposed —
  `docs/stage` is key=value precisely so a reader addresses a field by name
  (WI-498 slice 1), which is a stronger fix than the one asked for and is why
  the spec's own wording was not followed literally.
- `tier_signal`'s keyword is `stage_moved`, so the signal and its input name the
  same axis.
- **Unreadable on either side now answers False**, which the retired docstring
  claimed and the code did not do (a None on one side compared unequal to a
  value on the other and reported a move). It matters at exactly one commit per
  adopting repo — the kit upgrade that first writes `docs/stage`.
- **The regression pins this row demanded**, both driven on real two-commit git
  repos in `tests/test_stage_event_detectors_driven.py`: value changed with the
  header byte-identical → True; header-only change → False. Plus two this row
  did not ask for (absent on one side, unknown rung) and — the pin that actually
  discharges the row's subject — an END-TO-END drive of `intake._amendment_drafts`
  proving `tier_signal`'s `strong` arm now mints, with the stage-held-still
  counterfactual minting `medium`. A unit test of the input would not have shown
  that the ROW can fire.
- **The sibling sweep this row instructed**: two `splitlines()[0]` sites remain
  in the kit (`integrate.py`, `trunk_step.py`) and NEITHER is in the defect
  class — both read the first line of git command output, where line 0 is the
  value by the command's own contract. The sweep is mechanized as
  `test_no_kit_script_takes_splitlines_0_of_a_GENERATED_file`, an AST read that
  names those two, so a third site has to be judged rather than inherited.
- Adopter-facing: a RESYNC_PACK §3 entry leading with the fact that a mechanism
  which has been silently dead in an adopter's repo starts firing, and that no
  NEW rows appear — some existing ones are simply graded at the tier they always
  warranted.

## Context

Found by the 2026-08-21 stage-rekey deep-check (incidental finding, verified
live): `intake.py:480` `_gate_moved` compares `splitlines()[0]` of
`docs/gate` across revisions — the STATIC header comment ("# DERIVED BAR —
generated by..."), byte-identical at every revision since the derived-gate
migration — so the function is always False and `tier_signal` can never
mint its `strong` adjudication row. It worked pre-derived-gate, when a
hand-set gate file's line 0 WAS the value, and broke silently at the
migration.

Fix: read the first non-comment line (the same idiom the file's own header
documents and the other readers use), and PIN it — a regression test that
drives two revisions of a real gate file (value changed, header unchanged)
and asserts `_gate_moved` is True; plus the inverse (header-only change,
False). Check whether any sibling in intake.py shares the `splitlines()[0]`
idiom on a generated file while sweeping — fix only within this defect
class if so, record anything wider as a finding.
