title = "A `blockref` is a LABEL, not a SUBSCRIPTION - decide whether a park is re-checkable or human-swept, and make the repo SAY which. MECHANISM AS BUILT: `blocked` has no directory; it is derived as `queued/` plus a `blockref` frontmatter key (concurrency-restructure §7 design note, `schedule.py` - `if st == 'queued' and wi['blockref']: return 'blocked', [...]`). The derivation reads the KEY'S PRESENCE and never resolves what it points AT. So the referenced item's own state is never consulted: flipping an `OI-N` to `ruled`, or closing a referenced WI into a terminal folder, does NOT return the parked row to the ready frontier. Today every park is permanent until a human notices it. THIS ROW WAS DRIVEN, NOT REASONED: WI-391 was the first park this repo created, and it was created on the explicit assumption that ruling its blocker (OI-11) would release it. That assumption was wrong, the park was measured to be permanent, and WI-391 was CANCELLED instead - so the worked example is in the log for 2026-08-01 and the cost of the silence is already one mis-taken disposition. TWO HONEST READINGS, NOT A RECOMMENDATION - this row files the question, it does not rule it. (A) PARKS ARE RE-CHECKABLE: the derivation should consult the blocker's state, so a row whose blocker is `ruled` (an OI) or terminal (a WI) rejoins the frontier MECHANICALLY and the park releases itself. Honest cost: `schedule.py` would have to resolve blockrefs across TWO registries (`docs/work/` specs and `docs/requirements/open-items.csv`), which is a new cross-registry read in a module that is deliberately stdlib-only and self-contained; and a DANGLING blockref - naming an id that does not exist, or one whose registry is absent - becomes a brand-new failure mode that needs its own rule (refuse? warn? treat as unblocked, which fails open, or as blocked, which fails closed and re-creates the permanent park). (B) PARKS ARE HUMAN-SWEPT: then that is a legitimate design, but the repo must SAY it - the `WI-000` exemplar states only that `blocked` is `queued/` plus a `blockref` naming the reason and that *readiness is the scheduler's to derive*, which reads as a promise the scheduler does not keep, and no process text corrects it. That sentence lives in TWO files, byte-identical, and both must change together: `docs/work/queued/WI-000-example.md` (this repo's own copy) and `project-trajectory/work/WI-000.template.md` (the shipped template), at lines 40-41 in each. Mutation-proven: editing the repo copy alone reds `tests/test_dogfood_sync.py::test_dogfooded_boilerplate_matches_template`. Cost is one paragraph in each, plus a sweep habit nobody currently owns. WHY THE EXEMPLAR QUOTE IS FAIR - and it is a stronger claim than it looks: WI-391's own refutation killed the specs-mirror partly on the ground that DERIVED DATA WITH NO REGENERATOR IS HAND-MAINTAINED DATA WEARING A DERIVED LABEL. `blocked` is derived data whose input is never read. By the standard that refutation established, the exemplar promises exactly what this row says it promises. BOTH OPTIONS TOUCH KIT-SHIPPED SURFACES THAT ADOPTERS INHERIT, and a ruler should see that before choosing: (B) edits the shipped `WI-000.template.md` boilerplate every scaffold copies, and (A) is the larger of the two by some way. `scripts/schedule.py` is a `bootstrap.py` MAPPING destination materialized into every adopting repo, and it is NOT a leaf: `drive.py`, `integrate.py`, `agent_loop.py`, `gen_trajectory.py` and `check_trajectory.py` all consume it, and `check_trajectory.py` runs in the SHIPPED pre-commit hook. So (A) changes readiness semantics underneath five shipped modules and a hook, not underneath one script - a ruler should see that true size before choosing. Either way downstream repos see a behaviour or wording change on their next kit resync; neither option is meta-repo-local. WHAT IS WRONG TODAY IS NOT THE CHOICE BUT THE SILENCE: the mechanism IMPLIES a subscription it does not provide, and the natural reading of `blocked` is that it clears when the blocker does. Same shape, one registry over, as WI-394 - the row filed on the `wi-383` branch finding that a WI id cited in prose is never checked to EXIST.
