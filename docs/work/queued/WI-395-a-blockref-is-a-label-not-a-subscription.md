title = "A `blockref` is a LABEL, not a SUBSCRIPTION - decide whether a park is re-checkable or human-swept, and make the repo SAY which. MECHANISM AS BUILT: `blocked` has no directory; it is derived as `queued/` plus a `blockref` frontmatter key (concurrency-restructure §7 design note, `schedule.py` - `if st == 'queued' and wi['blockref']: return 'blocked', [...]`). The derivation reads the KEY'S PRESENCE and never resolves what it points AT. So the referenced item's own state is never consulted: flipping an `OI-N` to `ruled`, or closing a referenced WI into a terminal folder, does NOT return the parked row to the ready frontier. Today every park is permanent until a human notices it. THIS ROW WAS DRIVEN, NOT REASONED: WI-391 was the first park this repo created, and it was created on the explicit assumption that ruling its blocker (OI-11) would release it. That assumption was wrong, the park was measured to be permanent, and WI-391 was CANCELLED instead - so the worked example is in the log for 2026-08-01 and the cost of the silence is already one mis-taken disposition. TWO HONEST READINGS, NOT A RECOMMENDATION - this row files the question, it does not rule it. (A) PARKS ARE RE-CHECKABLE: the derivation should consult the blocker's state, so a row whose blocker is `ruled` (an OI) or terminal (a WI) rejoins the frontier MECHANICALLY and the park releases itself. Honest cost: `schedule.py` would have to resolve blockrefs across TWO registries (`docs/work/` specs and `docs/requirements/open-items.csv`), which is a new cross-registry read in a module that is deliberately stdlib-only and self-contained; and a DANGLING blockref - naming an id that does not exist, or one whose registry is absent - becomes a brand-new failure mode that needs its own rule (refuse? warn? treat as unblocked, which fails open, or as blocked, which fails closed and re-creates the permanent park). (B) PARKS ARE HUMAN-SWEPT: then that is a legitimate design, but the repo must SAY it - the `WI-000` exemplar states only that `blocked` is `queued/` plus a `blockref` naming the reason and that readiness is the scheduler's to derive, which reads as a promise the scheduler does not keep, and no process text corrects it. Cost is one paragraph plus a sweep habit nobody currently owns. WHAT IS WRONG TODAY IS NOT THE CHOICE BUT THE SILENCE: the mechanism IMPLIES a subscription it does not provide, and the natural reading of `blocked` is that it clears when the blocker does. Same shape as WI-394's finding, one registry over. SCOPE: this is a FILING, not a design - rule (A) or (B), then implement whichever is ruled (for (A) the derivation plus the dangling-blockref rule and its tests; for (B) the `WI-000` exemplar wording plus the process-options text that names the sweep and its owner). Do not build both."
