## 3. Pitfalls worth inheriting

**A test that always fails in the working context is not a guard.** Every
builder all session reported a "standing red" and learned to ignore it. It was
`test_this_repo_is_not_a_work_branch`, whose premise had expired: it asserted
the *current* checkout holds no claim, which is false by construction in a lane
worktree. When WI-386 made a lane worktree run the suite as a **gate**, that red
made the station protocol's own refresh unable to go green — so nothing could
merge at all. Fixed by naming the primary checkout explicitly. The tell was
visible for hours and normalised by everyone who saw it.

**Green in a working tree is not green in a fresh checkout.** Two trunk defects
hid behind local on-disk state: links into a directory git cannot track once
empty, and a generated file present locally but absent from a bare extraction.
Both were found by measuring against `git archive` rather than the working tree.

**A ratchet cannot warn when an entry exists on only one side of a merge.** An
auto-merge silently kept a stale size figure because trunk carried no entry for
that file. Caught only by re-measuring with arithmetic that had to reconcile.
(Note: this is *not* a hole — restoring the stale value reds the ratchet test
instantly, and that test runs in the refresh bar before anything merges.)

**Record defects outnumbered code defects roughly five to one.** Across the four
second-wave rows, review rounds after the first found almost nothing in the
code and a great deal in the *record*: unreproducible figures, populations
inherited rather than derived, mechanisms asserted without being executed. One
row's classifier needed no edit after its second commit; five subsequent rounds
were the record catching up to what was true.

**The single most useful formulation the session produced**, from a builder who
had just reported a figure they had not measured:

> A background run is not a measurement until its output has been read.
> "The suite passed" is not the same proposition as "I saw the suite pass."

And its companion, from a row that took six rounds:

> Six rounds of attention did not prevent a seventh instance. That is the
> argument for the remedy being **mechanical rather than attentional** — run the
> command, do not resolve to be careful.

Both are why **WI-392** exists. It now has four independent worked cases from
four different lanes.

**A citation style that reads naturally to a human is invisible to the
checker.** A backticked path with a line suffix is a dangling reference, and a
bare directory prefix is convicted as a missing file. This fired **five times on
one branch**, three of them while the author was actively writing about it, and
once *inside the row filed to document it*. That is a tooling gap
(**WI-396**), not carelessness.

**`blocked` is a park with no automatic release.** `blocked` is derived as
`queued` + `blockref`, and the blocker's state is never consulted — so parking a
row pending a decision creates something that cannot come back. Learnt by making
that exact mistake (see §4).

## 4. Was this caused by driving the cycle from an LLM instead of `agent-resume`?

Partly, and it is worth being precise about which parts, because the answer
splits cleanly.

**Yes — these are attributable to the way I drove it:**

- **I ran four lanes concurrently. The shipped loop runs one.** `drive.py` is
  frontier → claim → worker → serial merge queue, one work item at a time. The
  multi-lane dispatcher is **WI-381, which is not built yet**. So I was
  hand-simulating a component that does not exist, and inherited its unsolved
  problems.
- **Id collision.** Two lanes minted `WI-392` independently, because a lane can
  only see its own tree. That is exactly the reservation hazard the design
  discusses — and it cannot happen when one worker runs at a time. Caused by the
  concurrency, not by the agent.
- **A population handed over instead of derived.** I briefed a builder with a
  set of four branches to measure; the real population was twenty. They
  inherited my framing without re-deriving it. A worker booting from the spec
  rather than from an orchestrator's summary would have had to derive it.
- **Round inflation.** Several rows ran five and six review rounds. The declared
  policy asks for **one** APPROVE. Rounds beyond that were my calls, and while
  most found real record defects, the cost is real: a cancelled row consumed six
  rounds.
- **A wrong disposition.** I parked a refuted row as `queued` + `blockref`
  pending an owner ruling, which — as §3 notes — creates a row that can never
  return. Corrected to `cancelled` on review.

**No — these would have happened under `agent-resume` too:**

- Every trunk-side defect (§3, first two entries). They were pre-existing and
  latent; the drain exposed them.
- **The lane canary blocking the station protocol.** This is a property of
  WI-386's design meeting a pre-existing test, and it would have blocked the
  *first* `agent-resume` drain just as completely. Arguably the loop would have
  hit it sooner and with less context to diagnose it.
- Builder-side figure errors, the `path:line` trap, the alphabetical queue
  ordering, and the `blockref` semantics — all properties of the tooling and the
  registry, independent of who is driving.

**The honest summary.** The attended drive did not cause the defects; it caused
the *concurrency*, and concurrency is what surfaced the id collision and made
the queue-ordering coupling visible. Both are findings the program wanted
anyway — WI-381 has to answer them. What an LLM-driven cycle genuinely added
was **judgement in the loop** (a refuted row correctly cancelled rather than
built, a design sentence escalated to the owner) and **round inflation**, which
is the cost side of the same coin.

The sharpest version: *the shipped loop is serial, so I was testing a design
that has not been built. Most of what hurt was the design's own open questions
arriving early.*

## 6. Two findings the resolution produced, unfiled (no id minted)

Recorded here as prose because a lane may not mint a work-item id and the
integrator did not mint one on trunk either (trunk's max is 394; the unmerged
`wi-391` branch carries 395/396, so a trunk mint would recreate the collision
§4 describes). Both want a row when ids are next assigned.

1. **A `check.py` failure never reaches the integrator's refusal message.**
   `agent_common._failure_tail` prefers the LAST `  FAIL  <step>` line and then
   walks back to the nearest `=== <step> :` banner. `check.py` prints every
   step's status a second time in its final summary block (`check.py` ~L1531),
   at *any* `--jobs`, so the last `FAIL` is always the summary copy and the
   extracted window is always summary lines. The refresh's whole diagnostic
   surface is that message, which is why this session's red lost its error text
   **three times** before it was reproduced by hand. The fix is small and
   narrowing: anchor on the FIRST `FAIL` after the last banner, or have
   `check.py` re-emit the failing step's captured output. Until then, a red
   refresh must be reproduced by hand (`git merge --no-ff --no-commit <trunk>`,
   `trunk_step.py`, `git add -A`, then the step directly) — the refresh's `undo`
   resets the lane, so the failing tree is gone by the time you read the message.
2. **Only the station can see a new module's containment, and that is now twice.**
   `docs/architecture.md` is trunk-owned, so its freshness gate SKIPs on a
   claimed work branch (SR-133) and a new module never enters the arch-map
   inventory until the refresh regenerates it. The knowledge⇒component rule then
   ERRORs under `--strict`, *after* the last review round — so the remedy always
   lands after an APPROVE and always costs a round. `WI-374`/`drive.py` was the
   first instance; `WI-387`/`handback.py` is the second, with the identical
   two-row remedy. The constraint-shaped answer is to make the containment owed
   where the module is *added* (a check on `bootstrap.py`'s MAPPING / the
   shipped-module set rather than on the regenerated inventory), so a branch
   that ships a module cannot be APPROVED without it.
