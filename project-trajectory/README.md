# Project Trajectory Template

A portable, **stack-agnostic** kit for taking a project from brief (or draft)
to an accepted, maintainable deliverable via a **gated, requirement-traced**
process — with modular/deduplicated code, testable chunks, and explicit
attention to end-user usability and corner cases.

It encodes a key lesson: the value is in the **artifacts, gates, and role
discipline** — not in spawning many agents. One driver wears the role "hats" in
continuous context; a separate reviewer is summoned only for high-risk pre-gate
audits.

| `registries/components.template.toml` | CMP-### **domain-neutral component** registry — the set-grained home for **knowledge + lifecycle** (a subsystem, "the left arm", a software package group). | `registries/hats.template.toml` | The **hats roster** — the declared expert perspectives every applicable decomposition must face (SN-036) → copy to `docs/requirements/hats.toml`. Ships with **content**, not as a blank form — the roster itself is the census (several hats stay silent *by design* until your project uses their tags) — and is **owner text**: adopters are expected to *edit* it, which is the only thing that keeps an inherited `applies_when` honest. `scripts/hats.py` reads it and `scripts/plan_briefs.py` injects the applicable hats' questions into the dual-plan **planner** brief. Deleting the file is a supported opt-out (composers proceed without hats); a file that exists and does not parse **refuses loudly**. |
| `registries/work-items.template.csv` | **Legacy-format reference, no longer scaffolded** (Phase 2c): the WI registry now scaffolds as the `docs/work/` spec folder (see `work/WI-000.template.md`), and this template survives as the 17-column schema of record that `scripts/wi_convert.py` migrates a pre-flip repo from. In the legacy CSV each row is a work item that **delivers** SR(s), belongs to a **workstream**, and **depends on** predecessor WIs (hard or advisory edges). The seven-state lifecycle is `draft→queued→active→done`, with `draft` for thinking-in-progress, `deferred` for deliberately postponed work, `blocked` for a named impediment, and terminal `cancelled` for work that will not be built. Optional `BuildTier` and `CritiqueBudget`/`CritiqueExhaustion` cells steer unattended routing and subjective-quality loops per WI. Off-spine like procurement/assets; `check_trajectory.py` owns the `WI-` ids (`trace.py` doesn't read them). Ships an inert `WI-000` row, so a repo that never adopts the layer pays nothing (process-options.md "Trajectory / work-items layer"). Its `SpecRef` column + the status.md↔registry SSOT rules (R-A hard; R-E/R-F + the forward-only done-id rule warn at commit, ERROR under `--strict` at DevStg-Tests+; R-B/R-C retired) are mechanized by `check_trajectory.py`. |
| `work/WI-000.template.md` | The **spec-folder home** of the same registry (docs/concurrency-restructure.md §2), scaffolded to `docs/work/queued/WI-000-example.md` beside the empty `draft/`, `active/`, `deferred/`, `cancelled/` and `complete/` directories: one Markdown spec per work item, **status encoded as the directory, which is the whole statement** (moves in distinct paths never conflict, and two branches claiming one item collide visibly in git), TOML frontmatter between `+++` fences for the row's cells, and the long `Deliverable` in the body where nothing needs escaping. `blocked` gets no directory — it is `queued/` plus a `blockref`; `draft/` is declared rather than improvised so a held id is visible to the duplicate-id guard and the dashboard; and each TERMINAL has its own directory (`complete/`, `cancelled/`), which is what let WI-384 delete the `disposition` key, its validator and both of its raise paths. ## The core ideas (why it produces sustainable code)

- **Traceability:** `SN → SR → LLR → TC`, joined by a generated matrix that must
  report **zero orphans**. Every line of intent is traceable to a need and a test.
- **Single source of truth + decomposition (not paraphrase):** facts live once
  and are referenced by ID; children add detail. This is what keeps docs and code
  from rotting into contradiction.
- **Modularity & dedup:** shared logic in one place; pure testable cores split
  from I/O/GUI shells; one-page architecture, generated so it can't drift.
- **Testability:** measurable acceptance criteria; tests cite requirement IDs;
  coverage threshold; a harness that runs locally and in CI.
- **Usability & corner cases:** a standing end-user lens for setup/first-run,
  failure modes, safety, automation/never-block, and honest docs.
- **Honest gates:** machine-checkable criteria where possible; everything else is
  explicitly classified Demonstration / Manual / Inspection — nothing hand-waved.

## Tuning knobs

- `COVERAGE_THRESHOLD` and `MAX_ROUNDS` in `PROCESS.md`.
- Drop a hat/gate for tiny projects (e.g. skip UX for a library); keep the
  SN→SR→LLR→TC spine.
- Scale review depth to risk — don't gate a rename like you'd gate a crypto path.
- Scale *structure* to scope: one module in one repo is the default; a repo can
  host several modules on the same spine (grouped by `Module`/component, with an
  integration TC per seam), and multi-repo under a coordinator is a rare, later
  step — climb the ladder only when scope forces it (process.md §10; the
  coordinator model is `MULTI_REPO.md`, a design with the tooling deferred).
