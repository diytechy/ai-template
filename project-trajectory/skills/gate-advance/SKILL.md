# Bar advance (clear DevStg-Reqs → DevStg-Tests → DevStg-Impl honestly)

Clearing a bar is a **decision recorded in a reviewed commit**, backed by a green
harness at that bar. Never self-advance; never report a green you didn't run.
Authority: `docs/process.md` §4 (the stage ladder), §5 (verdict protocol), §7
(the derived bar). The bar's **acceptor** is whoever the
`[attestation] human_ratification_through` dial in `docs/process.toml` declares
(default 4 = a human through every spine tier; the levels + the deviation
register: process-options.md "Gate authority levels") — on a non-default repo,
read "human" in this skill as that declared acceptor.

## Two axes: you are IN a stage, you CLEAR a bar

The **stage ladder** has eight rungs and names the rung *in work*; the three
**bars** are the subset of rung boundaries a human certifies. A stage is a state,
a bar is an event.

```
DevStg-Needs      vision and stakeholder needs in work
DevStg-Boundary   the frame: what is outside, what crosses, each typed.  ONCE.
DevStg-Reqs       obligations at the current boundaries.  RECURSES.
   ══ DevStg-Reqs ══     Stakeholder · UX · System Engineer
DevStg-Arch       partition each scope into sub-boundaries.  RECURSES.
DevStg-LLReqs     the inside of a leaf, bound to a code symbol.  TERMINAL.
DevStg-Tests      the test set in work
   ══ DevStg-Tests ══    System Engineer · Test Engineer
DevStg-Impl       implementation in work
   ══ DevStg-Impl ══  System Engineer · Test Engineer
DevStg-Release    nothing in work; release checklist available
```

Each bar is named for the **top rung it certifies**, so "which bar am I clearing"
is answered by "which rung am I finishing". **The ladder is not monotonic** —
`DevStg-Reqs` and `DevStg-Arch` oscillate as the decomposition descends, and
minting a drafted `CMP` row legitimately drops the reported stage back to
`DevStg-Arch`. That is the honest report, not a regression: do not "fix" it by
editing anything.

**The retired `G*` tags.** `G1`/`G2`/`G3` (and `G0`/`G-Release`/`G-Final`)  <!-- check_vocab: allow -->
retired with this ladder. They are accepted as **read-side aliases** so existing
hooks keep working (`check.py --gate G2` warns and runs `DevStg-Tests`), and  <!-- check_vocab: allow -->
`check_vocab.py` refuses them in authored text. Never write one into a new file.
**Never re-word a past attestation**: a sign-off that recorded a human certifying
`G1` recorded exactly that.  <!-- check_vocab: allow -->

## The derived-bar mechanism (derived, not hand-set)

The first non-comment line in **`docs/gate`**
(`DevStg-Reqs|DevStg-Tests|DevStg-Impl`) is the bar the repo must next clear,
which `scripts/check.py` reads to run exactly that bar's checks — so CI enforces
the bar the project is working toward. `docs/gate` is **generated by
`scripts/derive_gate.py`**, not hand-set (the operative rule is
`docs/process.md` §4): the value is **computed from the artifact states** (SN
draft-ness + SR/LLR/TC `Status` maturity) as the **min** over every in-scope
artifact's own bar, so the least-mature row selects it and a draft pulls it down.
You never edit that line; you **ratify artifacts** and regenerate.

- **Regenerate** after a ratification: `python scripts/derive_gate.py` (rewrites
  `docs/gate` with the computed value, a `# basis:` derivation carrying
  `stage=DevStg-<Label> stage-ord=<n> stage-of=8`, and a compute date).
- **Freshness** is guarded by the `derived-gate` step (`derive_gate.py --check`),
  wired into the pre-commit floor and every bar — so a ratification that moved
  the states but not the cache fails loudly.
- **Position is derived, never authored.** Cite the LABEL (`DevStg-LLReqs`), not
  the ordinal: an inserted rung re-numbers everything and moves no citation.

## Ratification = a reviewed Status-change commit

Clearing a bar is not a `docs/gate` bump. The acceptor **marks a batch of
artifacts ratified in a reviewed commit** — that commit *is* the sign-off, and
the bar derives from it:

- **Into `DevStg-Reqs`** — a draft requirement is ratified: `Status` **`Drafted`
  → `Approved`** on the SR (and an SN leaves its draft state). The ratification
  date is git-derived (the commit that moved it).
- **`DevStg-Tests` → `DevStg-Impl`** — the SR is `Approved` and its tests
  pass; the derived bar follows. Note what `Approved` does and does not say: it
  blesses the row's **TEXT** and makes no claim that any test passed — whether
  they pass is the harness's answer, never a cell's.
- **Re-attest (an amended `Approved` row)** — **there is no Status cell to
  move.** An approved row whose content is later amended STAYS `Approved`;
  what marks it is the DIFFERENCE from its copy in
  `docs/archive/last_approved/`, and the pending-owner-actions projection
  carries one line per drifted SR. Read the before/after first — `python
  scripts/trace.py --ratify modified [--out docs/ratify/<date>-reattest.md]`
  (the scope word is a CLI name, not a Status value). Blessing the amendment
  is `python scripts/intake.py snapshot` in the reviewed commit: the copy IS
  the signature now, so without it the record of what was blessed does not
  move. If the amendment invalidated the evidence, that is the harness's
  problem to report and not a Status value. Record the ruling in the log's
  Decisions, like any ratification. Amend and re-copy in the **same commit**
  (the `--staged` warn enforces it); a row's `Status` answers for its OWN
  cells (owner ruling 2026-08-17) — a child LLR/TC amendment never touches
  the owning SR.

  > **The vocabulary is CLOSED at three values** — `Drafted`, `Approved`,
  > `Founded` — matched case-insensitively, and a value outside it is an
  > always-on integrity finding. `Founded` is COMPUTED (the artifacts the row
  > calls for exist); never type it to advance a gate. `Draft`, `Verified`,
  > `Planned` and `Modified` are RETIRED — `Verified`/`Planned` folded into
  > `Approved` (D-9, 2026-08-15), which is why there is no evidence-invalidated
  > Status, and `Modified` retired (2026-08-20) once the snapshot diff answered
  > the same question. Do not reintroduce them.

**Carry the batch-scoped hierarchy view.** A ratification brief presents the
batch's `SN → SR → LLR/TC` tree with its prose so the acceptor rules on the whole
decomposition, not a row list. **Generate it, never hand-copy:**
`python scripts/trace.py --ratify <phase> --out docs/ratify/<phase>-tests.md`
(scope is a phase tag or an `SR-###` list) emits the tree with each SR's
Requirement/AC, LLR Detail, TC Method/Expected, and any cited rubric — then link
that file from the `## OI-N` brief. `check_trajectory.py` warns (never fails)
when a `[phase]-[reqs|tests]` ratification brief carries no such link.

This preserves the reviewed-commit discipline while making the marker computed.
It **composes with the ratification levels**: level 4 = the human ratifies each
batch; a lower level hands the lower rungs to the loop; level 0 = a
fresh-context reviewer's recorded verdict ratifies. **An agent may make the
ratifying commit** on the acceptor's behalf, governed by that level. Record the
sign-off in `docs/log.md`'s **Sittings** table — a **sitting is an occasion, not
a rung**, so each row names the **rung range it certifies** rather than being one
row per boundary.

## What each bar takes

- **`DevStg-Reqs` (Needs · Boundary · Reqs certified).** Real SN/SR rows (no
  `-000` placeholders where committed), acceptance criteria measurable, the
  UX/edge-case lens applied. If the repo declares an `external.toml` frame, the
  boundary inventory is settled — every declared `[boundary.B-##]` crossing
  `approved` — or `DevStg-Boundary` honestly holds the ladder down (WI-442
  re-key; a repo with no `external.toml` skips the rung). Sign-offs recorded
  in `docs/log.md`.
- **`DevStg-Tests` (Arch · LLReqs · Tests certified).** If the repo declares a
  `components` registry, no component is still `planned` or `has-gap`. Every SR
  decomposes to LLR/TC; each requirement's TC exists as a **failing test first**
  (red → green). The harness at `DevStg-Tests` runs traceability +
  `--no-placeholders` + runnable tests + flow checks. `orphans=0`. **A tests
  batch also authors/updates the `IF-###` interface rows its new LLRs imply** —
  when a decomposition mints a seam (a module now provides/consumes a contract),
  add its `interfaces.toml` row in the same batch rather than retrofitting later
  (PROCESS.md §8; the `registry-hygiene` skill).
- **`DevStg-Impl` (Impl certified).** Code implements the LLRs with
  `Implements:` back-links; the full harness passes: `trace.py --strict
  --no-placeholders --strict-schema --require-verified`, coverage ≥ threshold,
  arch-map fresh, flows current. Every test-verifiable SR is `Approved`
  with its tests green.

Run the bar with `scripts/check.py` (it selects the bar's checks from
`docs/gate`); paste the real output into the `docs/log.md` audit log.

## Sync before you ratify (iteration-branch repos)

**Policy-flip sweep.** A change to any dial in `docs/process.toml` —
`human_ratification_through`, `push`, `review_rounds`, `guardrails` — is a
status-staleness event: in the same sitting, grep `docs/status.md` for old
pause/stop/approval wording and point it to the declared dial rather than
paraphrasing the value.

If the repo runs the **agent iteration branch & sync** layer
(`docs/process-options.md`; agent work rides `llm/<branch>`, the development
branch is curated), a bar closure is a **sync point**. Run the five-step ritual
before the ratifying commit lands: backup ref → scrub (privacy-checked repos
only; fail closed if the scrub agent can't run) → optional iteration-branch push
per the `push` dial → collate into categorical commits → land on the development
branch. The ratification (the `Status`-change commit + the regenerated
`docs/gate`) rides the landed, collated history. Landing is not a stopping
point — but *pushing* follows the `push` dial (default `human`: an agent never
pushes; the human publishes at leisure).

## Honest verification where machines can't (`Attest`)

Some SRs can't be mechanically tested (subjective quality, a binary asset, a
witnessed behavior). Use the **`Attest`** verification method: a **named human's
recorded judgment**, captured in the TC's `Parameters`/`Expected` cell (who +
when + what was judged) — a trust-based floor, not a runnable check. `Attest`
(like `Analysis`/`Inspection`) is **LLR-exempt** but still needs ≥1 TC. Don't
fake subjective work into a `Test`; give it an honest `Attest` home.

## Report attested vs. mechanized

`trace.py` always emits a **"Verification basis (attested vs mechanized)"**
count. When reporting a bar's readiness, state that split honestly — how many SRs
are machine-verified vs. resting on a human attestation — so a reviewer sees the
trust footprint rather than a single "all green". An attested bar can be
legitimate; hiding that it's attested is not.
